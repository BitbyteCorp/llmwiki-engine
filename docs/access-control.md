# 폴더별 접근 제어
전역 역할과 경로별 규칙을 함께 적용하여 웹, MCP와 도니가 사용자의 읽기·쓰기 범위를 지킨다.

## 배경
팀 위키에는 공용 지식과 일부 사용자만 읽을 수 있는 지식이 함께 들어간다. 목록에서 파일을 숨기는 것만으로는 검색 발췌, Git 패치, 대화 인용, 이벤트와 내보내기를 통한 노출을 막을 수 없으므로 모든 접점에서 같은 경로 정책을 적용한다.

## 내용

### 규칙과 우선순위
전역 역할 `viewer`, `editor`, `admin`은 유지한다. 관리자는 경로 규칙을 우회한다. 적용 가능한 규칙이 없는 경로는 조회자에게 읽기, 편집자에게 쓰기를 허용하므로 규칙을 만들지 않은 기존 설치의 동작은 바뀌지 않는다.

마이그레이션 `013_acl.sql`의 `acl_rules`는 `id`, `prefix`, `subject_type`, `subject`, `access`, `created_by`, `created_at`을 저장한다. `subject_type`은 `user`, `role`, `everyone`이고 `access`는 `none`, `read`, `write`다. 사용자 주체는 사용자 ID의 문자열, 역할 주체는 역할 이름, 전체 주체는 빈 문자열이다. 사용자 ID는 삭제 뒤 다른 이메일 계정의 접근 권한으로 해석하지 않는다.

접두사는 저장소 상대 경로다. 폴더 규칙은 `wiki/private/`처럼 `/`로 끝나고 파일 규칙은 `wiki/private/plan.md`처럼 정확한 파일 경로다. 루트 `/`는 모든 경로에 적용한다. 절대 경로, 상위 이동, 역슬래시와 Git 내부 경로는 허용하지 않는다.

사용자에게 적용 가능한 규칙이 있는 가장 긴 접두사를 먼저 고른다. 그 접두사 안에서는 사용자 규칙, 현재 전역 역할 규칙, 전체 규칙 순으로 하나를 고른다. 해당 사용자에게 적용되는 주체가 없는 더 긴 접두사는 상위 규칙을 무효화하지 않는다. `write` 규칙도 전역 `viewer`를 편집자로 올리지 않으며 실제 쓰기에는 전역 `editor` 이상이 필요하다.

`AclService`는 규칙을 캐시하고 규칙 변경 시 정책 버전으로 캐시를 무효화한다. 읽을 수 없는 경로는 존재 여부를 숨기는 `404 not_found`를 반환한다. 읽을 수 있지만 쓸 수 없는 경로는 `403 forbidden`을 반환한다.

### 관리 접점
관리 화면의 `접근 권한` 탭에서 접두사별 규칙을 조회하고 추가·삭제한다. 트리에서 폴더를 선택하거나 정확한 파일 경로를 입력하고 사용자·역할·전체 주체와 권한을 고른다. 같은 접두사와 주체에 다시 저장하면 기존 규칙을 갱신한다. 삭제는 확인을 요구한다. `접근 확인`은 선택 사용자와 경로의 실효 권한과 적용 규칙을 설명한다.

| 요청 | 응답과 동작 |
| --- | --- |
| `GET /api/admin/acl` | `{ rules }`를 반환한다. |
| `POST /api/admin/acl` | `{ prefix, subjectType, subject, access }`를 받아 `201 { rule }`을 반환한다. |
| `DELETE /api/admin/acl/:id` | 규칙을 삭제하고 `204`를 반환한다. |
| `GET /api/admin/acl/check?userId=&path=` | `{ userId, path, access, rule, reason }`을 반환한다. `reason`은 `admin`, `rule`, `role_default`다. |

모든 접점은 관리자만 사용하며 생성·갱신·삭제는 감사 로그에 기록한다. OAuth·REST 토큰은 별도 권한 주체가 아니라 토큰 소유자의 현재 사용자 역할과 경로 규칙을 적용한다.

사용자를 삭제하면 해당 사용자 주체의 규칙도 같은 DB 트랜잭션에서 감사·삭제하고 정책 버전을 바꾼다. SQLite가 삭제된 숫자 ID를 새 계정에 재사용하더라도 이전 계정의 경로 권한을 상속하지 않는다.

### 읽기와 쓰기 범위
노트 트리·내용·이름 해석·줄 출처·원문 파일은 읽을 수 있는 경로만 반환한다. 이름 해석 후보에서도 숨겨진 경로를 제거한다. 직접 저장·삭제와 첨부 저장은 대상 쓰기 권한을 요구하고 이동은 원본과 대상 모두 검사한다. 되돌리기는 선택한 변경의 모든 경로에 쓰기 권한을 요구한다.

전체 이력은 읽을 수 있는 파일을 건드린 커밋만 페이지에 포함한다. 커밋 상세·비교·작업 상세의 파일과 패치는 읽을 수 있는 경로로 제한하며 이름 변경은 이전 경로도 검사한다. 읽을 수 없는 경로만 변경한 커밋은 노출하지 않는다. 접근 가능한 변경과 제한된 변경이 섞인 경우 제한된 내용을 담을 수 있는 요약·본문도 보수적으로 가린다.

파일과 디렉터리가 같은 이름으로 바뀌는 이력에서도 허용된 파일 이름을 재귀 Git 경로 선택으로 확장하지 않는다. 패치는 정확히 허용된 파일만 가진 임시 Git 트리에서 생성한다. 병합 커밋의 요약·본문·trailer는 선택한 비교 부모가 아니라 모든 부모의 변경 경로로 인가하므로 다른 부모를 고르는 것으로 제한된 설명을 읽을 수 없다.

검색은 결과 페이지를 만든 뒤 숨기는 대신 후보 제한과 벡터 top-k 전에 읽기 정책을 적용한다. 관련 노트, 자동 완성, 유사 노트와 중복 후보에도 같은 정책을 적용한다. 검색 커서는 사용자·역할·정책 버전에 묶이며 규칙을 바꾼 뒤 이전 커서는 새 검색으로 대체한다. 그래프에는 읽을 수 없는 노드와 간선이 없고 태그 수는 읽을 수 있는 서로 다른 노트 수다.

활동·일기·꿈꾸기 조회는 경로와 관련 변경을 필터링하고 읽을 수 없는 변경만 있는 요약을 가린다. `main.updated.paths`는 SSE 구독자별로 필터링하며 읽을 수 있는 경로가 하나도 없으면 이벤트를 보내지 않는다. 내보내기는 선택 접두사 아래의 읽을 수 있는 파일만 아카이브에 넣는다.

실시간 구독은 이벤트 전달 시 현재 사용자를 다시 조회하므로 연결 중 역할 변경과 사용자 삭제도 적용한다. 활동과 검색 커서는 사용자·역할·정책 버전에 결합한다. 제한된 변경과 공개 변경이 섞인 꿈꾸기 요약·오류·push 사유도 보수적으로 가린다.

활동·일기 조회와 내보내기는 비동기 Git·파일 작업 뒤 응답을 확정하기 전에 현재 사용자 신원·역할·정책을 다시 확인한다. 처리 중 권한이 바뀐 스냅샷은 403으로 폐기하며 자동으로 재시도하지 않는다. 내보내기는 응답 헤더와 스트림을 시작하기 직전에도 확인한다.

ZIP은 읽을 수 있는 파일만 담을 수 있지만 Git bundle은 전체 과거 객체를 포함하므로 안전한 경로별 필터링이 불가능하다. ACL 규칙이 하나라도 있으면 비관리자의 bundle 요청은 403으로 거절한다. 관리자의 bundle과 로컬 CLI 내보내기는 명시적인 시스템 작업으로 제한 없이 수행한다.

MCP 도구·리소스·경로를 받는 프롬프트는 인증된 토큰 사용자의 정책을 적용한다. 도니 질의의 검색과 노트 읽기도 질문한 사용자로 실행하며 인용과 고정 노트 문맥을 검증한다. 초안 생성도 대상 경로의 쓰기 권한을 요구한다.

대화 중 `write_knowledge`는 전역 `editor`·`admin`에게만 제공한다. 전역 `viewer`는 자신이 만든 대화의 소유자이거나 대화 구성원 편집자여도 이 도구를 받지 못하며 읽기 질의응답은 계속 이용한다. 대화 서비스는 허용된 요청에만 제출 콜백을 전달하고 도구 실행 시에도 전역 역할과 현재 대화·읽기 정책을 검사한다. REST Bearer로 질문 작성·수정·재시도·재생성을 요청하면 기존 [변경 요청의 `write` scope 검사](auth.md#rest-api-토큰)를 거치므로 `read` 범위 토큰으로 이 쓰기 경로에 진입할 수 없다.

도구 제공 자체는 특정 경로에 대한 저장 허가가 아니다. 접수한 작업은 아래의 요청자별 근거 읽기·변경 경로 쓰기 검사도 통과해야 한다. 기록 요청의 비동기 결과는 [쓰기 흐름](write-flow.md#대화에서-제출하는-쓰기)에 기록한다.

도니 쓰기 작업은 요청자의 현재 역할과 규칙을 다시 조회한다. 작업 워크트리의 변경 경로를 머지 전에 검사하고 충돌 해결 뒤 실제 main 반영 직전에도 검사한다. 허용되지 않은 경로를 바꾸면 명확한 권한 오류와 함께 작업을 실패로 끝내며 main에 반영하지 않는다. 수집 원문을 `raw/`에 보존하는 시스템 쓰기는 허용하지만 이어지는 도니 통합 작업은 수집 요청자의 권한을 따른다.

읽은 원문 경로는 작업 단계 이력에 출처로 보존하고 실행 중 정책이 바뀌면 출처 읽기 권한도 main 반영 전에 다시 검사한다. 규칙이 있는 상태에서 출처 추적이 없는 과거 도니 작업은 비관리자의 조회에서 입력·요약을 가리며 실행·재시도를 거절한다. 필요한 내용은 현재 읽기 범위 안에서 새 작업으로 제출한다.

작업 조회는 패치를 만들지 않고 모든 부모에 대한 변경 경로를 모아 권한을 판정하므로 큰 패치도 조회 제한의 근거가 되지 않는다. 커밋을 해석할 수 없거나 직접 작업의 입력을 해석할 수 없으면 비관리자의 작업 메타데이터를 보수적으로 가린다. 관리자는 이 경우에도 입력·요약·커밋 정보를 그대로 볼 수 있으며, 경로 수집 뒤 현재 사용자와 정책이 유지되는지 확인하는 절차는 적용한다.

### 공유 대화
대화 구성원 권한은 대화 자체에 대한 접근을 정하며 노트 접근 권한을 대신하지 않는다. 각 구성원이 볼 수 있는 인용은 해당 구성원의 읽기 정책으로 제한한다. 제한된 인용이나 고정 문맥을 사용한 턴은 인용 목록만 지우면 답변 본문으로 내용이 새므로 해당 구성원에게 턴 본문과 문맥도 보수적으로 가린다. 생성 이벤트의 재생과 실시간 전달에도 같은 제한을 적용하고, 다른 사용자의 제한된 턴이나 요약을 도니의 새 질문 문맥으로 재사용하지 않는다.

다른 구성원의 실행 중 답변과 이벤트는 출처를 확정할 수 있을 때까지 전달하지 않고 종료 뒤 해당 구성원의 정책으로 투영한다. 새 생성은 출처 추적 여부와 읽은 경로를 영속 프레임에 기록하며 내부 출처 프레임은 SSE로 내보내지 않는다. 규칙이 있는 상태에서 출처 추적이 없는 과거 턴은 비관리자에게 보수적으로 가린다. 규칙이 없는 기존 설치의 과거 대화는 그대로 보인다. 저장된 공통 요약은 새 질문의 문맥으로 재사용하지 않고 질문자가 읽을 수 있는 턴에서 다시 만든다.

사용자가 직접 입력한 자유 문장에는 서버가 모든 출처를 알아낼 수 없다. 접근 제어는 이미 허용된 사람이 비밀을 공용 메시지에 직접 복사하는 행위까지 자동으로 판별하는 내용 검열 기능이 아니다.

### 꿈꾸기와 한계
꿈꾸기는 사용자가 아닌 시스템 작업으로 전체 지식을 읽고 정리한다. 정리 지침은 제한된 폴더의 정보를 더 넓게 공개되는 폴더·메모리·일기로 이동하거나 복사하지 않도록 명시한다. 규칙이 있는 상태의 실행에는 ACL 경계 간 정보 이동을 자동으로 보장할 수 없다는 경고를 감사 로그와 실행 로그에 남긴다.

서로 다른 표현으로 같은 사실을 옮기는 의미적 복사까지 경로 권한만으로 판별할 수는 없다. 따라서 꿈꾸기는 경로별 요청자 쓰기 검사와 달리 정보 흐름 격리를 보장하지 않는다. 민감한 지식을 운영하는 관리자는 실행 기록과 변경을 검토하고, 완전한 정보 흐름 격리가 필요한 경우 자동 꿈꾸기 실행을 사용하지 않아야 한다.
