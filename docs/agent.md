# 도니
도니는 엔진에서 지식 쓰기·충돌 해결·꿈꾸기·웹 질의응답을 수행하는 에이전트이며, 제공자는 `LLM_PROVIDER`, 모델은 `LLM_MODELS`로 고른다.

## 배경
엔진은 사용자가 보낸 지식을 문서에 반영하고, 기존 지식과의 관계를 정리하며, 지식을 근거로 질문에 답해야 한다. Luna는 모델 이름이지 에이전트 이름이 아니므로 에이전트를 도니로, 코드 식별자와 기존 `luna` 작업 종류를 `agent`로 분리했다. 도니가 파일을 편집하는 경계는 엔진이 통제하며, 검색에 필요한 임베딩은 응답 모델과 별도로 선택한다.

## 내용
### Nest 모듈과 의존성
`src/agent/`의 `AgentModule`은 `KnowledgeModule`과 `RagModule`을 가져오고, `agent.service.ts`의 `AgentService`와 `checkpoints.repository.ts`의 `AgentCheckpointsRepository`를 제공하며 다른 모듈에 내보낸다. 서비스는 설정·로그를 공용 `CONFIG`, `LOGGER` 토큰으로 주입받고, `KnowledgeRepo`와 `SearchService`를 클래스 타입으로 주입받는다. 체크포인트 저장소는 공용 `DB` 토큰으로 SQLite 연결을 주입받는다.

에이전트 도구와 실행 옵션의 형식은 `agent.types.ts`에 두며, 작업 워크트리 도구는 `worktree.ts`, 쓰기와 충돌 해결의 절차는 `writes.ts`에 둔다. 서비스는 에이전트 실행·문맥 로딩·쓰기·충돌 해결·질의응답의 인터페이스를 유지한다. 대화 중 쓰기 작업 제출은 대화 서비스가 `answer()`에 전달하는 콜백으로 연결하므로 `AgentModule`이 `JobsModule`을 가져오는 순환 의존성을 만들지 않는다.

### 모델과 호출 방식
엔진은 OpenAI SDK와 Responses API의 함수 호출(function calling)을 사용해 도니를 실행한다.

`LLM_MODELS`는 쉼표로 구분한 선택 가능 모델 목록이며 제공자별 기본값은 [환경 변수](development.md#환경-변수)를 따른다. 각 항목의 앞뒤 공백을 제거하고 빈 항목을 버리며, 정리한 목록은 비어 있을 수 없다. 첫 항목이 기본 모델이고 웹 답변의 요청별 `model`도 이 목록에 있어야 한다. 대화 서비스는 사용자 메시지를 저장하기 전에 `AgentService.validateModel()`과 `validateEffort()`를 호출하며 `answer()`도 모델 호출 전에 검증한다. `GET /api/models`는 선택 가능 모델과 첫 항목인 기본 모델, 요청 가능한 추론 강도와 서버 기본 강도를 반환한다. 웹 API의 요청별 추론 강도는 `low`, `medium`, `high`만 받으며 웹에서 서버 기본값을 선택할 때는 `effort`를 생략한다. API 키·주소와 `LLM_REASONING_EFFORT`·`LLM_BACKGROUND_REASONING_EFFORT`의 허용 값·기본값도 위 환경 변수 표를 따른다.

함수 호출 결과를 다음 Responses 입력으로 돌려주는 루프를 사용한다. 도구 실행이나 인자 해석 실패는 오류를 담은 도구 출력으로 모델에 전달하므로 도니가 수정하거나 설명할 수 있다. 기본 호출 상한은 32턴이며 상한 안에 작업을 끝내지 못하면 실패한다. 웹 답변은 텍스트 델타를 즉시 전달하고, 취소 신호가 오면 추가 모델·도구 호출을 중단한다.

`runAgent()`는 `{ text, finalText, toolCalls }`를 반환한다. `text`는 도구 호출 턴의 진행 설명까지 모든 턴의 텍스트를 이어 붙인 누적값이며 스트리밍과 인용을 쓰는 대화 답변이 사용한다. `finalText`는 이번 실행에서 승인한 마지막 도구 없는 턴의 텍스트만 담고, `beforeFinish`가 거절한 응답은 포함하지 않는다. 쓰기 작업 요약(턴 한도 마무리 포함), `proposal()`의 초안 본문과 경로 선택, 꿈꾸기 실행 요약, 서브에이전트 결과는 `finalText`를 사용한다. 상용 쓰기 요약에 "먼저 … 확인하겠다" 같은 중간 진행 설명이 최종 요약 앞에 붙고, 도니의 영어 메모가 섞여 저장된 사례가 있었기 때문이다. 초안 본문에 진행 설명이 섞이면 저장할 Markdown 파일 자체가 오염된다.

`answer()`는 텍스트 또는 Responses의 `input_text`·`input_image`·`input_file` 콘텐츠 배열을 사용자·답변 메시지의 입력으로 받는다. 진행 이벤트는 `status` 단계, 도구의 `start`·`end`, 최종 인용, 모든 모델 턴을 합산한 `usage`다. 토큰 필드와 합산 경계는 아래의 [비용과 사용량](#비용과-사용량)을 따른다. 읽기 도구의 공개 요약은 검색 질의나 노트 경로만 담으며 도구 결과나 노트 본문을 넣지 않는다. `write_knowledge`는 예외로 시작·종료 요약에 제출할 `content`의 앞 80자까지 표시하므로 기록할 내용 자체가 대화 구성원에게 보일 수 있다. 생성의 근거 경로와 ACL 투영은 [공유 대화](access-control.md#공유-대화)의 규칙을 따르며, 기록 요청의 성공한 도구 종료 이벤트에는 작업 링크용 `jobId`를 별도로 담는다.

#### 제공자 선택
`LLM_PROVIDER`로 `openai`, `openrouter`, `openai-codex`를 선택한다. OpenAI와 OpenRouter는 같은 OpenAI SDK로 Responses API와 Embeddings API를 호출한다. Codex는 CLI로 로그인한 ChatGPT OAuth 자격 증명으로 Responses API만 호출하며, 로그인·상태 확인·로그아웃 절차는 [Codex OAuth](codex-oauth.md)를 따른다. 키·기본 주소·모델 기본값과 명시한 설정의 우선순위는 [환경 변수](development.md#환경-변수)에 기록한다.

Codex의 ChatGPT 로그인은 OpenAI Platform API 키와 별개다. `openai-codex`에서도 문서·질의 임베딩은 `OPENAI_API_KEY`와 선택적인 `OPENAI_BASE_URL`을 사용하는 Platform 경로에 남는다. `CODEX_BASE_URL`은 Codex Responses 주소만 바꾸며 임베딩 주소나 키를 대체하지 않는다. 따라서 Codex 로그인이 되어 있어도 임베딩에는 별도 API 키가 필요하다.

Codex fetch 어댑터는 모든 Responses 요청을 `stream: true`, `store: false`로 보내고 `max_output_tokens`와 `max_completion_tokens`를 제거하며 비어 있지 않은 `instructions`를 보장한다. 비스트리밍 호출자에게는 SSE의 `response.completed` 최종 응답을 JSON으로 돌려주므로 호출자는 기존 SDK 응답 형식을 사용한다. HTTP 401이면 OAuth 자격 증명을 갱신하고 요청을 한 번 다시 보낸다.

서버 측 문맥 압축은 `openai`에서만 사용한다. OpenRouter의 Responses API는 stateless beta이며 `context_management`를 지원하지 않고 Codex에도 이 매개변수를 보내지 않는다. 따라서 두 제공자의 긴 실행은 [문맥 크기와 도구 페이지](#문맥-크기와-도구-페이지)의 도구 출력 상한과 페이지 읽기에 의존한다. 세 제공자 모두 `store: false`, 암호화 추론 포함, 프롬프트 캐시 키, 추론 강도와 함수 도구 설정은 유지한다.

OpenRouter 모델 ID는 `openai/...`처럼 제공자 이름을 포함해야 한다. `.env.example`을 복사한 설정에는 OpenAI 모델 ID가 명시되어 있으므로 OpenRouter로 바꿀 때는 `LLM_MODELS`와 `EMBEDDING_MODEL`도 해당 ID로 바꾸거나 두 줄을 지워 제공자별 기본값을 적용한다. `LLM_MODELS=`처럼 빈 값으로 남기면 시작 시 거절한다. 제공자 전환으로 임베딩 모델 문자열이 바뀌면 기존 벡터의 재임베딩이 필요하며, `vector_mismatch`와 재구축 절차는 [RAG의 신선도와 정직한 저하 모드](rag.md#신선도와-정직한-저하-모드)를 따른다. 제공자를 바꿔도 [임베딩 모델을 분리하는 이유](#임베딩-모델을-분리하는-이유)는 그대로 적용된다.

#### 비용과 사용량
비용 개선의 근거가 된 대화 답변 9건의 관찰에서 입력 토큰 합계는 427,936개, 출력 토큰 합계는 12,778개였다. 토큰 수는 입력이 지배적이므로 답변을 짧게 만드는 것만으로는 반복 전송되는 문맥 비용을 충분히 줄이지 못한다. 이 수치는 해당 표본의 토큰 수이며 모델별 가격·캐시 적중률을 반영한 청구 금액이나 모든 요청의 절감률을 뜻하지 않는다. 따라서 공통 프롬프트의 캐시 재사용, 더 이른 문맥 압축, 필요한 부분만 읽는 도구 페이지를 우선 적용하고 백그라운드 추론과 위임 규모도 제한한다.

모든 `runAgent()` Responses 요청은 `prompt_cache_key: llmwiki:<lane>:<model>`을 보낸다. `lane`은 `chat`, `summarize`, `proposal`, `write`, `subagent`, `conflict`, `dreaming`이며 운영 호출자는 용도를 명시한다. 직접 호출자의 이전 계약을 보존하기 위해 생략한 `lane`만 `chat`으로 처리한다. 키에는 작업 ID·날짜·턴 번호를 넣지 않으므로 같은 용도와 모델의 실행 사이에서도 안정적으로 유지된다. 키는 캐시 재사용을 돕는 값이지 적중을 보장하거나 서로 다른 입력을 같은 결과로 치환하는 응답 캐시가 아니다.

실행 루프는 `instructions`와 함수 도구 정의를 실행 시작에 한 번 구성해 턴 사이에 고정한다. 공통 지침·도구 접두사 앞에 턴별 메시지나 작업 식별자를 끼워 넣지 않으며, 후속 메시지와 도구 결과는 `input`에 추가한다. 공유 접두사 이후에 지식 저장소 문맥이나 작업 자료가 달라질 수 있으므로 실제 재사용량은 응답의 캐시 사용량으로 확인한다.

`summarize`, `write`, `subagent`, `conflict`, `dreaming`은 백그라운드 추론 강도를 사용한다. 대화 답변인 `chat`과 읽기 전용 초안인 `proposal`은 기존 기본 추론 강도를 유지하며, `RunAgentOptions.effort`가 있으면 어느 용도에서든 그 값이 우선한다. 서브에이전트의 총 생성 수와 동시 실행 수는 [쓰기 서브에이전트](#쓰기-서브에이전트)의 상한을 따른다.

`TokenUsage`는 `inputTokens`, `cachedInputTokens`, `outputTokens`, `reasoningTokens`를 담는다. `cachedInputTokens`는 Responses의 `input_tokens_details.cached_tokens`를 합산한 입력 토큰의 부분집합이며 입력 합계에 다시 더하지 않는다. `reasoningTokens`도 출력 토큰의 부분집합이다. 새 실행에서 생성하는 사용량은 캐시 정보가 없더라도 숫자 `cachedInputTokens: 0`을 포함한다. 과거 메시지·체크포인트 JSON에는 이 필드가 없을 수 있으므로 타입과 대화 스트림 스키마는 선택적으로 유지하고 표시·재개 시에는 0으로 해석한다. 웹 답변 하단에는 입력·캐시·출력·추론 토큰 수를 함께 표시한다. 과거 캐시 사용량을 추측해 채우지는 않는다.

`RunAgentOptions.onUsage`는 누적치가 아니라 사용량을 받은 응답 한 건의 델타를 즉시 전달한다. 실패·미완료 응답도 사용량이 있으면 오류를 던지기 전에 전달하며, 사용량을 받지 못한 실패는 추정하지 않는다. 최종 `onEvent('usage', ...)`와 체크포인트의 `usage`는 재개한 이전 사용량을 포함한 실행 누적치다. 따라서 작업별 비용은 델타 콜백으로 합산해야 하며 재시도에서 체크포인트 누적치를 다시 더하지 않는다. 대화 메시지는 기존 `messages.usage` 열의 JSON에 누적 사용량을 보존하므로 캐시 필드 추가를 위한 DB 마이그레이션은 필요하지 않다. 쓰기 작업의 영속 이벤트·로그 경계는 [쓰기 사용량](write-flow.md#쓰기-사용량)에, 꿈꾸기의 로그 경계는 [꿈꾸기 실행 기록](dreaming.md#실행-기록과-운영-조회)에 기록한다.

같은 응답 델타는 모든 실행 용도에서 공통 사용량 원장에 저장한다. 관리자 집계·보존 기간과 검색·임베딩을 포함하는 기록 범위는 [운영의 LLM 사용량 원장](operations.md#llm-사용량-원장)을 따른다.

#### 문맥 크기와 도구 페이지
한 도니 요청의 입력이 358,989토큰까지 커져 조직의 분당 토큰 제한(TPM)에 걸린 사례가 있었다. `store: false` 실행에서 매 턴 이전 입력·추론·도구 결과를 모두 다시 보내던 방식은 큰 파일과 반복 읽기가 누적될수록 문맥을 키웠다. `openai`의 각 Responses 요청은 `context_management: [{ type: 'compaction', compact_threshold: N }]`를 보내 서버 측 문맥 압축을 사용한다. OpenRouter와 Codex의 예외는 [제공자 선택](#제공자-선택)을 따른다. `N`과 낮춘 기본값은 [환경 변수](development.md#환경-변수)의 `LLM_COMPACT_THRESHOLD`를 따른다. 이 임계값은 압축을 시작하는 기준이지 TPM 제한 자체를 보장하는 예산은 아니다.

서버가 반환한 암호화 `compaction` 항목은 메시지·함수 호출·암호화 추론과 함께 다음 입력에 보존한다. 가장 최근 압축 항목보다 앞선 입력은 모두 버리고 그 항목 이후의 입력과 이번 턴 도구 출력을 연결한다. 스트리밍에서도 `response.completed`의 최종 출력에 같은 규칙을 적용한다. 승인된 마지막 도구 없는 응답은 다음 호출이 없으므로 입력에 추가하지 않는다. 완료 검사에서 거절된 응답은 후속 요청이 있으므로 응답 항목과 재작업 지시를 입력에 보존한다.

모든 함수 도구의 결과와 오류 출력은 잘림 안내를 포함해 최대 16,000자로 제한한다. 안내는 모델에 페이지를 이어 읽거나 검색 범위를 좁히도록 요구한다. `read_note`와 `read_file`은 기본·최대 300줄, 본문과 직렬화된 본문 각각 최대 12,000자 안의 페이지를 반환한다. 결과에는 `content`, `totalLines`, `nextOffset`, `truncated`가 있으며 `offset`은 0부터 시작하는 줄 번호다. 긴 한 줄을 나누면 `nextCharOffset`도 반환하므로 다음 호출에 `offset: nextOffset`, `charOffset: nextCharOffset`을 전달한다. 줄 경계에서 이어 읽을 때 `charOffset`은 생략하거나 0으로 둔다. 마지막 페이지의 `nextOffset`은 `null`이다. 페이지는 줄바꿈을 보존하므로 순서대로 본문을 연결하면 원문을 얻는다. 전체 파일을 덮어쓰는 `write_file`은 원래 계약을 유지하므로 수정 전 필요한 모든 페이지를 읽고 원문 전체를 재구성해야 한다.

고정 노트 문맥도 전체 본문을 모델 입력에 넣지 않고 위와 같은 첫 페이지와 `path`, 고정 `sha`, 페이지 메타데이터만 전달한다. 나머지는 `read_note`에 `nextOffset`과 필요한 `nextCharOffset`을 전달해 이어 읽도록 안내한다. 이어 읽기는 최초에 고정한 버전을 사용하므로 답변 중 main이 바뀌어도 원문이 섞이지 않는다. 선택 인용은 최대 32,000 UTF-16 코드 단위이며 서로게이트 쌍을 나누지 않는 경계에서 자른다. 체크포인트에는 인용 검증을 위한 전체 원문을 별도로 보존하지만 이를 모델 입력에 다시 넣지는 않는다. 전체 원문이 없는 이전 체크포인트의 고정 문맥은 저장된 `sha`에서 전체 노트를 복원해 다음 페이지를 읽는다. 첨부 재생의 별도 예산은 [첨부 파일과 가져오기 업로드](#첨부-파일과-가져오기-업로드)를, 충돌 버전의 페이지 읽기는 [쓰기 흐름](write-flow.md#충돌-해결)을 따른다.

도구 출력·발췌의 잘림과 본문 페이지의 시작·끝은 유니코드 코드 포인트 경계에 맞춰 이모지의 UTF-16 서로게이트 쌍을 나누지 않는다. OpenAI가 단독 서로게이트를 `400 invalid_json`으로 거절하므로, 매 Responses 요청 전 입력 문자열을 정상 유니코드로 정규화해 이미 잘못 저장된 체크포인트의 단독 서로게이트도 U+FFFD로 치환하고 재개한다.

`list_files`는 한 페이지에 최대 500개 경로를 반환하며 직렬화한 경로 배열에도 위의 본문 페이지 문자 예산을 적용한다. 경로가 길면 개수 상한에 도달하기 전에 페이지가 끝날 수 있으며, 첫 경로가 예산보다 길면 이어 읽기가 진행되도록 그 한 경로는 반환한다. 반환된 `nextOffset`과 같은 `prefix`로 이어 읽거나 디렉터리로 범위를 좁힌다. 도니의 검색 `limit`은 최대 30건이다. 서브에이전트의 결과와 오류 문자열은 각각 최대 8,000자로 제한한다. 꿈꾸기에서 관련 노트의 본문을 미리 넣는 대신 짧은 발췌와 경로를 제공하는 규칙은 [꿈꾸기](dreaming.md)에 기록한다.

#### 실행 체크포인트
`src/agent/agent.types.ts`의 `AgentCheckpoint`는 다음 요청에 보낼 `input`, 누적 답변 `text`, 누적 도구 호출 수 `toolCalls`, 선택적인 누적 토큰 `usage`를 담는다. `RunAgentOptions.onCheckpoint`는 한 턴의 도구 출력이 모두 추가된 뒤 압축 이전 문맥이 제거된 상태의 독립적인 JSON 직렬화 가능 스냅샷을 동기적으로 받는다. 승인된 마지막 도구 없는 응답에는 호출하지 않지만 완료 검사에서 거절된 응답과 재작업 지시가 추가되면 호출한다. 거절된 완료 문구는 누적 답변에 합치지 않는다. 따라서 이전 턴에 실행한 도구를 다시 실행하지 않고 다음 모델 호출부터 이어갈 수 있다.

`RunAgentOptions.resume`을 지정하면 `input` 옵션은 무시하고 저장된 입력·답변·호출 수·사용량에서 실행을 이어간다. `maxTurns`는 재개 실행에서 새로 계산한다. 실행 루프는 SQLite를 직접 읽거나 쓰지 않으며 호출자가 권한과 수명에 맞게 저장·조회·삭제 시점을 결정한다.

`RunAgentOptions.beforeFinish`는 도구 없는 응답을 승인하기 전에 실행한다. 후속 사용자 지시 문자열을 반환하면 완료를 거절하고 그 지시를 추가한 뒤 턴 루프를 계속하며, `undefined`를 반환하면 기존 방식으로 종료한다. `onTurnLimit`는 턴 상한에 도달했을 때 호출자가 구체적인 실패 원인을 던질 수 있는 훅이다. 가져오기 작업의 필수 원문 읽기 판정은 [원문 수집](ingestion.md#통합-작업과-복구)에 기록한다.

부모 쓰기 실행은 고정 `instructions`에 턴 예산과 한도 전에 작성·검토·커밋을 마쳐야 한다는 지시를 넣는다. `runWrite()`의 `beforeTurn`은 이번 실행에서 완료한 모델 턴을 0부터 세고, 현재 요청을 포함해 12턴이 남은 85번째 요청 직전에 사용자 경고를 한 번만 추가한다. 경고는 새 탐색을 멈추고 이미 읽은 자료로 노트를 작성·확장한 뒤 실행 중인 자식의 종료 대기, 실제 변경 검토, 커밋, 최종 요약을 순서대로 마치도록 요구한다. 후속 턴마다 경고를 다시 추가하거나 공유 프롬프트 접두사를 바꾸지 않는다. 재개 시에는 저장된 대화와 별개로 카운터를 0부터 다시 시작하며 이전 실행의 경고가 대화에 남아 있어도 이번 실행의 임계점에서만 새 경고를 추가한다. 이 경고를 도입한 실패 사례와 읽기 순서는 [도니 비동기 쓰기](write-flow.md#도니-비동기-쓰기)에 기록한다.

`AgentCheckpointsRepository`는 `save(owner, checkpoint)`, `get(owner)`, `delete(owner)`, `copy(from, to)`를 제공한다. 없는 owner의 `get`은 `undefined`, 없는 원본의 `copy`는 `false`다. `019_agent_checkpoints.sql`의 `agent_checkpoints` 테이블에 owner별 JSON 문서와 갱신 시각을 저장한다. owner는 `message:<메시지 ID>` 또는 `job:<작업 ID>` 같은 불투명 문자열이며 서비스에서 이미 사용하는 base62 ID 표현을 그대로 붙인다. 접두사를 포함한 owner나 체크포인트의 재생 문서는 SQLite의 UUID 열처럼 다시 인코딩하지 않는다. 식별자 표현 경계는 [식별자](identifiers.md)를 따른다.

체크포인트를 쓰는 호출자는 두 곳이다. 실패·취소·중단된 대화 답변의 이어서 재시도는 [웹](web.md)의 대화 절에서, 실패한 지식 쓰기 작업의 이어서 재시도는 [쓰기 흐름](write-flow.md)에서 설명한다. 꿈꾸기는 체크포인트를 저장하지 않는다. 실패한 꿈꾸기는 다음 실행이 마지막 성공 지점 이후의 변경과 아직 학습하지 않은 메시지를 다시 모으므로 같은 실행을 이어갈 필요가 없다.

#### OpenAI 재시도 정책
도니의 Responses 호출과 문서·질의 임베딩은 `src/common/openai.ts`의 공용 클라이언트 팩터리를 사용한다. LLM 팩터리는 설정한 제공자에 따라 API 키 기반 클라이언트 또는 Codex OAuth fetch 어댑터를 선택하고, 임베딩 팩터리는 API 키 기반 경로를 유지한다. 최대 재시도 횟수는 [환경 변수](development.md#환경-변수)의 `OPENAI_MAX_RETRIES`로 정하며, 실제 재시도·백오프·취소는 OpenAI SDK가 담당한다. Codex의 요청 변환과 401 갱신 외에는 어댑터가 SDK의 요청 인자와 취소 신호를 그대로 fetch에 전달한다.

OpenAI SDK는 HTTP 429를 재시도하지만 `x-ratelimit-reset-tokens`와 `x-ratelimit-reset-requests`를 대기 힌트로 읽지 않는다. 따라서 분당 토큰 제한(TPM)을 만났을 때 SDK의 기본 백오프만으로는 토큰이 다시 사용 가능해지기 전에 재요청할 수 있다. 어댑터는 기존 `Retry-After` 또는 `retry-after-ms`가 없는 429 응답에만 `retry-after-ms`를 추가한다. 두 reset 헤더에서 해석 가능한 기간 중 최댓값을 사용하고, 유효한 reset 헤더가 없으면 오류 본문의 `try again in <기간>` 메시지를 사용한다. 선택한 기간에는 250ms의 여유를 더한다. 기존 대기 헤더와 429가 아닌 응답은 변경하지 않으며, 본문을 읽을 때는 응답 복제본을 사용해 SDK가 원래 오류 본문을 그대로 읽게 한다.

SDK는 60초를 초과하는 대기 힌트를 무시하고 기본 백오프로 돌아간다. 250ms의 여유를 더한 값에도 이 제한이 적용되며, 엔진이 별도 대기 루프를 두어 제한을 우회하지는 않는다.

선택적 검색 질의 확장과 재정렬도 공용 LLM 팩터리를 사용하므로 설정한 제공자와 Codex 로그인을 따른다. 다만 SDK 옵션은 기존의 `maxRetries: 0`, 5초 타임아웃을 유지하며, 실패하면 질의 확장은 원래 질의를, 재정렬은 기존 검색 순위를 사용한다. Codex 어댑터의 401 갱신 한 번은 이 SDK 재시도 설정과 별개다. 질의 임베딩에는 공용 임베딩 재시도 정책이 적용된다.

### 사용처
- 지식 쓰기에서는 [쓰기 흐름](write-flow.md)의 문서 반영 판단과 편집을 맡는다.
- 머지 충돌 해결에서는 [쓰기 흐름](write-flow.md)의 작업 워크트리에서 충돌을 해결한다.
- [꿈꾸기](dreaming.md)에서는 변경된 지식과 기존 지식을 검토하고 정리한다.
- [웹 질의응답](web.md)에서는 [RAG](rag.md)를 활용해 지식을 근거로 답한다.

도니의 기본 문맥에 항상 포함하는 메모리의 형식·예산·갱신과 통합 규칙은 [지식 저장소](knowledge-repository.md#메모리-파일의-문맥-제공-규칙)에 기록한다.

`baseInstructions()`는 main의 루트 작성 규칙·메모리와 함께 공유 `WikiCatalog`의 읽기 권한별 목차를 인용된 참고 자료로 제공한다. 도메인 허브와 설명, 주제 폴더별 노트 수, 아직 주제 폴더에 배치되지 않은 노트 수를 표시하며 공유 개념·엔티티는 제목과 설명을 표시한다. 코드가 파일과 frontmatter에서 생성하므로 허브에 연결되지 않은 노트도 목록에서 사라지지 않는다. 목차의 크기·캐시·권한 경계는 [MCP의 서버 지침](mcp.md#서버-지침과-개인정보-경계)을 따른다. 도니는 해당 도메인에 쓰거나 편집하기 전에 `wiki/<domain>/AGENTS.md`가 있으면 읽는다. 도메인 schema의 적용 범위와 우선순위는 [도메인 schema](knowledge-domains.md#도메인-schema)를 따른다.

### 엔진이 정의하는 함수 도구
도니에게는 OpenAI 호스티드 셸 대신 엔진이 정의한 함수 도구를 제공한다. `search`는 main의 검색 색인과 [RAG의 두 단계 기본 검색](rag.md#기본-검색의-두-단계)을 사용한다. `browse_catalog`는 `{ folder: "wiki/<domain>/<topic>/" }`를 받아 현재 사용자가 읽을 수 있는 main의 전체 하위 노트 목차를 `{ folder, listing }`으로 반환한다. 각 항목은 제목·경로·유형·설명을 담으며 인바운드 링크가 없어도 포함된다. 이 도구와 검색 결과는 작업 워크트리의 미머지 편집을 포함하지 않는다. 작업 파일을 읽거나 편집할 때는 `list_files`, `read_file`, `write_file`, `delete_file`, `move_file`, `commit`을 사용하며 이 도구는 작업 워크트리 안으로 제한된다.

예를 들어 지식 쓰기나 충돌 해결 중 파일을 편집할 때도, 도니가 도구를 통해 작업 워크트리 밖의 파일을 변경하지 못하게 한다. 작업 워크트리와 main의 관계는 [쓰기 흐름](write-flow.md)에서 설명한다.

#### 쓰기 서브에이전트
지식 쓰기의 부모 도니는 같은 작업 워크트리에서 독립적인 지식 단위를 서브에이전트에 병렬로 맡길 수 있다. `SubagentPool`은 쓰기 작업마다 생성하며 `agent.runAgent`, 공통 `instructions`, 기존 워크트리 `tools`, 원문 읽기 권한·존재 검사 콜백 `validateSource`, 상태 변경 콜백 `onChange`를 받는다. `tools()`는 아래의 관리 도구를, `parentTools()`는 파일 소유권과 커밋 경계를 검사하는 부모용 워크트리 도구를 제공한다. 충돌 해결과 꿈꾸기에는 이 풀을 제공하지 않는다.

| 도구 | 계약 |
| --- | --- |
| `spawn_subagent` | 이름·담당 작업·쓰기 소유 범위 `files`와 선택적인 필수 읽기 경로 `sources`를 받아 백그라운드 실행을 시작하고 `{ id, name, status: "running" }`을 즉시 반환한다. |
| `subagent_status` | 모델 응답을 기다리지 않고 현재 상태 스냅샷을 반환한다. |
| `wait_subagents` | `ids`로 대상을 지정하고 `mode: "any"` 또는 `"all"`(기본값)로 하나 또는 전부의 종료를 기다린다. `ids`를 생략하면 전체가 대상이다. `timeoutSeconds`는 0~600의 정수이며 기본값은 300초다. 타임아웃은 대기만 끝내며 서브에이전트를 취소하지 않는다. |
| `message_subagent` | 실행 중인 서브에이전트에 후속 지시를 큐로 전달한다. 현재 모델 호출을 끼어들어 바꾸지 않고 다음 모델 턴의 사용자 메시지로 전달한다. |
| `cancel_subagent` | 대상 실행의 취소 신호를 보내고 종료를 기다린다. 이미 수행한 파일 변경을 되돌리지는 않는다. |

파일 소유 범위는 정규화된 저장소 상대 경로의 정확한 파일명 또는 `/`로 끝나는 디렉터리 접두사다. 예를 들어 `wiki/engineering/topic.md`는 그 파일만, `wiki/engineering/topic/`는 그 디렉터리 아래만 소유한다. 실행 중인 서브에이전트들의 소유 범위는 서로 겹칠 수 없으며, 종료하면 그 범위를 해제한다. 저장소 루트의 `index.md`, `MEMORY.md`, `AGENTS.md`와 `raw/`, 도메인 schema인 `wiki/<domain>/AGENTS.md`는 서브에이전트에 맡길 수 없다. schema 파일이 아직 없어도 보호하며, 이를 포함할 수 있는 `wiki/`·`wiki/<domain>/` 같은 넓은 소유 범위도 거부한다. 부모는 개별 도메인 노트나 schema와 겹치지 않는 하위 폴더로 범위를 나누어 맡긴다. 절대 경로·상위 디렉터리 탈출 등은 기존 워크트리 경계에서도 거부한다. 파일 소유권을 내부 별칭으로 우회하지 못하도록 이 작업의 부모·자식 편집은 심볼릭 링크를 경유하지 않는다.
잘못된 UTF-16(짝이 없는 surrogate)이 포함된 경로는 소유권 선언과 실제 워크트리 접근 모두에서 거부한다. 소유권 비교는 Unicode NFC로 통일하므로 한글의 NFC·NFD 이름도 같은 범위로 취급하지만, 파일 접근에는 원래 경로를 유지하여 기존 NFD 파일을 다른 이름으로 바꾸지 않는다.

`files`는 수정 권한을 나누는 소유권 선언이고 `sources`는 읽을 자료를 정확히 전달하는 목록이다. Notion 가져오기에서 부모가 “CRM 파일 19개를 담당한다”는 작업 설명만 보냈으나 자식에게 실제 원문 경로 목록이 전달되지 않아 파일을 읽지 않은 사례가 있었다. 부모 입력은 자동으로 자식에게 상속되지 않으므로 위임할 원문 경로를 `sources`에 명시한다. 예를 들어 `files: ["wiki/crm.md"]`, `sources: ["raw/<sha>/extracted/notion/files/CRM.md"]`로 원문 읽기와 위키 출력의 역할을 분리한다.

`sources`는 최대 200개 저장소 상대 파일 경로를 받으며 `read_file`과 같은 워크트리 경계로 `.`·중복 `/`를 정규화하고 중복 경로를 제거한다. 파일 접근에 필요한 원래 Unicode 형태는 유지한다. 생성 전에 요청자의 읽기 ACL과 파일 존재·워크트리 경계를 검사하며 잘못된 경로, 읽을 수 없는 경로, 없는 파일은 도구 오류로 거절한다. `raw/`와 부모 전용 노트도 읽기 경로로 전달할 수 있으며, 다른 자식과 같은 원문을 읽어도 소유권 충돌로 보지 않는다. 이 목록 자체는 실제 원문 접근 이력이 아니다.

서브에이전트는 기존 읽기·검색 도구를 사용하되 `write_file`·`delete_file`은 자신의 소유 범위에만 실행할 수 있고 `move_file`은 출발지와 목적지가 모두 자신의 범위 안에 있어야 한다. 요청자의 ACL은 그대로 적용한다. 서브에이전트는 커밋하거나 다른 서브에이전트를 만들 수 없으므로 위임 깊이는 1이다. 부모도 실행 중인 서브에이전트가 소유한 경로를 쓰기·삭제·이동할 수 없고, 하나라도 실행 중이면 커밋할 수 없다. 부모는 상태와 결과를 확인하고 종료 후 변경을 검토하며 공용 색인·메모리 갱신과 최종 커밋을 담당한다.

한 풀에서 동시에 실행할 수 있는 서브에이전트는 최대 2개, 작업 전체에서 생성할 수 있는 수는 최대 4개다. 위임마다 공통 문맥을 별도 모델 실행에 보내므로 비용과 동시 요청 규모를 제한하기 위한 상한이다. 각 서브에이전트의 모델 호출 상한은 32턴이고 부모 쓰기 실행은 최대 96턴이다. 실패한 서브에이전트는 실패 상태와 오류를 보고할 뿐 부모 쓰기 작업을 자동으로 실패시키지 않는다. 부모가 남은 변경을 검토해 수정·재위임·중단 여부를 결정한다. 부모 실행 종료와 자식 수명의 경계는 [쓰기 흐름](write-flow.md#도니-비동기-쓰기)에 기록한다.

상용 실행에서 자식이 `Dony exceeded maxTurns (32)`로 종료되어 최종 결과를 남기지 못한 사례가 있었다. 자식의 고정 지침은 32턴 예산과 한도 전에 소유 파일 작성·결과 응답을 마쳐야 한다는 조건을 명시한다. `beforeTurn`은 자식 실행마다 완료한 모델 턴을 0부터 세고, 현재 요청을 포함해 6턴이 남은 27번째 요청 직전에 사용자 경고를 한 번만 추가한다. 경고는 새 자료 읽기와 탐색을 중단하고 이미 읽은 자료로 소유 파일을 작성·확장한 뒤 실제 통합한 내용·경로와 남은 사항을 응답하도록 요구한다. 대기 중인 부모 메시지는 기존 순서대로 먼저 전달하고 그 뒤에 경고를 붙인다. 부모의 예산 안내는 [실행 체크포인트](#실행-체크포인트)에 기록한다.

자식 취소 신호는 검색의 질의 확장·임베딩·재정렬 HTTP 호출에도 전달하므로 응답하지 않는 검색 서버나 SDK 재시도 대기가 부모 종료를 막지 않는다. 이미 시작한 파일 변경은 취소하지 않고 끝날 때까지 소유권을 유지한다. 상태 이벤트 저장 콜백이 실패하면 오류를 로그와 조회 가능한 자식의 failed/cancelled 스냅샷에 남기며, 백그라운드 Promise 거절로 엔진을 종료시키지 않는다.

상태 스냅샷은 `id`, `name`, `status`, `files`, `sources`, `toolCalls`, `startedAt`과 종료 시의 `finishedAt`, 선택적인 `result` 또는 `error`를 담는다. 상태는 `running`, `completed`, `failed`, `cancelled`다. `runAgent()`의 `beforeTurn` 훅으로 메시지 큐를 비우고 `onToolCall` 훅으로 누적 도구 호출 수를 갱신한다. 모델 응답 뒤와 도구 실행 전후에 취소 신호를 다시 검사하므로 취소된 실행이 응답 처리나 후속 도구 호출을 계속하지 않는다. 풀의 상태 변경은 `editing` 단계의 `detail.subagent`에 이름·상태·소유 경로·읽기 담당 경로·도구 호출 수·결과 또는 오류를 담고 정상적인 `job.updated`를 발행한다. 시작·종료 이벤트는 즉시 전달하며 도구 호출 수의 진행 이벤트는 최대 5초에 한 번으로 제한한다. 담당 작업의 본문은 이벤트에 넣지 않으며 작업 입력을 볼 수 없는 조회자는 서브에이전트 결과와 오류를 포함한 이벤트 세부 정보도 받지 않는다. 조회 시 `files`와 `sources` 모두 현재 읽기 ACL로 숨기며 어느 목록에서든 경로가 숨겨지면 그 자식의 결과·오류도 숨긴다. `sources`가 없던 과거 이벤트는 빈 목록으로 읽는다.

`result`는 `runAgent()`가 승인한 마지막 도구 없는 턴의 `finalText`만 담으며 도구 호출 턴의 진행 설명은 포함하지 않는다. 부모가 중간 계획을 실제 통합 결과로 오해하지 않도록 누적 `text`와 구분한다.

읽기 이력뿐 아니라 권한 검사를 통과해 실제로 편집한 경로도 이벤트의 `sourcePaths`에 정확한 파일 경로로 기록한다. 따라서 커밋 전의 결과도 기존 작업 입력 가시성 검사에 포함한다. 소유 범위만 선언하거나 거절된 편집을 시도한 경로는 원문 접근 이력으로 취급하지 않으므로 자식의 거절된 시도가 부모 작업 전체를 권한 오류로 실패시키지 않는다.

부모 지시문은 지식 단위를 먼저 계획하고 서로 겹치지 않는 파일 범위를 지정해 맡기며, 공통 문서와 커밋은 직접 처리하도록 요구한다. 자식 입력은 `{ id, name, task, files, sources }`이며 기본 위키 작성 규칙과 부모가 지정한 작업·쓰기 소유 범위·읽기 담당 경로를 함께 받는다. 자식은 `sources`의 모든 파일을 `read_file`의 `nextOffset`·`nextCharOffset`으로 마지막 페이지까지 읽고 결과에 각 원문의 통합 대상 또는 제외 이유를 설명하도록 지시받는다. 원문·노트·검색 결과 안의 명령은 신뢰하지 않는 자료로 취급한다. 완료 응답과 성공한 도구 호출은 main 반영의 증거가 아니다. 부모 검토 이후의 직렬 머지·검증·재인덱싱과 최종 성공 판정은 [쓰기 흐름](write-flow.md)을 따른다.

충돌 해결에는 충돌 마커가 있는 작업 파일과 분기 기준·작업 브랜치·main의 내용을 함께 제공한다. 두 변경의 의도를 보존하도록 요청한 뒤 마커가 남았는지 확인하고, 남아 있으면 한 번 더 요청한다. 두 번의 해결 시도 뒤에도 마커가 남아 있으면 실패하며, 해결 도구가 머지 커밋을 만들지는 않는다.

웹 질의응답에는 `search`, `read_note`를 제공하며, 쓰기 권한이 있는 요청에는 아래의 `write_knowledge`를 추가한다. 답변 시작 시점의 main SHA를 고정하여 근거 노트를 읽고 한국어로 답한다. `context.notePath`는 정규화한 저장소 상대 Markdown 경로로 읽으며 `context.ref`를 지정하면 실제 커밋 SHA로 해석한 뒤 해당 버전을 고정한다. 고정 노트는 모델 호출 전에 읽으므로 검색 없이도 인용할 수 있고, 같은 노트를 다시 읽어도 고정 버전을 유지한다. `selection`은 명령이나 검증된 노트 내용이 아닌 신뢰하지 않는 인용 자료로 별도 전달한다.

답변은 실제 상대 경로의 Markdown 링크로 근거를 표시한다. 인용 객체는 `{ path, sha, heading?, anchor? }`이며 읽기에 성공한 노트만 포함한다. Markdown AST의 일반 링크와 참조 링크를 검사하고 코드 블록·인라인 코드·원시 HTML은 제외한다. `#fragment`는 해당 노트 본문의 제목을 GitHub Slugger로 만든 실제 앵커와 일치할 때만 인정하며, 중복 제목의 `-1` 접미사와 코드·강조·위키링크 별칭을 포함한 제목도 렌더러와 맞춘다. 검색 결과만 본 노트, 존재하지 않는 제목, 읽었지만 실제 답변에서 인용하지 않은 노트는 목록에 넣지 않는다.

#### 대화 답변과 문서의 문체
`answer()`의 사용자 대상 답변은 항상 친절하고 부드러운 존댓말로 작성한다. 기본은 해요체이며 필요하면 합니다체를 쓰지만 반말·딱딱한 명령조·훈계조는 사용하지 않는다. 권한 때문에 기록을 요청할 수 없을 때도 이유와 사용자가 다음에 할 수 있는 일을 정중하게 설명한다. 이 답변 지침은 기본 문맥의 위키 문체 규칙보다 우선한다.

대화 말투를 지식 문서에 옮기지는 않는다. 위키 노트·일기와 `proposal()`의 Markdown 초안은 기존 [평서형 작성 규칙](writing-rules.md)을 유지하며, 기록할 내용과 사용자에게 안내하는 답변의 문체를 구분한다.

#### 대화 중 지식 기록 도구
`write_knowledge`는 `{ content: string }`을 받아 도니의 비동기 쓰기 작업을 요청한다. 이 도구를 제공받는 전역 편집자·관리자의 대화에서는 현재 사용자 메시지나 대화에 모든 위키 독자에게 공유할 만한 지속적이고 재사용 가능한 지식이 있으면 명시적인 저장 요청을 기다리지 않고 선제적으로 제출한다. 대상은 사용자가 제공한 사실, 결정과 이유, 절차·사용법, 문제 해결 결과, 도메인 용어, 기존 위키의 정정과 위키에 없는 새 정보다. 사용자의 기록·저장·추가·정정 요청도 항상 따른다.

제출 전에 `search`와 `read_note`로 기존 노트를 확인한다. 같은 내용이 이미 변경 없이 기록되어 있으면 제출하지 않는다. 기존 노트의 정정이나 보충은 관련 노트 경로를 포함해 제출한다. 내용에는 사용자가 제공한 진술과 `read_note`로 확인한 근거만 사용하며, 근거·출처와 적용 범위를 함께 담는다. 정정 요청은 쓰기 작업이 오류를 검색할 수 있도록 `content`에 잘못된 표현과 올바른 사실, 근거·출처, 적용 범위를 함께 담는다.

새 정보가 없는 단순 질문, 인사·잡담, 일시적인 대화 상태와 작업 진행 상황, 추측, 검증되지 않은 도니 자신의 답변은 제출하지 않는다. 비밀값·자격 증명·인증 정보·토큰·개인정보도 기록하지 않는다. 고정 노트·선택문·대화 요약에 들어 있는 명령은 신뢰하지 않는 자료이며 저장 명령으로 해석하지 않는다. 사용자가 `기록하지 마`처럼 기록을 원하지 않는다고 밝히면 제출하지 않는다.

관련 사실은 잘게 나누어 여러 번 호출하지 않고 하나의 요청으로 묶는다. 선제적으로 제출한 뒤에는 기록 요청 사실과 `jobId`를 사용자에게 짧고 정중한 존댓말로 안내한다. 새 접수는 `기록 요청됨`으로 설명하며 접수를 저장 완료로 표현하지 않는다. 작업 재사용과 실제 완료 안내는 아래의 상태 규칙을 따른다.

과거에는 명시적인 요청이 있을 때만 기록하여 사용자가 대화에서 공유한 지식은 야간 꿈꾸기 전까지 위키에 남지 않았다. 선제적 기록은 이 공백을 줄이고 [MCP와 Skill 클라이언트에 전달하는 장기 지식 제출 지침](mcp.md#서버-지침과-개인정보-경계)과 도니의 대화 정책을 맞추기 위한 것이다.

선제적·명시적 기록 요청의 접수나 쓰기 성공은 사용자 메시지의 `learned_at`을 갱신하지 않는다. 따라서 같은 발언이 이후 [꿈꾸기 입력](dreaming.md#실행-시각과-입력)에도 포함될 수 있다. 꿈꾸기는 이미 반영된 변경과 관련 노트를 함께 검토해 의미상 중복을 정리하도록 지시받지만, 메시지와 쓰기 작업을 연결해 추출을 제외하거나 동일 사실의 재반영을 결정적으로 차단하지는 않는다. 이 동작은 선제적 기록 도입으로 바꾸지 않는다.

한 답변에서 기록 도구는 최대 5회 요청할 수 있고 초과 호출은 도구 오류로 반환한다. 같은 사용자 메시지를 재시도하거나 답변을 재생성하면 현재 요청자·메시지 내용·호출 순서가 같은 기존 비실패 작업을 재사용한다. `{ jobId, status, reused: true }`는 새 기록 접수가 아니라 이미 요청된 작업과 현재 상태를 뜻하므로 도니는 `이미 기록 요청됨`으로 안내한다. 메시지를 편집해 내용이 바뀌거나 다른 구성원이 요청하면 별도 작업이며, 한 답변 안의 여러 호출도 서로 다른 작업이다.

같은 기록 권한으로 `get_write_status({ jobId })`와 `wait_write({ jobId, timeoutSeconds? })`도 제공한다. 두 도구는 대화 서비스가 현재 요청자와 대화에 묶은 콜백으로 실행하며, 사용 전과 비동기 조회·대기 후에 대화 편집 권한·현재 사용자 역할·ACL 정책을 재검사한다. 작업 요청자가 현재 사용자와 다르면 관리자라도 `not found` 오류를 반환한다.

상태 결과는 작업 ID·상태·최신 단계·요약·오류·머지 SHA·커밋 목록을 담는다. 서브에이전트 이벤트가 있으면 ID별 최신 상태·담당 파일·도구 호출 수·결과를 함께 반환하며 작업 지시문은 반환하지 않는다. 입력이 제한된 작업의 요약과 서브에이전트 결과·오류는 숨기고, 읽을 수 없는 담당 파일도 제외한다. 작업의 실제 원문 접근·편집 경로와 커밋 변경 경로를 대화 생성의 근거 경로로 추적하므로 결과를 설명한 답변에도 기존 공유 대화의 접근 제한을 적용한다. 담당 파일 선언만으로 접근 이력을 만들지는 않는다. 커밋 경로는 패치를 생성하지 않고 모든 부모 기준의 변경 이름만 조회하며 가시성 검사에서 수집한 경로를 그대로 재사용한다. 커밋 경로를 확인하지 못하면 상세 결과를 제한한다.

`get_write_status`는 즉시 스냅샷을 반환한다. `wait_write`의 대기 시간은 기본 60초, 최대 120초이며 성공·실패 상태가 되거나 제한 시간이 지나면 같은 상태 결과와 `timedOut`을 반환한다. 대기는 1초 이하 간격으로 저장된 작업 상태를 조회하고 답변의 취소 신호에 반응한다. 제한 시간이나 답변 취소는 쓰기 작업을 취소하지 않는다. 두 도구의 시작·종료 진행 이벤트는 작업 ID를 `summary`와 `jobId`에 담으며 작업 본문이나 결과를 요약에 넣지 않는다.

도니는 기록 접수 뒤 잠시 기다리거나 상태를 확인하여 실제 결과를 안내할 수 있다. `succeeded`를 확인한 경우에만 저장·반영 완료를 말하고, 아직 대기·실행·병합 중이면 진행 중이며 작업 단계에 링크가 있다고 안내한다.

도구 노출과 실행의 권한 경계는 [폴더별 접근 제어](access-control.md#읽기와-쓰기-범위)를 따른다. 답변 도구는 파일을 직접 편집하거나 커밋하지 않는다. 제출 결과와 실제 반영 사이의 경계는 [대화에서 제출하는 쓰기](write-flow.md#대화에서-제출하는-쓰기)에, 진행 단계와 작업 링크는 [웹 대화 작업 공간](web.md#도니-대화-작업-공간)에 기록한다.

#### 대화 요약과 노트 제안

`summarize()`는 오래된 텍스트 대화에서 목표·근거·결정·미해결 질문을 보존하는 요약을 만들며 도구를 제공하지 않는다. 대화 서비스는 답변을 요청한 사용자가 현재 읽을 수 있는 사용자 메시지와 완료된 답변만 이력에 포함한다. 이 이력이 16개를 넘거나 본문 합계가 48,000자를 넘으면 요청 시점에 오래된 앞부분을 요약한다. 최근 메시지는 최대 12개·32,000자 안에서 유지하되 마지막 사용자 메시지는 크기가 커도 원문을 보존한다. 요약을 대화별로 저장하거나 다른 구성원·다음 요청에 재사용하지 않는다. 공유 요약에는 다른 구성원의 제한된 근거가 섞일 수 있으므로 요청자의 현재 읽기 권한으로 매번 다시 계산한다. 요약 중 권한 정책이 바뀌면 이후 답변 호출을 중단한다. 첨부의 재생 범위와 예산은 [첨부 파일과 가져오기 업로드](#첨부-파일과-가져오기-업로드)를 따른다. 답변에 전달하는 요약은 신뢰하지 않는 참고 자료로 구분한다.

`proposal(answer, mode, path?)`는 읽기 전용 검색·노트 도구로 근거를 확인하고 완성된 Markdown 파일의 `{ path, baseSha, original, proposed }`를 반환한다. `edit`는 기존 경로가 필요하며 원문과 frontmatter를 보존하도록 지시한다. 기존 `wiki/` 직하 노트도 편집할 수 있지만, `new`는 [노트 배치 기준](knowledge-domains.md#노트-배치와-탐색)에 맞는 경로를 사용하고 기존 파일을 덮지 않는다. 새 도메인 노트에는 읽을 수 있는 기존 `wiki/<domain>/index.md` 허브가 필요하며, 경로는 해당 도메인의 적합한 주제 폴더 안에서 고른다.

새 경로를 생략하면 답변의 첫 제목 또는 첫 문장에서 파일명 slug를 만들고, 읽기 전용 모델 단계가 요청자가 쓸 수 있는 도메인·주제 후보나 `wiki/concepts/`·`wiki/entities/` 공유 정본 경로를 고른다. 도메인은 허브가 있는 기존 영역에서 고르며, 적합한 기존 주제 폴더를 우선하고 필요한 경우 안정적인 새 주제를 정한다. 적합한 도메인이 없고 공유 정본에도 해당하지 않으면 도메인 허브를 먼저 만들도록 오류를 반환하며, 공유 폴더를 미분류 지식의 기본 저장 위치로 사용하지 않는다.

자동으로 고른 경로와 명시한 새 경로 모두 `src/knowledge/domains.ts`의 공통 helpers로 얕은 도메인 배치·깊이 초과·잘못된 폴더 이름을 검사하고, 도메인 허브와 요청자의 쓰기 권한, 기존 파일 유무를 확인한다. 해당 도메인 schema가 있으면 그 파일의 읽기 권한을 먼저 검사하고 고정한 `baseSha`에서 읽어 초안 문맥에 넣는다. schema는 [엔진 구조 규칙의 우선순위](knowledge-domains.md#도메인-schema)를 바꾸지 않는다. 제안은 파일·워크트리·커밋을 만들지 않으며 실제 저장은 사용자가 미리보기를 확인한 뒤 일반 노트 쓰기 API로 수행한다.

### 임베딩 모델을 분리하는 이유
기본 응답 모델인 `gpt-6-luna`는 OpenAI Embeddings 엔드포인트를 지원하지 않는다. 따라서 문서와 질의의 임베딩에는 응답 모델과 별도의 모델을 사용한다. 임베딩 모델의 선택과 인덱싱 방식은 [RAG](rag.md)에서 설명한다.

### 첨부 파일과 가져오기 업로드
`UploadsModule`은 `JobsModule`을 가져오고 `UploadsService`를 내보낸다. `POST /api/uploads`는 인증된 사용자의 multipart `file` 필드와 선택적 `purpose` 필드를 받는다. 기본 `purpose=chat`은 최대 20 MiB의 PNG·JPEG·WebP·GIF·PDF·UTF-8 텍스트 및 마크다운을 받는다. 확장자나 브라우저의 Content-Type을 신뢰하지 않고 파일 시그니처와 엄격한 UTF-8 디코딩으로 종류를 판별한다. 제어 문자가 들어간 바이너리를 텍스트로 위장해 올릴 수 없다. `purpose=import`는 editor 이상만 사용할 수 있으며, 같은 파일 종류 외에 시그니처로 확인한 ZIP을 받고 최대 크기는 100 MiB다. 가져오기 업로드는 채팅 첨부로 사용할 수 없다.

응답은 `{ id, userId, name, mediaType, size, createdAt, purpose }`다. 원본 바이트는 `DATA_DIR/uploads/<id>`에 저장하고 저장 후 변경하지 않는다. `GET /api/uploads/:id`는 업로드 소유자에게만 제공하며 관리자도 다른 소유자의 파일을 직접 받을 수 없다. 다운로드 이름에서 경로·제어 문자를 제거하고 Content-Disposition의 ASCII 이름과 UTF-8 이름을 각각 안전하게 인코딩한다. 응답은 attachment, nosniff, sandbox CSP, private/no-store를 사용한다.

editor 이상의 `POST /api/uploads/:id/save { path, baseSha }`는 소유자의 파일을 `assets/` 아래 경로에 저장하거나 기존 자산을 교체한다. 절대 경로, 역슬래시, 빈 경로 조각, `.`·`..` 이동을 거절한다. `NoteWriterService.apply`에 `contentBase64`를 전달하며 클라이언트가 읽은 `baseSha` 뒤에 해당 경로가 변경되었다면 `stale_note`로 거절한다. 저장의 이력·동시 변경 검사는 [쓰기 흐름](write-flow.md)의 직접 쓰기와 같고 응답은 `{ jobId, mergeSha }`다. 지식 저장소 저장에 성공한 뒤에만 업로드를 보존 대상으로 표시한다.

채팅 이력의 `parts(userId, ids, budget?, options?)`는 이미지를 data URL의 `input_image`, PDF를 파일명과 base64 data URL을 가진 `input_file`, 텍스트를 파일명과 내용의 `input_text`로 변환하고 `{ parts, bytes }`를 반환한다. 텍스트 파일은 앞의 32 KiB까지만 읽고 잘린 UTF-8 문자는 제외하며, 비용은 실제 포함한 본문의 UTF-8 바이트 수다. 이미지·PDF의 비용은 base64로 확장한 데이터와 data URL 접두사를 합한 바이트 수다. 전체 답변 이력은 8 MiB 예산 하나를 공유하며 최근 메시지부터 첨부를 포함한다. 이미지·PDF 원본은 가장 최근 사용자 턴과 바로 전 사용자 턴에서만 재생하고, 더 오래된 바이너리에는 파일명과 필요시 재첨부하라는 짧은 텍스트 안내를 남긴다. 예산을 넘은 첨부도 같은 방식으로 사유를 안내하되 이후의 작은 첨부는 포함할 수 있다. 생략 안내는 바이너리 재생이나 예산 소비로 계산하지 않는다. 이미지의 `detail`은 마지막 사용자 턴에 첨부가 정확히 하나일 때만 `auto`이며, 같은 턴의 여러 첨부와 이전 턴의 이미지는 모두 `low`다. 생략할 첨부를 포함한 모든 ID의 존재·소유권·채팅 용도를 먼저 검사하므로 예산이 0이거나 오래된 첨부여도 잘못된 첨부를 숨길 수 없다.

시작할 때와 매시간 보존 기간이 지난 미사용 업로드를 정리한다. `UPLOAD_RETENTION_DAYS`는 양수인 일 수이고 기본값은 7이다. `messages.attachments` JSON에 참조된 업로드와 자산 저장을 성공한 업로드는 보존하며, 자산 저장 중인 파일도 정리하지 않는다. 파일 생성과 DB 기록 사이의 비정상 종료로 생긴 파일만 있는 오래된 고아도 정리한다. 실패한 저장은 보존으로 간주하지 않는다.
