# 꿈꾸기

꿈꾸기는 매일 변경된 지식과 저장소의 구조를 검토하고, 입력과 구조 신호에 맞는 정리 범위를 골라 일기를 남기는 배치 작업이다.

## 배경

개별 쓰기 요청을 반영하는 것만으로는 기존 지식과의 충돌이나 중복, 쌓여 가는 구조 문제를 함께 정리하기 어렵다. 꿈꾸기는 변경된 노트와 관련된 기존 노트를 함께 검토하고, 변경이 없는 날에도 위키 폴더를 순환 점검해 누적된 지식을 정돈한다. 예를 들어 새 노트가 기존 노트와 같은 내용을 다루면 중복을 정리하고, 한 폴더에 노트가 몰리면 주제별 분리와 색인 보완을 검토한다.

지식 저장소의 파일 배치, 일기의 경로, 메모리 파일의 역할과 GitHub 백업 정책은 [지식 저장소](knowledge-repository.md)에 설명한다.

## 내용

### Nest 모듈과 실행 수명

`DreamingModule`은 `KnowledgeModule`, `AgentModule`, `RagModule`을 가져오고 `DreamRunsRepository`와 `DreamingService`를 제공·내보낸다. 서비스는 지식 저장소, 도니, 인덱서, 검색·catalog·비교 서비스, ACL·감사 서비스와 `CONFIG`, `LOGGER` 토큰, 실행 기록 저장소, 전역 `EventsService`를 생성자 DI로 받는다.

`DreamRunsRepository`는 실행 기록 SQL, 중단된 실행의 실패 처리, 성공 체크포인트 조회, 미학습 사용자 메시지 조회와 학습 완료 표시를 담당한다. `DreamRun`과 대화 입력 형식은 `dream-run.types.ts`에 두며, 서비스는 배치·머지·백업 흐름을 담당한다.

HTTP 진입점인 `main.ts`는 `app.init()` 직후 `recoverInterrupted()`로 중단 기록을 동기적으로 정리하고 스케줄러를 명시적으로 시작한다. `JOBS_AUTOSTART=false`여도 HTTP 시작 시 기록 정리는 수행하지만 `start()`는 예약 실행을 만들지 않으며 수동 실행은 유지한다. 설정의 운영 경계는 [자동 실행 중지](operations.md#자동-실행-중지)를 따른다. `dreaming.commands.ts`의 `registerDreamCommands`는 Nest 애플리케이션 컨텍스트에서 서비스를 조회하지만 CLI 컨텍스트 생성은 스케줄러를 시작하거나 중단 기록을 정리하지 않으므로, 같은 DB를 사용하는 별도 HTTP 프로세스의 실행 중 기록을 바꾸지 않는다. 종료 훅은 스케줄러를 중단하고 진행 중인 배치가 끝날 때까지 기다린 뒤 반환하므로 DB 종료 전에 학습 완료 표시와 실행 기록 저장을 마친다.


### 실행 시각과 입력

기본 실행 시각은 매일 03:00 `Asia/Seoul`이다. Croner가 `DREAM_CRON`과 `TZ_DREAM` 설정을 사용한다. `pnpm cli dream run` 또는 설치된 `llmwiki dream run`으로 즉시 실행할 수도 있다. 같은 프로세스에서 같은 지식 저장소를 대상으로 실행 중인 배치가 있으면 새 배치를 만들지 않고 기존 실행의 결과를 기다린다.

운영 HTTP 진입점은 `runManual()`을 사용한다. 같은 저장소에서 실행 중인 배치가 있으면 기존 결과를 기다리지 않고 HTTP 409, 코드 `dream_running`으로 거절하며 새 실행 기록을 만들지 않는다. CLI와 스케줄러의 `runOnce()`는 기존처럼 실행을 합친다. 서비스 인스턴스가 달라도 같은 `KnowledgeRepo` 객체를 사용하면 이 규칙을 공유한다.

입력 범위는 직전 성공한 `dream_runs.to_sha`를 제외한 이후 커밋부터 실행 시작에 읽은 main HEAD까지다. 첫 실행의 기준점은 저장소의 첫 커밋이다. 도니가 작업하는 동안 main에 추가된 커밋은 이번 학습 체크포인트를 앞당기지 않으며 다음 실행에서 검토한다.

수집 과정에서 생긴 잔여물을 위한 노트 후보도 입력에 포함한다. `local`·`structural`에서만 위 입력 커밋 구간의 `Wiki-Source: import` 커밋에 변경으로 나타난 `wiki/` 아래 Markdown 노트를 모은다. 또한 `run.fromSha`와 `run.toSha` 사이의 순변경에 남은 노트만 후보로 삼으므로, 실행 중 수정됐더라도 내용과 경로가 시작 시점과 같게 복원된 노트는 제외한다. `wiki/<domain>/AGENTS.md`는 기존 도메인 schema 경로 판별 규칙에 따라 제외한다. 후보 경로는 `run.toSha` 시점의 현재 경로로 해석해 이름 변경은 현재 이름으로 반영하고 삭제된 노트는 버린다. 현재 경로 기준으로 중복을 제거하고 사전순으로 정렬한 뒤 `importedNotes`에는 최대 20개를 넣고, `importedNotesCount`에는 제한 전 전체 후보 수를 넣는다. `sweep`에는 별도 후보를 전달하지 않아 `importedNotes`는 빈 배열, `importedNotesCount`는 0이며, 대신 선택한 `focus`에 직접 들어 있는 노트를 살펴 같은 잔여물을 정리한다.

대화 입력은 [웹 대화 기록의 하루치 학습 배치](web.md#대화-기록과-학습)를 따른다. 배치 시작 시점까지 생성된 `role='user'`, `learned_at IS NULL` 메시지만 가져온다. 실패한 날짜의 미학습 메시지도 함께 가져오므로 날짜 경계 때문에 누락되지 않는다. assistant 메시지는 입력에 넣지 않는다.

실행 시작의 저장소와 검색 catalog에서 구조 신호를 모은 뒤 아래 모드를 선택한다. 커밋 변경과 미학습 메시지가 없는 날도 점검할 위키 폴더가 있거나 기존 `MEMORY.md`의 형식·예산 위반이 있으면 도니를 실행하고 일기를 쓰므로 LLM 비용이 발생한다. 입력도 구조 신호도 없고 `sweep` 대상으로 고를 폴더도 없으면 도니를 호출하거나 일기를 쓰지 않고 백업 push만 시도하며 LLM 비용은 0이다. 유효한 메모리의 존재만으로 추가 실행을 만들지는 않는다.

### 모드와 구조 신호

모드는 구조 문제가 있는 `structural`, 새 입력이 있는 `local`, 순환 점검인 `sweep` 순서로 선택한다.

| 모드 | 선택 조건과 범위 |
| --- | --- |
| `structural` | 아래 구조 임계값 중 하나라도 충족하면 선택한다. 구조 신호가 지목한 영역에서 중복·링크·배치·허브 문제를 정리하고 새 커밋과 대화 입력도 함께 검토한다. |
| `local` | 구조 임계값을 충족하지 않지만 새 커밋이나 미학습 사용자 메시지가 있으면 선택한다. 변경 노트와 관련 노트 중심으로 정리하며 다른 영역의 구조는 바꾸지 않도록 지시한다. |
| `sweep` | 구조 임계값과 새 입력이 없으면 마크다운 노트가 직접 들어 있는 위키 디렉터리 하나를 점검한다. 하위 디렉터리의 노트까지 한꺼번에 점검하지 않는다. 대상 디렉터리도 없으면 모드를 선택하지 않는다. |

일반 구조 후보는 `wiki/` 아래에 추적된 마크다운 노트로 한정하며 `.MD`처럼 확장자의 대소문자가 다른 노트도 포함한다. 도메인 schema는 노트 후보에서 제외하고, 도메인 허브는 일반 고아 후보에서 제외하여 아래의 루트 연결 신호로만 점검한다. `raw/`, `journal/`과 저장소 루트의 파일도 후보에서 제외한다. 다만 링크 해석용 경로 목록은 첨부를 포함한 실행 시작 저장소의 전체 파일로 구성하며 첨부의 바이너리 본문은 읽지 않는다. 대상 유형에 따른 해석은 [정리 경계의 링크 검증](#코드로-강제하는-정리-경계)과 같은 기준을 적용한다. 고아·도메인 허브·배치 신호는 같은 커밋 스냅샷의 공통 탐색 검사(`navigationIssues`)를 사용하며 catalog의 유무나 신선도에 의존하지 않는다. 기존 `wiki/index.md` 같은 미분류 노트도 후보에 포함한다. 관련 검색과 링크 해석의 원리는 [RAG](rag.md)를 따른다.

| 신호 | `structural` 선택 임계값 |
| --- | --- |
| 중복 후보 | 정확한 중복이나 의미 중복 후보가 하나라도 있다. |
| 고아 노트 | 루트 `index.md`나 다른 위키 노트에서 들어오는 해석 가능한 위키링크가 없는 일반 노트가 5개 이상이다. 자기 링크와 도메인 schema·raw·journal에서 들어오는 링크는 세지 않는다. 나가는 링크만 있어도 고아 후보가 되지만, 루트에서 도달하지 못하는 노트라도 다른 위키 노트의 링크가 있으면 고아가 아니다. |
| 과밀 폴더 | 마크다운 노트가 직접 15개를 초과하는 폴더가 있다. 하위 폴더의 노트는 이 수에 합산하지 않는다. |
| 모호한 위키링크 | 해석 가능한 대상 경로가 둘 이상인 링크가 하나라도 있다. |
| 미해결 위키링크 | 대상 경로를 찾을 수 없는 링크 후보가 5개 이상이다. 같은 원본 노트의 동일한 정규화 대상은 한 번만 세며, 다른 원본 노트에서 같은 대상을 참조하면 별도로 센다. |
| 태그 허브 부재 | 같은 태그를 가진 서로 다른 노트가 5개 이상인데, 그중 절반 이상으로 링크하는 위키 허브가 없다. 홀수 개이면 절반을 올림한다. |
| 도메인 허브 부재 (`missingDomainHubs`) | 노트나 schema가 있는 도메인에서 `wiki/<domain>/index.md`가 하나라도 없다. |
| 전체 허브 연결 누락 (`unlinkedDomainHubs`) | 존재하는 도메인 허브 중 루트 `index.md`의 위키링크로 해석되는 대상에 포함되지 않은 허브가 하나라도 있다. |
| 미분류 노트 (`unclassifiedNotes`) | `wiki/` 바로 아래의 마크다운 노트가 하나라도 있다. `.gitkeep`는 노트가 아니다. |
| 얕은 도메인 노트 (`shallowDomainNotes`) | 도메인 바로 아래의 일반 마크다운 노트가 하나라도 있다. 도메인 허브와 schema는 제외한다. |
| 깊이 초과 노트 (`tooDeepNotes`) | 도메인·주제·하위 주제보다 깊거나, 공유 영역·주제보다 깊은 마크다운 노트가 하나라도 있다. |
| 잘못된 폴더 이름 (`invalidFolderNames`) | `wiki/` 아래에 ASCII 소문자 kebab-case가 아닌 이름, 한 글자 이름, `batch`·`part`·`chunk` 뒤에 번호가 붙은 이름, `YYYY`·`YYYY-MM`·`YYYY-MM-DD` 형태의 이름이 하나라도 있다. |
| 노트 메타데이터 오류 (`invalidMetadata`) | 엔진 자동 속성을 제외한 필수 속성 누락·잘못된 형식·금지 속성 같은 문제가 있는 노트가 하나라도 있다. 필드 규칙은 [노트 메타데이터 표준](note-metadata.md)을 따른다. |
| 메모리 오류 (`memoryIssues`) | 실행 시작 커밋의 기존 `MEMORY.md`가 형식·예산 검사를 하나라도 위반한다. 새 커밋·대화·위키 폴더가 없어도 `structural`을 선택한다. 규칙은 [메모리 파일의 문맥 제공 규칙](knowledge-repository.md#메모리-파일의-문맥-제공-규칙)을 따른다. |

큰 노트와 작은 노트는 참고 신호다. 전체 마크다운이 20,000자를 초과하면 큰 노트이며, frontmatter를 제외한 본문의 앞뒤 공백을 제거한 길이가 200자 미만이면 작은 노트다. 이 두 신호만으로 `structural`을 선택하지 않는다. 도니에게 전달하는 각 후보 목록과 후보 안의 경로 목록은 최대 20개로 제한한다. `local`에서는 변경 경로와 해당 위키 폴더에 관련된 신호만, `sweep`에서는 선택한 폴더에 관련된 신호만 전달한다.

`memoryIssues`는 오류 설명 문자열 배열이며 catalog가 없어도 검사한다. 메모리 파일이 없으면 빈 배열이고, `local`·`sweep` 범위를 좁힐 때도 전역 신호로 그대로 남긴다.

도메인 신호는 기존 태그 허브 부재와 구분한다. 도메인과 공유 영역의 구분, 허브의 역할 및 정본 배치는 [지식 도메인 구조](knowledge-domains.md)를 따른다. 같은 구조 신호를 수정 없이 확인하는 명령은 [읽기 전용 lint](development.md#지식-구조-점검-cli)에 설명한다.
깊이 신호는 허용 경로를 벗어난 노트의 경로 배열이고, 폴더 이름 신호는 추적 파일에서 확인한 모든 상위 폴더의 `{ path, reason }` 배열이다. 폴더 경로는 `/`로 끝난다. 각 목록은 경로순 최대 20개다. `local`·`sweep`에서는 깊이 후보를 선택한 직접 노트 범위로 좁히고, 이름 후보는 그 노트나 선택 폴더의 조상 폴더만 남긴다. 선택 폴더의 하위 폴더나 다른 영역의 이름 문제는 함께 전달하지 않는다. 도구·출처·유형·상태·작성자처럼 이름만으로 확정할 수 없는 금지 분류 축은 자동 판정하지 않는다.


메타데이터 후보는 경로순으로 최대 20개의 `{ path, issues: [{ field, message }] }`를 전달한다. `invalidMetadataCount`는 후보 목록을 자르거나 `local`·`sweep` 범위로 좁히기 전의 전체 문제 노트 수다. `author`, `date created`, `date modified`는 엔진 자동 속성이므로 이 정리 신호에서 제외한다. 도니는 도메인 배치·허브와 깨지거나 모호한 링크를 우선하며, 메타데이터 backlog의 보완 원칙은 [기존 저장소의 메타데이터 정리](note-metadata.md#기존-저장소의-메타데이터-정리)를 따른다.

`sweep` 후보에는 `wiki/` 자체를 포함하여 노트가 직접 들어 있는 디렉터리만 들어간다. 해당 디렉터리를 대상으로 마지막으로 성공한 `sweep` 실행이 오래된 순서로 고르며, 아직 성공한 점검이 없는 디렉터리를 먼저 고른다. 성공 이력이 없거나 마지막 성공 시각이 같으면 경로순으로 결정한다. 실패한 점검은 순환을 진행한 것으로 보지 않는다. 선택한 디렉터리는 실행 기록의 `focus`에 보존한다.

### 정리 작업

main에서 `dream-YYYY-MM-DD` 작업 워크트리를 파생한다. 날짜는 스케줄러 시간대 설정과 별개로 항상 한국 표준시를 따른다. 변경 노트마다 검색 결과에서 자기 자신을 제외한 상위 5개 관련 노트의 경로·제목과 최대 1,500자 발췌만 입력에 포함한다. 관련 노트의 전체 본문을 반복해 주입하지 않으며 더 많은 근거는 `read_file`로 조회한다. 도니는 지식 저장소 `AGENTS.md`와 `MEMORY.md` 문맥, 워크트리 편집 도구를 사용해 다음 작업을 수행한다.

- 변경된 노트와 의미적으로 가까운 기존 노트를 찾아 지식의 충돌과 중복을 정리한다. 유사 노트 조회에는 [RAG](rag.md)를 사용한다.
- 대화 배치에서 추출한 지식을 지식 저장소에 반영한다.
- 깨진 위키링크와 전체·도메인 허브를 정리한다.
- 도니를 호출하는 모든 실행에서 메모리 파일인 `MEMORY.md`를 통합·정리하며 [메모리 파일의 문맥 제공 규칙](knowledge-repository.md#메모리-파일의-문맥-제공-규칙)을 적용한다. 이 점검만을 위한 별도 도니 호출은 만들지 않는다.
- `journal/YYYY-MM-DD.md`에 그날의 변경과 정리 결과, 남은 쟁점을 요약한다. 가져오기 잔여물을 정리한 실행은 일기의 `정제` 절에 정제한 노트 경로와 반영한 핵심 내용, 남은 후보와 남긴 이유를 기록한다. 같은 날짜에 다시 실행하면 기존 일기를 보존하며 보완한다.
- `structural`이나 `sweep`에서는 후보 노트의 주제별 분리·병합·재배치와 태그·도메인 허브 보완을 검토한다. 도니는 미분류·얕은 도메인 노트를 `wiki/<domain>/<topic>/`에 배치하고, 깊이 초과를 줄이며 잘못된 폴더를 안정적인 주제로 재분류하도록 지시받는다. 도메인 허브·schema의 위치는 유지한다. 과밀 신호가 있어도 하위 주제 분리 조건을 만족하지 않으면 기계적으로 나누지 않는다. 정확한 배치와 분리 조건은 [도메인 배치 규칙](knowledge-domains.md#레이아웃)을 따른다. 이동·삭제의 경로와 이유, 상한 때문에 남긴 후보는 일기의 `구조 정리` 절에 기록하도록 지시한다. 엔진이 이 절의 형식을 파싱해 검증하지는 않는다.

가져오기 잔여물은 `local`·`structural`의 `importedNotes`와 `sweep`의 `focus`에 직접 들어 있는 노트에서 정제한다. 원문 표·목록을 그대로 옮긴 덤프는 그 안의 재사용할 사실·결정과 이유·절차·용어로 정리하고, 기존 정본에 통합하거나 적절한 노트에 배치한다. 노트나 그 raw 출처에 없는 사실을 만들거나 의미 있는 내용을 버리지 않으며 [작성 규칙](writing-rules.md)을 따른다.

가져오기·변환 과정의 설명과 내보내기 잔여물인 Notion 페이지 ID, 의미 없는 빈 제목·템플릿 항목, 깨진 첨부 참조는 위키 노트에서 제거하되 실제 식별자와 의미 있는 사실은 보존한다. 반복되는 출처 주의 문구는 실제 시점과 출처 맥락을 정확히 설명하는 한 번의 문구로 줄인다. 중복 지식은 기존 정본에 합치고, 재사용할 지식이 없는 노트는 병합·삭제할 수 있다. 이동·삭제는 기존 20건 상한에 포함하며, 상한 때문에 남긴 후보는 일기에 기록한다.

원문은 출처 확인, SHA 기반 중복 판정과 위키 노트의 출처 링크에 필요한 근거이므로 `raw/`에서 변경·이동·삭제하지 않는다. 정리 대상은 원문이 아니라 그로부터 파생된 `wiki/` 노트다. 출처는 노트 frontmatter의 `source` 배열이나 본문 `출처` 절에만 기록하며, `source` 값은 [노트 메타데이터 표준](note-metadata.md#적용-범위와-필드)에 따라 실제 위키링크 또는 `http(s)` URL 문자열이어야 한다.

편집에는 [작성 규칙](writing-rules.md)을 적용한다. 사용자 발언에서 직접 말한 사실과 정정만 추출하며 질문을 사실로 바꾸거나 도니 답변을 재학습하지 않는다. 일기 파일이 없거나 비어 있으면 main에 반영하지 않고 실패로 기록한다.

꿈꾸기가 바꾼 위키 노트도 커밋 전에 엔진 자동 속성을 채운다. 별도의 메타데이터 보완 실행을 추가하지 않으며, 위의 구조 신호와 정리 작업으로 의미 속성을 보완한다. 자동 속성의 보존·갱신 기준은 [노트 메타데이터 표준](note-metadata.md#엔진-자동-속성)을 따른다. 일기는 메타데이터 표준의 적용 대상이 아니다.

워크트리 파일 읽기와 목록의 상한·이어 읽기 규칙은 [도니의 문맥 크기와 도구 페이지](agent.md#문맥-크기와-도구-페이지)를 따른다. 관련 노트 발췌만으로 충돌이나 중복을 판단하기 어려우면 `read_file`로 필요한 본문 페이지를 조회한다. `write_file`은 전체 파일을 교체하므로 기존 내용을 보존할 때 첫 페이지만 읽고 덮어쓰지 않는다. 추론 강도와 프롬프트 캐시 정책은 [도니의 비용과 사용량](agent.md#비용과-사용량)을 따른다.

### 코드로 강제하는 정리 경계

꿈꾸기 도구는 원문 `raw/`를 불변으로 취급하여 쓰기·이동·삭제를 거절한다. 이동·삭제는 `journal/` 전체와 저장소 루트의 `MEMORY.md`, `AGENTS.md`, `index.md`, 도메인 schema인 `wiki/<domain>/AGENTS.md`도 보호하며 이동의 출발지와 목적지를 모두 검사한다. 이 보호는 경로를 정규화한 뒤 대소문자를 구분하지 않고 판정한다. 공유 영역이나 더 깊은 폴더의 같은 파일명은 도메인 schema로 판정하지 않는다. 일기·메모리·색인 갱신과 루트·도메인 `AGENTS.md`의 쓰기는 이 도구 보호에서 금지하지 않는다.

한 실행에서 성공한 `move_file`과 `delete_file` 호출을 합쳐 최대 20건만 허용한다. 동시 호출도 진행 중인 이동·삭제를 상한에 포함하고, 실패한 호출은 성공 건수에 넣지 않는다. 상한을 넘는 후보는 일기에 남기고, 읽기·쓰기로 이동·삭제를 흉내 내어 상한을 피하지 않도록 지시한다. ACL 이동 경계의 코드 검사와 의미적 복사에 대한 지침의 보장 범위는 [폴더별 접근 제어](access-control.md#꿈꾸기와-한계)를 따른다.

링크 검증은 위키링크 `[[...]]`와 임베드 `![[...]]`를 모두 다룬다. `.md`나 확장자 없는 대상은 마크다운 노트에서, 다른 확장자를 가진 대상은 첨부를 포함한 전체 파일 경로에서 해석한다.
구조 신호·루트 허브 연결과 도입된 링크 검증은 frontmatter 별칭도 해석하며, 정확한 경로·파일명 우선순위와 모호성 처리는 [RAG의 링크 해석](rag.md#http-읽기-인터페이스)을 따른다. 첨부 링크는 별칭 없이 파일 경로로 해석한다.

도니 편집 직후에는 실행 시작에 읽은 main의 미해결 링크 대상 집합을 기준으로 링크 대상을 다시 해석한다. 워크트리를 만들 때 main이 이미 앞서가 더 최신 커밋을 상속했다면, 실제 워크트리 기준 커밋의 미해결 대상 집합도 편집 검증 기준에 합친다. main 반영 직전에는 직렬 머지 락 안에서 main을 워크트리에 머지하기 전에 현재 main의 미해결 대상 집합을 읽고, 실행 시작 main과 현재 main의 집합을 합친 기준으로 머지 결과를 검사한다. 각 검증 기준에 없던 깨진 링크나 모호한 링크 대상이 생기면 실행을 실패시키고 main에 반영하지 않는다. 이는 링크를 쓴 노트가 아니라 정규화한 대상 식별자 단위의 검사이며, 같은 미해결 대상을 `[[Missing.MD]]`에서 `[[missing]]`으로 바꾸는 것만으로는 새로 깨진 링크로 세지 않는다. 오류에는 원래 링크 대상 표기를 남긴다. 기준에 이미 있던 미해결 대상은 남아 있어도 허용한다. 작업 중 다른 쓰기가 main에 추가한 기존 미해결 대상 때문에 꿈꾸기가 실패하지 않지만, 꿈꾸기가 새로 만든 깨진 대상까지 허용하는 것은 아니다.

충돌 해결에는 `search`, `read_file`, `write_file`만 제공하며 파일 읽기·쓰기는 실제 충돌한 파일 목록으로 제한한다. 검색 결과를 얻더라도 충돌하지 않은 파일은 이 도구로 읽거나 수정할 수 없다. 이동·삭제·커밋 도구는 제공하지 않는다.

작업 결과는 `GIT_BOT_NAME`과 `GIT_BOT_EMAIL`을 author로 커밋한다. 직렬 머지 락 안에서 main을 워크트리에 머지하고, 충돌이 발생하면 도니가 해결한 뒤 main을 fast-forward한다. 재인덱싱까지 성공한 뒤 이번 배치에 포함된 사용자 메시지만 `learned_at`으로 표시한다. 머지나 재인덱싱 실패 시에는 미학습 상태를 유지한다. 작업 워크트리 격리와 직렬 머지 방식은 [쓰기 흐름](write-flow.md)을 따른다.

학습 완료 표시는 캡처한 메시지 ID뿐 아니라 본문도 현재 DB 값과 같을 때만 적용한다. 배치가 실행되는 동안 같은 ID의 사용자 메시지가 수정되면 새 본문은 이번 배치에서 읽지 않은 내용이므로 미학습 상태를 유지하고 다음 배치 입력으로 남긴다.

꿈꾸기가 만든 커밋에는 `Wiki-Job: <실행 ID>`, `Wiki-Source: dreaming`, `Wiki-Requester: <봇 이메일>` 트레일러를 붙인다. 성공한 main 머지 직후에는 실제 반영된 경로와 머지 SHA를 담은 `main.updated` 이벤트를 발행한다. 이름이 바뀐 파일은 이전 경로와 새 경로를 모두 포함하며, 후속 인덱싱이 실패해도 이미 반영된 main의 갱신 이벤트는 유지한다.

### 백업과 실패의 관계

꿈꾸기 후 GitHub에 main을 하루 한 번 push한다. 꿈꾸기가 실패하더라도 main push는 시도한다. GitHub는 백업이므로, 정리 작업의 실패가 이미 main에 반영된 지식의 백업까지 막아서는 안 되기 때문이다.

로컬 전용 저장소에서는 push를 건너뛰고 이유를 로그에 남긴다. push 오류는 `push.status='failed'`와 `push.reason`에만 기록하며 정리 실행의 성공·실패와 오류를 바꾸지 않는다. main 반영·재인덱싱·학습 완료 표시까지 성공했다면 `status='succeeded'`, `error=null`과 입력 체크포인트를 유지하므로 다음 실행이 이미 처리한 입력 커밋을 다시 검토하지 않는다. 도니를 호출하지 않은 백업 전용 실행도 push 실패만으로 로컬 체크포인트를 무효화하지 않는다. 반대로 정리·머지·재인덱싱 자체의 실패는 계속 실패로 남는다. push는 머지 락 안에서 실행하며 성공 결과에는 실제 원격 이름과 전송한 SHA를 남긴다. 수동 CLI 실행 결과는 JSON으로 출력하고 정리 실행이 실패한 경우에만 종료 코드 1을 설정한다.

### 실행 기록과 운영 조회

`dream_runs`는 시작·종료 시각, 상태, 입력 커밋 범위, 머지 SHA, 기존 `pushed` 불리언과 오류를 저장한다. 추가 필드는 도니 최종 응답인 `summary`(없으면 `null`), 이번 머지에서 실제 바뀐 `changedPaths`, 검증된 일기 경로 `journalPath`(정리하지 않은 날은 `null`)다. `mode`는 `local`, `structural`, `sweep` 중 선택한 모드이며 선택 전 실패나 정리 없는 실행에서는 `null`이다. 선택 후 실패한 실행은 선택한 모드를 유지한다. `focus`는 순환 점검 디렉터리이며 그 밖의 모드에서는 `null`이다. `structuralChanges`는 워크트리에서 성공한 이동·삭제 도구 호출의 목록이며 각 항목은 `{ kind: 'move' | 'delete', from: string, to?: string }`이다. 삭제에는 `to`가 없고 구조 변경이 없으면 빈 배열이다. 이후 정리나 머지가 실패해도 이 목록은 보존하므로 main에 반영한 변경 목록과는 구분한다. push 결과는 `push.status`(`pending`, `succeeded`, `skipped`, `failed`), `remote`, `sha`, `at`, `reason`으로 별도 보존한다. 확인할 수 없는 원격과 SHA는 `null`이며 추측하지 않는다.

`DreamRunsRepository.get(id)`는 상세 실행 또는 `null`을 반환한다. `list({ before, limit })`는 시작 시각 내림차순, 같은 시각에서는 ID 내림차순으로 조회한다. `before`는 이전 페이지의 마지막 실행 ID이며 시각 커서도 지원한다. 기본 한도는 50개이고 최대 200개다. `latest()`는 가장 최근 실행, `running()`은 실행 중인 기록을 반환하며 없으면 `null`이다. `backupStatus()`는 push 시도가 끝난 마지막 실행 `lastAttempt`와 성공한 마지막 push 실행 `lastSuccess`를 반환한다. 정리 자체가 실패했어도 push가 성공했다면 `lastSuccess`에 포함한다.

HTTP 시작 시 명시적으로 호출하는 `recoverInterrupted()`는 이전 프로세스가 남긴 `status='running'` 기록을 `failed`로 바꾸고 종료 시각과 엔진 재시작으로 중단되었다는 오류를 저장한다. 기존 입력 범위·머지 결과·요약과 모든 push 필드는 보존하며 변경된 실행마다 `dream.updated` 실패 이벤트를 발행한다. 이미 완료된 기록은 건드리지 않으며 다시 호출해도 추가 변경이나 이벤트는 없다. 같은 프로세스에서 같은 저장소 객체의 실제 실행이 진행 중이면 복구 호출도 그 실행을 중단 처리하지 않는다. 이 메모리 상태는 다른 프로세스의 실행을 알 수 없으므로 Nest 초기화 훅에서는 복구하지 않는다. 실행 중복 방지는 DB의 `running` 행이 아니라 저장소 객체별 메모리 상태로 판단하므로, 오래된 행 자체가 다음 수동 실행을 막지는 않지만 HTTP 재시작 시 운영 화면에 계속 실행 중으로 남지 않도록 정리한다.

시작 기록을 저장한 뒤와 최종 결과를 저장한 뒤에 `dream.updated` 이벤트를 발행한다. 이벤트는 실행 ID와 상태만 포함하므로 클라이언트는 상세 데이터를 다시 조회한다. push가 끝나기 전에는 완료 상태 이벤트를 보내지 않는다. 기존 DB는 `008_ops.sql`로 운영 필드를 확장하며, 과거의 성공 불리언은 성공 상태로 이관하되 기록되지 않은 원격·SHA는 채우지 않는다. `021_dream_modes.sql`은 `mode`, `focus`, `structural_changes`를 추가한다. 과거 실행은 모드와 점검 디렉터리가 `null`이며 구조 변경 목록은 빈 배열이다.

정리 모델과 후속 머지 충돌 해결 응답의 사용량 델타는 실행별로 합산하고, 최종 성공·실패 로그의 `usage`에 남긴다. 토큰 필드와 실패 응답 집계 규칙은 [도니의 비용과 사용량](agent.md#비용과-사용량)을 따른다. 도니를 호출하지 않고 백업 push만 시도한 실행은 합계가 0이다. 현재 `dream_runs`와 `DreamRun`에는 토큰 사용량을 저장하는 필드가 없으므로 토큰 합계는 로그에만 남기며 자연어 `summary`에 섞거나 DB·운영 조회·Slack 알림에 새 필드를 추가하지 않는다.

### Slack 완료 알림

선택 환경변수 `SLACK_WEBHOOK_URL`을 설정하면 실행 결과를 DB에 최종 저장한 뒤 성공·실패 알림을 한 번 보낸다. 알림은 상태, 실행 시간(밀리초), 머지 SHA, push 상태와 push SHA만 포함한다. `summary`, 일기·노트 본문, 사용자 입력, 경로, 오류 문자열과 push 이유는 포함하지 않는다. 실행 기록에 남은 민감한 내용이 외부 채널로 넘어가지 않도록 허용된 메타데이터만 새 메시지로 구성한다.

전송에는 5초 제한을 적용한다. HTTP 오류, 네트워크 오류와 시간 초과는 경고 로그만 남기며 완료된 실행의 성공·실패, 학습 여부, push 결과를 바꾸지 않는다. Slack 응답을 읽거나 실행 실패 원인으로 합치지 않는다.
