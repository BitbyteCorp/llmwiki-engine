# 식별자 인코딩
엔진 식별자는 API와 애플리케이션에서 base62, SQLite의 식별자 열에서 base64url로 표현한다.

## 배경
엔진이 생성하는 식별자의 원본은 128비트 UUID다. 이전의 하이픈을 포함한 36자리 UUID를 그대로 노출하지 않고, URL과 외부 도구에서 쓰기 쉬운 고정 길이 표현으로 통일한다. 같은 원본을 서로 다른 문자열로 표현하므로 인코딩 변환의 경계를 명확히 해야 조회와 외래 키 연결이 어긋나지 않는다.

## 내용
### 두 가지 표현과 SQL 경계
`src/common/ids.ts`의 `newId()`는 UUID v4를 생성하고 `0-9A-Za-z`를 사용하는 22자리 base62 문자열을 반환한다. 앞자리 0을 유지하므로 모든 식별자의 길이가 같다. API 응답·SSE·MCP·이벤트·로그·`X-Request-ID`와 서비스의 값, 메모리 내 키, 검색 스냅샷 식별자도 이 표현을 쓴다.

SQLite의 기본 키·외래 키·식별자 값 열은 같은 16바이트를 패딩 없는 22자리 base64url로 저장한다. `+`와 `/` 대신 `-`와 `_`를 쓰며 `=` 패딩은 저장하지 않는다. 이 표현은 일반적인 base64와 같은 원본 바이트를 담지만 URL 안전 알파벳을 쓴다.

SQL 매개변수를 바인딩하는 저장소 코드에서 `toStorageId()`로 변환하고, 조회 행을 애플리케이션 값으로 매핑할 때 `fromStorageId()`로 되돌린다. 컨트롤러나 서비스에서 저장 표현을 다루지 않는다. SQL 경계 한 곳에서만 변환해야 SQL 조인과 외래 키는 같은 표현을 유지하고 외부 응답에는 저장 표현이 섞이지 않는다. 잘못된 API 입력은 조회 실패나 입력 오류로 처리하며, 잘못된 저장 값은 정상 식별자로 위장하지 않고 오류로 드러낸다.

사용자 번호처럼 원래 정수인 키는 바꾸지 않는다. 클라이언트가 제공한 `clientId`와 OAuth `client_id`, 비밀 토큰 값·해시·git SHA·노트 경로는 엔진 UUID가 아니므로 그대로 보존한다.

### 이전 UUID 입력과 외부 파일
`parseApiId()`와 `idSchema`는 base62와 이전의 정규 UUID 문자열을 입력으로 받아 base62로 정규화한다. 이전 링크와 외부 클라이언트를 유지하기 위한 입력 호환성이며, 응답에 정규 UUID를 다시 내보내는 규칙이 아니다.

새 git 커밋의 `Wiki-Job` 트레일러, 대화 쓰기가 대화 식별자를 남기는 `Wiki-Client` 트레일러와 작업 워크트리 이름·참조는 base62를 쓴다. 예전 커밋에서 읽은 두 트레일러의 UUID 값과 blame의 작업 식별자는 커밋을 파싱할 때 base62로 정규화하며, `web` 같은 일반 클라이언트 이름은 그대로 둔다. git 이력을 다시 쓰지 않고 이력·활동·blame 응답과 커밋의 작업 연결을 같은 애플리케이션 표현으로 맞춘다. git의 커밋 본문(`%b`)은 트레일러 블록을 다시 포함하므로 응답의 `body`에서는 `trailers`와 중복되는 마지막 트레일러 블록을 제거한다. 이를 두지 않으면 예전 커밋의 본문이 정규화하지 않은 UUID를 그대로 노출한다.

디스크의 새 업로드 파일 이름은 base62 업로드 식별자를 쓴다. SQLite의 업로드 행 식별자만 base64url이다. 이전 UUID 파일 이름도 읽기 입력으로 받아 기존 첨부를 유지하며, 외부에 반환하는 첨부 식별자는 항상 base62다.

### JSON 소유권과 재생 문서
`messages.attachments`처럼 저장소가 소유하는 식별자 배열은 SQL에 저장할 때 각 업로드 식별자를 base64url로 바꾸고 읽을 때 base62로 되돌린다. JSON이라는 형식만으로 변환 방향을 정하지 않고 그 값의 소유권을 따른다.

`generation_frames.data`와 `write_job_events.detail`처럼 클라이언트로 재생하는 직렬화 문서는 이미 발행한 API 표현을 그대로 저장한다. 이 문서 안의 식별자는 base62이며 읽을 때 다시 인코딩하지 않는다. 메시지 본문·제목·노트 원문 등 사용자 콘텐츠는 식별자처럼 보이는 문자열을 포함하더라도 이 데이터 마이그레이션의 변환 대상이 아니다.

`audit_events.target`도 그대로 응답에 내보내는 불투명한 문자열이다. 작업 식별자 하나뿐 아니라 `대화 식별자/사용자 번호` 같은 복합 값도 담으므로 API 표현을 유지한다. 마이그레이션은 이 문자열 안의 이전 UUID만 base62로 바꾸며 사용자 이름을 담는 감사 요약은 바꾸지 않는다.

### 기존 데이터 마이그레이션
`018_base62_ids.sql`은 이전 정규 UUID 식별자 열과 소유한 첨부 배열을 base64url로, 이벤트·재생 문서의 UUID 값은 base62로 바꾼다. 러너는 마이그레이션 전에 결정적 SQLite 함수 `legacy_uuid_to_storage(text)`, `legacy_uuids_to_api(text)`, `legacy_json_ids_to_api(json)`을 등록한다. UUID가 아닌 값과 `NULL`은 그대로 유지하므로 빈 DB와 이미 변환된 값도 안전하게 처리한다.

`legacy_json_ids_to_api`는 JSON을 파싱하고 깊이에 관계없이 문자열 값 전체가 정규 UUID인 경우에만 변환한다. 문서의 키나 문장 안의 UUID 부분 문자열은 바꾸지 않으므로 `delta.text`에 인용된 UUID도 유지한다. 잘못된 JSON은 그대로 두며, 변환할 UUID 값이 없으면 원래 직렬화 문자열을 그대로 반환한다. JSON 재생 문서 전체에 정규식 치환을 적용하지 않는다.

대화 쓰기 작업의 `client`는 `source = 'chat'`일 때 대화 식별자를 담으므로 API 표현으로 바꾼다. `chat:<대화 ID>:<사용자 메시지 ID>:<호출 순번>:<내용 SHA-256>:<요청자 ID>` 형식의 작업 중복 키와 원문 수집의 `upload:<업로드 ID>` 출처도 해당 형식만 골라 API 표현으로 바꾼다. 다른 클라이언트 이름·중복 키·URL·파일 이름은 보존한다. 이 복합 문자열과 감사 대상의 UUID 부분 문자열은 `legacy_uuids_to_api`로 변환한다.

각 갱신은 인코딩이 실제로 달라지는 행에만 적용한다. 이미 변환된 행이나 UUID가 아닌 이전 값에 불필요한 `UPDATE`를 수행해 갱신 트리거를 실행하지 않는다.

기본 키와 참조 열을 한 트랜잭션에서 함께 갱신하고 `PRAGMA defer_foreign_keys = ON`으로 외래 키 검사를 커밋까지 미룬다. 외래 키 강제 자체를 끄거나 기존 git 이력·업로드 파일 이름·사용자 본문을 다시 쓰지 않는다. 적용 이력과 트랜잭션 처리의 일반 규칙은 [개발 환경](development.md#sql-마이그레이션과-테이블-재구축)에 기록한다.
