# 원문 수집
URL·PDF·텍스트·Markdown 파일·Obsidian 볼트·Notion 내보내기를 불변 원문과 출처 Markdown으로 보관한 뒤, 볼트의 Markdown을 빠짐없이 배치별 도니 통합 작업으로 연결한다.

## 배경
수집과 지식 통합은 서로 다른 단계다. 수집 단계는 다운로드·압축 해제·텍스트 추출을 수행하고 원문을 먼저 git에 저장한다. 통합 단계는 이미 커밋된 출처 Markdown을 도니가 읽어 위키 노트를 정리하는 작업이다. 통합이 실패하더라도 원문 커밋은 보존하므로 원문의 출처와 실패 원인을 확인할 수 있다.

대형 Notion 내보내기에서 Markdown 788개와 텍스트 약 2.9 MB를 단일 통합 작업에 맡겼으나, 도니는 27개만 읽고 하위 에이전트를 사용하지 않은 채 위키 노트 두 개를 작성하여 성공으로 끝냈다. 배치 분할 후에도 25개 배치 중 완료된 0~8번을 조사했을 때 2~6번의 담당 원문을 부모와 자식 모두 한 번도 읽지 않았다. 부모는 담당 파일 수만 작업 설명에 적고 실제 경로를 자식에게 전달하지 않았으며, 자식은 목록을 받지 못했다고 응답했다. 부모 요약에 미완료 사실이 있어도 엔진은 성공으로 처리했다. 따라서 배치 프롬프트만으로 전체 읽기를 보장하지 않고 읽기 배정 전달과 엔진의 완료 검증을 함께 적용한다.

## 내용
### 입력과 권한
`IngestModule`은 `IngestService`를 내보내며 REST와 MCP가 같은 `ingest`를 사용한다.

```ts
await ingest.ingest({
  userId: 1,
  kind: 'url', // url | pdf | text | obsidian | notion | file
  url: 'https://example.com/article',
  instructions: '주요 개념을 기존 위키에 연결한다.',
}); // { importId, jobIds }
```

`POST /api/imports`는 editor 이상이며, JSON에는 `userId` 없이 같은 필드를 전달한다. 세션 쿠키와 REST bearer 토큰을 지원한다. `url`, `uploadId`, `text` 중 하나만 전달하며 다음 규칙을 따른다.

| 종류 | 입력 | 처리 |
| --- | --- | --- |
| `url` | `url` | HTML 기사·PDF·UTF-8 텍스트·Markdown을 다운로드한다. |
| `pdf` | `url` 또는 `uploadId` | 실제 PDF 헤더를 확인하고 텍스트를 추출한다. |
| `text` | 비어 있지 않은 `text` | UTF-8 텍스트를 원문 그대로 보관한다. |
| `file` | `uploadId` | 업로드한 PDF·UTF-8 텍스트·Markdown을 추출한다. |
| `obsidian` | import 목적 ZIP의 `uploadId` | Markdown과 첨부 파일의 폴더 구조 및 위키링크를 유지한다. |
| `notion` | import 목적 ZIP의 `uploadId` | Markdown과 첨부 파일을 보관하며 경로와 링크의 내보내기 페이지 ID를 함께 제거한다. |

선택 필드 `filename`은 원문 파일명이고 `instructions`는 최대 10,000자의 요청자 지침이다. 업로드는 `POST /api/uploads`의 multipart `file`과 `purpose=import`로 먼저 생성한다. ZIP은 import 목적에서만 허용하며 해당 업로드를 만든 사용자만 수집할 수 있다. 채팅 첨부와 import ZIP은 서로 교환하지 않는다.

`GET /api/imports?limit=50&before=<importId>`는 `{ imports: [...] }`를 반환하며 viewer 이상이 자신의 기록만 조회한다. admin은 모든 사용자의 기록을 조회한다. `GET /api/imports/:id`도 같은 소유자/admin 규칙을 적용하며 다른 소유자의 기록은 404로 숨긴다. 기록은 `id`, `userId`, `kind`, `source`, `sha`, `status`, `rawPaths`, `jobs`, `error`, `retryable`, `retryReason`, `createdAt`, `updatedAt`, `finishedAt`을 포함한다. `retryable`은 원문 수집을 재실행할 수 있는지 나타내고, 불가능하면 `retryReason`이 이유를 설명하며 가능하면 `null`이다. 보존한 입력 텍스트와 요청자 지침은 응답에 노출하지 않는다. `jobs`는 배치 순서의 배열이며 각 항목은 0부터 시작하는 `batch`, 최신 재시도의 base62 `jobId`, 현재 작업의 `status`, `error`, 담당 Markdown 파일 수인 `files`를 담는다. 작업의 `merging`은 `running`으로 표현하며 작업 제출 전 수집 실패에서는 `jobs`가 빈 배열이다. 수집 응답은 `{ importId, jobIds }`이며 `jobIds`도 배치 순서다.

### 다운로드 보안과 한도
다운로더는 자격 증명이 없는 `http`와 `https`만 허용한다. DNS 응답 중 하나라도 사설·루프백·링크 로컬·공유 주소·비전역 주소이면 연결하지 않는다. IPv4 정수 표기와 IPv4-mapped IPv6도 URL 정규화와 주소 검사에서 차단한다. localhost, 로컬 도메인, 메타데이터 호스트, 메타데이터 주소와 IPv6 터널 주소도 차단한다.

각 리다이렉트에서 URL과 모든 DNS 응답을 다시 검사하고 최대 다섯 번만 따라간다. 검사한 IP를 실제 연결의 lookup에 고정하되 Host와 TLS SNI는 원래 호스트를 유지하므로 DNS 재바인딩을 허용하지 않는다. HTML의 이미지·iframe·스크립트·링크를 추가로 다운로드하지 않는다.

| 항목 | 한도 |
| --- | --- |
| URL 다운로드 총 시간 | DNS와 리다이렉트를 포함한 15초 |
| URL·PDF·텍스트·일반 파일 | 20 MiB |
| import JSON 인코딩된 요청 본문 | 21 MiB이며 추출된 원문은 별도로 20 MiB를 검사한다. |
| PDF | 최대 500페이지이며 OCR을 수행하지 않는다. |
| ZIP 압축 파일 | 100 MiB |
| ZIP 총 해제 크기 | 100 MiB |
| ZIP 개별 항목 | 20 MiB |
| ZIP 항목 수 | 디렉터리를 포함해 1,000개 |
| 리다이렉트 | 최대 5회 |

원격 Content-Type은 HTML/XHTML, PDF, text/plain, text/markdown만 허용하고 압축 HTTP 본문을 거부한다. Content-Length와 실제 스트림 바이트 수를 모두 검사한다. HTML은 linkedom으로 파싱한 뒤 Readability로 기사 본문을 골라 Turndown으로 Markdown을 만든다. 상대 HTTP 링크는 최종 URL을 기준으로 절대 주소로 바꾼다. PDF는 unpdf를 사용하며 추출할 텍스트가 없으면 오류를 반환한다.

ZIP은 fflate의 스트리밍 해제를 사용한다. 먼저 중앙 디렉터리를 검사하고 압축 조각을 작게 공급하며 선언 크기와 실제 해제 크기를 모두 검사한다. 절대 경로, `..`, 역슬래시, 제어 문자, `.git`, 중복 경로, symlink, 암호화, 다중 디스크 및 ZIP64를 거부한다. 서버 파일시스템에 ZIP 항목을 쓰지 않으며, `.obsidian` 같은 숨김 메타데이터와 `__MACOSX`는 위키 자료에서 제외한다. 원문 문장에 있는 ID와 외부 URL은 바꾸지 않는다.

Notion은 같은 부모 아래 제목이 같은 페이지를 허용한다. 예를 들어 제목을 비운 페이지는 모두 `제목 없음 <ID>.md`로 내보내진다. 따라서 ID를 일괄 제거하면 여러 페이지가 한 경로로 합쳐진다. 엔진은 먼저 ZIP의 전체 경로를 보고 같은 부모에서 ID 제거 후 이름이 겹치는 페이지만 원래 이름(ID 포함)을 유지한다. 나머지 페이지는 ID를 제거한다. 페이지 파일 `X <ID>.md`와 하위 폴더 `X <ID>/`는 같은 페이지로 보고 함께 판단하므로 둘의 이름이 어긋나지 않는다. 최근 내보내기처럼 하위 폴더 이름에 ID가 없으면(`X <ID>.md`와 `X/`) 그 폴더는 별도 페이지로 세지 않는다. 상대 Markdown 링크는 링크한 파일 위치에서 ZIP 경로로 해석한 뒤 바뀐 경로 기준의 상대 경로로 다시 쓰므로, 이름을 유지한 페이지로도 올바르게 연결된다. ZIP에 없는 대상과 위키링크는 ID 문자열만 제거한다. 이 규칙으로도 두 항목이 같은 경로가 되면 덮어쓰지 않고 `Normalized ZIP paths collide`로 전체 수집을 실패시킨다.

Notion 링크에는 일반 Markdown 파서가 놓치는 두 가지 모양이 있다. 링크 텍스트에 대괄호가 그대로 들어가고(`[[보상] 기준](…)`), 대상 경로에서 `(`는 `%28`로 인코딩하지만 `)`는 그대로 둔다(`%28해외)%20<ID>.md`). 엔진은 한 단계 중첩된 대괄호 텍스트를 허용하고, 대상이 리터럴 `)`를 지나 파일 확장자로 끝나며 바로 `)`가 이어지면 그 전체를 대상 경로로 본다. 다시 쓴 링크는 `)`도 `%29`로 인코딩한다. 내보내기 ZIP에 들어 있지 않은 첨부(이미지 없이 내보낸 경우 등)를 가리키는 링크는 원본에서처럼 끊긴 채 남는다.

### 불변 원문과 커밋
원본 바이트의 SHA-256을 디렉터리 이름으로 사용한다.

```text
raw/<sha256>/
├── original/<filename>                 # 다운로드·업로드·텍스트 원본 바이트
├── extracted/<kind>/files/<vault-path> # ZIP의 Markdown과 바이너리 첨부
└── imports/<importId>.md               # 추출한 본문 또는 볼트 노트 목록과 출처
```

출처 Markdown의 frontmatter에는 import ID, `importer`(수집을 요청한 사용자의 숫자 ID), 종류, 원래 source, 최종 URL, SHA-256, 파일명과 수집 시간을 기록한다. 본문은 불변 원문 링크와 추출 본문 또는 추출 노트 링크를 포함한다. 모든 새 원문·첨부·출처 Markdown은 `NoteWriterService.apply({ source: 'import', client: 'ingest' })` 한 번으로 커밋한다. 기존 raw 경로는 수정하지 않는다. 동일 원문을 다시 수집하면 git blob ID로 실제 바이트가 같은지 확인하여 기존 불변 자료를 재사용하고 별도의 출처 기록과 통합 작업을 생성한다. 대형 바이너리도 문자열로 읽지 않고 git 메타데이터와 입력 바이트의 blob 해시를 비교한다. 경로가 같으나 기존 바이트가 다르면 `409 raw_conflict`로 거부한다. git 커밋에는 일반 쓰기와 동일한 job/source/requester/client trailer가 들어간다.

### 통합 작업과 복구
원문 커밋은 한 번만 수행하고, 볼트의 추출 Markdown만 배치 계획에 넣는다. 기본 한도는 배치당 120,000자와 40개 파일이다. 경로를 구간별로 비교하여 같은 부모의 파일을 모으고 Notion 페이지 `X.md`를 하위 폴더 `X/…` 바로 앞에 둔 뒤, 연속된 파일을 한도 안에서 탐욕적으로 묶는다. 120,000자를 넘는 파일은 단독 배치로 두고 페이지 읽기로 처리한다. 첨부는 파일 수·문자 예산에서 제외하지만 링크로 읽을 수 있다. URL·PDF·텍스트·일반 파일과 Markdown 없는 볼트는 파일 목록 없는 출처 전용 배치 하나를 제출한다.

각 배치는 `source=import`인 별도의 도니 작업이며 직렬 쓰기 큐에서 가져오기끼리의 FIFO와 배치 순서를 유지한다. 중간에 대화형 작업을 실행할 수 있으며 우선순위와 가져오기 진행 보장은 [쓰기 흐름의 대기열 선택 순서](write-flow.md#대기열-선택-순서)를 따른다. 뒤 배치는 앞 배치가 `main`에 머지한 노트를 검색하고 확장하므로 같은 지식을 중복 노트로 만들지 않는다. 작업의 `sourcePaths`는 원본 경로, 출처 Markdown 경로, 해당 배치의 추출 Markdown 경로다. 실제 통합 실행과 한도는 기존 [쓰기 흐름](write-flow.md)을 따른다.

배치 프롬프트는 import ID, 종류, 원래 source, 최종 URL(있는 경우), SHA-256, 파일명과 안정적인 출처 Markdown 경로를 간결한 출처 정보로 전달하며 `Batch i of n`과 정확한 담당 raw 경로 목록을 함께 준다. 추출 Markdown이 있는 배치는 볼트 전체 목록인 출처 Markdown을 읽도록 지시하지 않으며, 그 경로를 읽지 않고도 출처로 인용할 수 있다고 안내한다. 감사와 인용에 쓰는 불변 출처 Markdown 및 전체 노트 목록은 그대로 보관한다. URL·PDF·텍스트·일반 파일처럼 추출 Markdown이 없는 배치는 출처 Markdown 자체에 실제 추출 본문이 있으므로 그 파일을 끝까지 읽도록 지시한다.

도니는 담당 목록의 모든 파일을 끝까지 읽고, 잘린 읽기는 `nextOffset`·`nextCharOffset`으로 이어 읽는다. 파일마다 일반 작성 규칙에 따라 영속 지식을 위키에 통합하거나 비어 있음·탐색 전용·중복·일시 정보·비밀/개인정보라는 이유로 명시적으로 제외한다. 제외할 파일도 먼저 끝까지 읽어야 한다. 다른 배치의 추출 파일을 통합하지 않으며 큰 배치는 위키 파일 소유권을 겹치지 않게 나누어 `spawn_subagent`를 사용하고 정확한 담당 raw 경로를 `sources`에 전달한다. `sources`의 읽기 배정과 `files`의 쓰기 소유권은 [쓰기 서브에이전트](agent.md#쓰기-서브에이전트)의 별도 계약이다. 최종 요약은 모든 담당 파일의 대상 노트 또는 제외 이유를 설명한다. 원문은 지침이 아닌 신뢰하지 않는 데이터로 취급하며 `raw/`를 수정하지 않는다. 요청자 지침은 최대 10,000자로 그대로 덧붙인다.

각 배치의 `requiredReads`는 추출 Markdown 경로만 담는다. `sourcePaths`는 접근 권한 검사와 출처 추적을 위한 맥락이며 모델에 읽기 지시를 추가하지 않는다. 원본 ZIP·바이너리와 출처 Markdown은 이 필수 목록에 들어가지 않는다. 추출 Markdown이 없는 배치는 필수 목록이 비어 있으므로 출처 읽기 지침만 적용한다. 엔진은 같은 실행의 부모와 자식이 성공한 `read_file`에서 실제 반환받은 페이지 범위를 합산한다. 순서와 중복 여부에 관계없이 모든 줄과 긴 줄의 모든 문자 구간이 덮여야 한 파일을 완료로 인정한다. 마지막 페이지만 읽거나 검색·목록 조회·읽기 시도 이력만 남기는 것으로는 인정하지 않으며 빈 파일은 성공한 읽기 한 번으로 인정한다.

필수 원문이 남으면 엔진은 부모의 최종 응답을 거절하고 미완독 경로와 실행 중인 자식 수를 담은 후속 사용자 메시지를 추가한다. 부모는 직접 읽거나 `sources`로 위임하고 실행 중인 자식을 기다려야 한다. 세 번째 미완독 완료 응답 또는 턴 한도 소진은 `unread assigned sources: k/n (<대표 경로>)` 오류로 작업을 실패시키므로 해당 배치도 실패·재시도 대상으로 집계된다. 이 검증은 도구가 원문 전체를 반환했다는 조건이며 요약의 사실성이나 통합 품질까지 보장하지는 않는다.

필수 목록은 `write_jobs.required_reads` JSON 열에 보존하고 재시도 작업에도 그대로 복사한다. 완독 범위는 실행 시도마다 새로 계산하며 체크포인트에서 복구하지 않는다. 따라서 이전 실행에서 읽은 원문도 재시도에서는 다시 읽어야 한다. 거절 응답과 후속 메시지의 체크포인트·실패 보존 절차는 [쓰기 흐름](write-flow.md#요청자-추적과-실패-복구)을 따른다.

`imports` SQLite 테이블은 수집 메타데이터와 집계 상태를 보관한다. `import_jobs`는 `(import_id, batch)` 기본 키와 현재 `job_id`, 담당 경로 JSON 배열인 `files`를 보관하며 작업 ID 인덱스로 이벤트를 연결한다. API·서비스에서는 base62 ID를 쓰고 식별자 열은 [식별자](identifiers.md)의 저장 규칙을 따른다. `020_import_jobs.sql`은 기존 단일 작업을 파일 목록 없는 배치 0으로 옮기고 `imports.job_id`를 제거한다.

집계 상태는 제출 전 `extracting`이다. 아직 종료하지 않은 배치가 있으면 실행 중인 배치가 하나라도 있을 때 `running`, 아니면 `queued`다. 모든 배치가 성공하면 `succeeded`다. 모든 배치가 종료했고 실패가 있으면 `failed`이며 `error`는 첫 실패 배치의 `batch i/n: <작업 오류>`다. 대기 중인 write job을 취소하면 작업이 `failed`(`error: canceled`)로 기록되므로 그 배치도 실패로 집계되어 `batch i/n: canceled`가 된다. 실패 없이 취소된 배치가 있으면 `cancelled`라는 분기는 계약에 남아 있지만 현재 write job에는 별도 취소 상태가 없어 도달하지 않는다. `finishedAt`은 집계 상태가 종료 상태일 때만 설정한다. `job.updated` 이벤트가 상태를 갱신하고, 목록·상세 조회와 시작 시 저장된 write job 및 재시도 연결을 확인하므로 놓친 이벤트도 복구한다. 작업 제출 전에 프로세스가 중단된 기록은 시작 시 실패로 바꾼다. 수집 실패는 기록에 남고 REST는 해당 오류를 반환한다.

`POST /api/imports/:id/retry`는 editor 이상이 소유한 기록이나 admin이 조회할 수 있는 기록에만 허용하며 다른 소유자의 기록은 404로 숨긴다. 원문 다운로드·추출·raw 저장 단계에서 실패했고 연결된 통합 작업도, 커밋된 원문도 없는 기록만 같은 import ID로 재시도한다. 성공 응답은 새 수집과 같은 `{ importId, jobIds }`다. 재시도할 수 없는 상태나 동시에 들어온 재시도는 `409 import_not_retryable`로 거부한다. 실행 전에 SQLite에서 `failed`를 `extracting`으로 원자적으로 바꾸고 이전 `error`와 `finishedAt`을 비운다. 재실패하면 같은 기록을 `failed`로 되돌리고 최신 오류와 종료 시간을 남긴다.

재시도는 최초 수집과 같은 다운로드·추출·불변 raw 저장 경로를 사용한다. URL은 최종 리다이렉트 주소가 아니라 원래 URL에서 다시 다운로드하고, 업로드는 저장된 `source`의 업로드 ID로 다시 읽는다. admin이 재시도해도 업로드 조회·출처의 `importer`·raw 커밋·통합 작업의 소유자는 원래 사용자로 유지한다. 최초 파일명과 요청자 지침도 유지한다. 업로드 행이나 실제 파일이 만료·삭제되었으면 목록과 상세의 `retryReason`에 원본 업로드를 다시 올려야 한다고 표시한다.

`025_import_retry.sql`은 별도 열 `retained_text`, `filename`, `instructions`, `raw_committed`를 추가한다. 새 텍스트 입력은 raw 저장이 성공할 때까지만 SQLite에 보존하며, 성공하면 `retained_text`를 지워 대형 원문을 영구 중복 보관하지 않는다. 업로드 ID는 이미 있는 `source`에만 두고 JSON이나 별도 소유 식별자 열로 복제하지 않는다. `sha`와 `rawPaths`는 raw 저장 시도 전에 기록되므로 이 값만으로 커밋 성공을 판단하지 않고 `raw_committed`로 구분한다. 이전 URL·업로드 기록은 남아 있는 출처로 재시도하지만 이전 텍스트 기록은 원문 입력이 보존되지 않았으므로 다시 제출해야 한다. 이전 기록에서 원문 커밋 후 작업 연결 전에 중단된 경우에는 목록이 재시도 후보로 표시할 수 있으나, 재시도 실행이 기존 출처 Markdown의 git blob을 확인해 원문 재수집을 거부하고 이후 `retryable=false`로 표시한다.

식별자 마이그레이션은 이미 커밋된 raw 파일명을 바꾸지 않는다. 이전 UUID 파일명의 출처 Markdown도 커밋 여부를 확인할 수 있도록 재시도는 현재 base62 import ID로 파일명을 다시 만들기보다 기록의 `rawPaths`에 보존된 출처 경로를 우선 사용한다.

시작 시 수집 상태 조정은 기록과 작업 연결의 정합성만 복구하며 수집 재시도나 통합 작업을 자동 실행하지 않는다. `JOBS_AUTOSTART=false`에서도 수동 수집·수집 재시도·일반 상태 조정은 그대로 동작하고, 통합 작업은 큐에 남는다.

실패한 배치 작업을 재시도하면 새 작업의 `queued` 이벤트에 저장된 `retryOf`가 이전 작업 ID를 가리킨다. 해당 배치의 `job_id`만 새 작업으로 바꾸고 다른 배치의 연결·성공 결과는 유지한다. 집계 상태를 다시 계산하여 미완료 상태로 돌아가면 이전 `error`와 `finishedAt`을 비운다. 원문·출처 경로와 SHA는 그대로 보존하고 수집이나 원문 커밋을 다시 수행하지 않는다. 연속 재시도와 누락 이벤트도 배치별 `retryOf` 연결을 따라 최신 작업으로 복구한다.

수집 제출의 `import.create`와 집계 종료의 `import.complete` 감사 기록에는 사용자, import ID, 종류만 남기며 원문 내용은 요약에 넣지 않는다. 집계가 종료 상태로 바뀔 때 한 번 기록하며 반복 조회는 중복 기록하지 않는다. 실패 후 재시도하여 다시 종료하면 그 실행 결과를 별도로 기록한다.
