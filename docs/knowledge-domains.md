# 지식 도메인 구조

하나의 지식 저장소 안에서 분야별 노트와 공유 개념·엔티티를 구분하고, 전체 허브와 도메인 허브를 연결한다.

## 배경

기존 구조는 `wiki/` 아래에 노트를 평평하게 모으고, 연구·ML 중심 태그 예시와 논문 속성 규칙을 공통 schema에 두었다. 진입점도 루트 `index.md` 하나여서 연구 외에 개발·건강 같은 분야가 늘어나면 분야별 조회 경로와 작성 기준을 분리하기 어려웠다.

저장소를 나누는 대신 폴더로 분야를 구분한다. 분야 안의 맥락은 도메인 노트에 두고, 여러 분야가 참조하는 지식은 공유 정본으로 연결해 저장소 전체의 관계를 유지한다.

## 내용

### 레이아웃

```text
index.md                     # 전체 허브
AGENTS.md                    # 도메인 중립 공통 schema
MEMORY.md
raw/
journal/
wiki/
  concepts/                  # 공유 개념·용어 정본
  entities/                  # 공유 사람·조직·도구·제품 정본
  <domain>/                  # engineering, research, health 등
    index.md                 # 도메인 허브(MOC)
    AGENTS.md                # 선택적인 도메인 schema
    ...                      # 분야별 노트, 중첩 폴더 허용
```

`<domain>`은 영어 소문자 kebab-case 이름이다. `concepts`와 `entities`는 공유 영역이므로 도메인 이름으로 사용하지 않는다. 원문·첨부·일기·메모리와 git 저장소의 운영 역할은 [지식 저장소](knowledge-repository.md)에 설명한다. 이 구조는 완성된 지식의 배치 규칙이며, 빈 seed에 예시 도메인이나 가짜 노트를 미리 생성한다는 뜻은 아니다.

### 노트 배치와 탐색

- 오래 유지할 노트는 정확히 하나의 정본 경로에 둔다. 특정 분야의 결정·절차·기록은 `wiki/<domain>/...`에 두며, `wiki/` 바로 아래에는 새 노트를 만들지 않는다.
- 두 개 이상의 도메인에서 재사용하거나 명백히 도메인 독립적인 용어·개념은 `wiki/concepts/`에 둔다. 같은 조건의 사람·조직·도구·제품 노트는 `wiki/entities/`에 둔다.
- 같은 대상을 여러 분야에서 참조해도 정본을 복제하지 않는다. 분야별 적용 맥락은 각 도메인 노트에 남기고 공유 정본에 위키링크로 연결한다. 예를 들어 캐시 무효화의 일반 원리는 공유 개념에, 특정 서비스의 캐시 결정은 engineering 도메인에 둔다.
- 새 도메인을 만들 때는 `wiki/<domain>/index.md`를 함께 만들고 루트 `index.md`에서 연결한다.
- 도메인 허브는 해당 분야의 중요한 노트와 조회 경로를 큐레이션하는 MOC(Map of Content)다. 전체 파일 목록이나 본문 복사본이 아니다.
- 루트 `index.md`는 전체 허브로서 각 도메인 허브와 분야를 가로지르는 공유 진입점을 연결한다. 탐색 흐름은 전체 허브 → 도메인 허브 → 노트이며, 공유 정본은 여러 도메인에서 직접 참조할 수 있다.

내용을 지식 단위로 나누고 저장 가치를 판단하는 절차는 [작성 규칙](writing-rules.md#저장-판단과-기존-노트-활용)을 따른다.

### 도메인 schema

루트 `AGENTS.md`에는 문체·사실성과 [노트 메타데이터](note-metadata.md)처럼 모든 분야에 적용하는 공통 규칙만 둔다. 논문의 외부 식별자처럼 분야에만 필요한 규칙은 선택적인 `wiki/<domain>/AGENTS.md`에 둔다.

도니는 `wiki/<domain>/` 안에 쓰거나 편집하기 전에 해당 도메인의 `AGENTS.md`가 있으면 읽는다. 우선순위는 엔진의 실행·보안 지시, 해당 도메인의 schema, 루트 schema 순이다. 도메인 schema는 해당 분야의 작성 관례를 확장하거나 재정의하며, 다른 도메인이나 `wiki/concepts/`, `wiki/entities/`에는 적용하지 않는다. 재정의로 ACL·불변 원문·민감 정보·사실성·정본 한 곳·공통 배치와 허브 규칙, 필수 메타데이터와 엔진 자동 속성의 소유 경계를 완화하지 않는다.

도메인 schema는 루트 schema와 같은 보호 대상이다. 서브에이전트의 소유 범위 경계는 [도니의 쓰기 서브에이전트](agent.md#쓰기-서브에이전트)에, 꿈꾸기의 허용 연산과 보호 경계는 [꿈꾸기](dreaming.md#코드로-강제하는-정리-경계)에 설명한다.

#### 연구 도메인 schema 예시

기존 공통 규칙의 논문 속성 절은 `wiki/research/AGENTS.md`로 옮기되, [노트 메타데이터](note-metadata.md)의 필수 속성과 공통 출처 형식을 유지한다. 아래는 그 파일의 내용 예시이며, 빈 저장소에 자동으로 생성하지 않는다.

```markdown
# 연구 도메인 작성 규칙

이 규칙은 wiki/research/ 안의 연구 노트에만 적용하며 루트 AGENTS.md의 공통 작성 규칙을 확장한다.

## 논문 노트의 속성

- 논문 읽기 상태를 frontmatter의 `status`나 `Read Status` 섹션으로 기록하지 않는다. 유지·관리 날짜는 엔진이 채우는 `date modified`를 따른다.
- 논문 원문과 정식 외부 식별자 URL은 공통 `source` 목록에 담는다. 분야 전용 `pdf`, `arxiv` 속성은 별도의 외부 식별이 필요할 때만 추가하며, 공통 출처 속성을 대체하지 않는다.
- 프로젝트 방향을 나타내기 위한 버전이나 실험 단계 속성을 추가하지 않는다. 버전과 주장 범위는 제목이나 본문에 적는다.
- 분야 전용 속성은 검색·필터링·출처 조회에 유용할 때만 추가한다. 공통 필수 메타데이터를 생략하거나 엔진 자동 속성을 직접 정하지 않는다.
```

### 권한과 검색

도메인은 별도 권한 모델이 아니다. 기존 [ACL 경로 접두사](access-control.md#규칙과-우선순위)로 `wiki/research/` 같은 범위를 지정하면 도메인별 읽기·쓰기 권한을 적용할 수 있다. 공유 개념·엔티티의 접근 범위는 그 공유 경로에 적용되는 ACL을 따른다. 루트 허브 링크가 대상 노트의 권한을 부여하지는 않는다.

검색의 기존 `folder` 필터에 `wiki/research/`를 지정하면 그 도메인으로 검색 범위를 좁힐 수 있다. 필터는 ACL을 대체하거나 우회하지 않는다. 도메인을 위해 RAG·API·MCP schema나 별도 색인을 추가하지 않으며, 검색과 인덱싱의 계약은 [RAG](rag.md)를 따른다.

### 설계 선택과 참고 구조

| 선택 | 이유 |
| --- | --- |
| 도메인은 폴더로 표현한다. | ACL·검색·인덱싱이 이미 경로 기반이다. [노트 메타데이터](note-metadata.md)와 도메인 경계를 구분하며, CMDS의 `CMDS:` 메타데이터처럼 폴더와 같은 분류를 속성에 다시 기록하지 않는다. |
| 지식 저장소는 하나를 유지한다. | 공통 개념과 분야 사이의 링크를 한 이력 안에서 유지한다. 워크스페이스는 독립적인 Git remote·LLM 설정·구성원 집합이 필요할 때의 경계지만, 현재는 그런 요구가 없어 채택하지 않는다. |
| 숫자 분류와 별도의 검토 워크플로 속성은 도입하지 않는다. | 100–900 같은 숫자 분류는 분야 이름보다 읽기와 경로 선택을 복잡하게 만든다. 노트의 공통 속성은 [노트 메타데이터](note-metadata.md)를 따르며, 별도의 승인 상태·검토 이력 체계는 요구하지 않는다. |

[LLM Wiki의 아키텍처](https://llm-wiki.cmdspace.work/#architecture)에서는 개념·엔티티를 공유 정본 영역으로, MOC를 도메인 허브로, lint를 읽기 전용 구조 점검으로 채택했다. 노트 유형과 메타데이터의 채택 범위·적용 결정은 [노트 메타데이터](note-metadata.md)에 설명한다. lint의 실행과 결과 계약은 [개발 환경의 지식 구조 점검 CLI](development.md#지식-구조-점검-cli)에 설명한다.

[CMDS](https://system.cmdspace.work)에서는 Head Quarter(HQ) → 분야 진입점 → 노트의 계층적 탐색을 채택했다. 이 저장소에서는 HQ를 루트 `index.md`, 분야 진입점을 도메인 허브로 대응시킨다.

### 기존 저장소의 수동 전환

엔진은 기존 지식 저장소의 도메인 배치를 자동으로 이동하거나 전환하지 않는다. seed를 다시 적용하거나 루트 schema를 자동으로 덮어쓰지 않는 [초기화 정책](knowledge-repository.md#엔진의-로컬-저장소-초기화)에 따라, 기존 저장소의 담당자가 다음 순서로 일반 쓰기 요청을 통해 배치를 전환한다. 메타데이터 적용과 기존 속성의 전환은 [노트 메타데이터](note-metadata.md)를 따른다.

1. 현재 노트와 위키링크를 확인하고, 분야별 노트와 공유 정본의 목적지를 정한다. 기존 정본을 옮기며 같은 내용의 새 복사본을 만들지 않는다.
2. 필요한 도메인 폴더와 도메인 허브를 만든다. 공유 개념·엔티티의 목적지 폴더도 필요한 노트를 옮길 때 만든다.
3. 일반 쓰기 요청으로 노트를 목적지로 이동하고, 해당 노트를 참조하는 링크를 새 경로로 갱신한다. 기존 평평한 경로를 계속 사용하는 호환 노트나 재지정용 복사본을 남기지 않는다.
4. 루트 `AGENTS.md`의 분야 전용 규칙을 해당 `wiki/<domain>/AGENTS.md`로 옮긴 뒤 루트에는 공통 규칙만 남긴다. 예를 들어 논문 속성 절은 위의 연구 도메인 schema로 옮긴다.
5. 각 도메인 허브를 큐레이션하고 루트 `index.md`에 연결한다. 기존 개별 노트 진입점 중 도메인 허브가 대신할 것은 정리하고, 분야를 가로지르는 공유 진입점은 유지한다.
6. 쓰기 작업이 `main`에 반영된 뒤 읽기 전용 lint 보고서로 미분류 노트·허브 누락·링크 문제를 확인한다. 남은 문제는 별도의 정상 쓰기 요청으로 수정한다. lint 자체가 이동이나 수정을 수행하지 않는다.

- [작성 규칙](writing-rules.md)은 모든 도메인에 적용하는 공통 작성 기준을 설명한다.
- [노트 메타데이터](note-metadata.md)는 도메인 schema가 유지해야 하는 공통 속성과 엔진 자동 속성을 설명한다.
- [도니](agent.md)는 도메인 문맥과 편집 도구의 경계를 설명한다.
- [꿈꾸기](dreaming.md)는 누적된 도메인 배치와 허브 문제의 점검을 설명한다.
