# 지식 도메인 구조

하나의 지식 저장소 안에서 최상위 관심 영역별 노트와 공유 개념·엔티티를 구분하고, 대상 중심의 주제 폴더와 허브로 탐색한다.

## 배경

`wiki/` 아래에 노트를 평평하게 모으면 노트가 늘어날수록 조회 경로를 고르기 어렵다. 반대로 개발·마케팅·디자인 같은 직무나 학문을 최상위 분류로 삼으면 한 제품의 지식이 여러 곳에 흩어진다. 가져오기 배치나 원문 폴더를 그대로 옮기는 방식도 미래의 독자가 찾을 주제를 드러내지 못한다.

실제로 `wiki/돈이돼지 batch18/a/…`처럼 제품명에 배치 번호와 한 글자 분할 폴더가 섞이거나, `wiki/` 바로 아래에 노트가 30개 넘게 쌓이는 배치는 지식의 관심 대상과 조회 주제를 드러내지 못한다. 이 구조에서는 입력 처리 순서가 아니라 미래의 조회 경로를 기준으로 배치한다.

도메인은 제품·서비스, 프로젝트, 조직의 업무 영역, 생활·연구처럼 지속적으로 관심을 두는 최상위 관심 영역이다. `donidoeji`, `butamaru`, `health`, `research`가 그 예다. 저장소를 나누는 대신 관심 대상 아래에 주제를 묶고, 여러 도메인에서 재사용하는 지식은 공유 정본으로 연결한다.

## 내용

### 레이아웃

```text
index.md                     # 전체 허브
AGENTS.md                    # 도메인 중립 공통 schema
MEMORY.md
raw/
journal/
wiki/
  concepts/                  # 공유 개념 정본: 평면 또는 <topic>/<note>.md
  entities/                  # 공유 엔티티 정본: 평면 또는 <topic>/<note>.md
  <domain>/                  # donidoeji, butamaru, health, research 등
    index.md                 # 도메인 허브(MOC), 기존 위치 유지
    AGENTS.md                # 선택적인 도메인 schema, 기존 위치 유지
    <topic>/
      <note>.md              # 일반 노트의 최소·기본 깊이
      <subtopic>/            # 분리 조건을 만족할 때만 추가하는 마지막 단계
        <note>.md
```

도메인·주제·하위 주제를 포함한 `wiki/` 아래의 모든 폴더 이름은 2자 이상의 ASCII 소문자 kebab-case로 정한다. 소문자·숫자와 단어 사이의 하이픈을 사용하며, 한글·공백·밑줄·대문자를 사용하지 않는다. 노트 파일명에는 이 폴더 규칙을 적용하지 않으므로 `wiki/donidoeji/auth/로그인 정책.md`처럼 사람이 읽기 좋은 이름을 쓸 수 있다. `concepts`와 `entities`는 공유 영역이므로 도메인 이름으로 사용하지 않는다.

원문·첨부·일기·메모리와 git 저장소의 운영 역할은 [지식 저장소](knowledge-repository.md)에 설명한다. 이 구조는 완성된 지식의 배치 규칙이며, 빈 seed에 예시 도메인이나 가짜 노트를 미리 생성한다는 뜻은 아니다.

#### 단계별 분류 기준

| 단계 | 선택 기준 | 경로와 깊이 |
| --- | --- | --- |
| 도메인 | 제품·서비스, 프로젝트, 조직의 업무 영역, 생활·연구 등 오래 유지할 최상위 관심 대상을 고른다. | `wiki/<domain>/`이며 일반 노트를 바로 두지 않는다. |
| 주제 | 해당 대상 안에서 독자가 함께 조회할 안정적인 기능·책임·문제를 고른다. `crm`, `rewards`, `ios`, `onboarding`, `ads`가 그 예이며 적합한 기존 주제를 우선한다. 노트가 한 개여도 주제 폴더를 둔다. | `wiki/<domain>/<topic>/<note>.md`가 일반 노트의 최소이자 기본 경로다. |
| 하위 주제 | 한 주제 폴더의 직속 노트가 15개를 초과하고, 그중 같은 세부 주제로 묶을 노트가 3개 이상일 때만 분리한다. 두 조건을 모두 만족해야 한다. | `wiki/<domain>/<topic>/<subtopic>/<note>.md`까지 허용하며 더 깊게 나누지 않는다. |
| 공유 개념·엔티티 | 여러 도메인에서 재사용하거나 명백히 도메인 독립적인 정본을 둔다. 필요하면 하나의 주제 단계로 묶는다. | `wiki/concepts/<note>.md`, `wiki/entities/<note>.md` 또는 각 공유 영역의 `<topic>/<note>.md`를 허용하며 더 깊게 나누지 않는다. |
| 도메인 허브·schema | 탐색 진입점과 도메인 작성 규칙의 역할을 유지한다. | `wiki/<domain>/index.md`와 `wiki/<domain>/AGENTS.md`는 위치를 바꾸지 않으며 일반 노트의 최소 깊이에서 제외한다. |

과밀하다는 이유만으로 폴더를 기계적으로 나누지 않는다. 분리할 의미 있는 묶음이 없으면 노트의 중복·범위를 먼저 검토하고 허브로 조회 경로를 보완한다.

#### 폴더 분류로 쓰지 않는 축

다음 축은 도메인·주제·하위 주제와 공유 영역의 주제 등 모든 폴더 단계에서 사용하지 않는다. 입력의 흔적이나 메타데이터가 아니라 노트가 설명하는 대상을 기준으로 배치한다.

| 금지 축 | 예와 이유 |
| --- | --- |
| 가져오기 배치·분할 순서 | `batch-01`, `part-2`, `chunk-3`처럼 처리 순서를 경로로 쓰지 않는다. 재시도나 재수집에 따라 달라지며 같은 주제의 지식을 흩뜨린다. |
| 날짜·기간 | `2026`, `2026-10`, `2026-10-15`, 분기·월별 폴더로 나누지 않는다. 지식의 주제는 시점과 독립적이며 날짜는 제목·본문·메타데이터에 둔다. 날짜별 일기는 `wiki/`가 아닌 `journal/`의 별도 역할이다. |
| 도구·출처 | `notion`, `obsidian`, `slack`, `imports`처럼 지식을 가져온 수단으로 나누지 않는다. 출처는 `source`와 불변 `raw/`에 남긴다. 제품 자체가 관심 대상인 도메인이나 도구 자체를 설명하는 공유 엔티티와는 구분한다. |
| 노트 유형 | `guides`, `decisions`, `references`처럼 역할별로 나누지 않는다. 같은 주제의 절차·결정·자료가 흩어지므로 유형은 `type`으로 표현한다. |
| 상태 | `draft`, `in-progress`, `done`처럼 진행 상태로 나누지 않는다. 상태 변화만으로 경로와 링크가 흔들리며 일시적 운영 상태는 메모리나 본문에서 다룬다. |
| 작성자 | 사람별 폴더로 나누지 않는다. 공동 편집과 담당 변경에도 주제의 위치는 유지되어야 하며 작성자는 엔진 자동 속성으로 기록한다. |

타입·출처·작성자 속성의 표준은 [노트 메타데이터](note-metadata.md)를 따른다. 구조 점검은 이름 형식과 `batch`·`part`·`chunk` 뒤의 번호, `YYYY`·`YYYY-MM`·`YYYY-MM-DD` 형태의 날짜 폴더를 기계적으로 찾는다. 나머지 금지 축과 주제의 적합성은 내용을 읽고 판단한다.

### 노트 배치와 탐색

- 오래 유지할 노트는 정확히 하나의 정본 경로에 둔다. 특정 관심 대상의 결정·절차·기록은 위의 [단계별 분류 기준](#단계별-분류-기준)에 따라 도메인과 주제 아래에 두며, `wiki/`나 도메인 바로 아래에는 새 일반 노트를 만들지 않는다.
- 두 개 이상의 도메인에서 재사용하거나 명백히 도메인 독립적인 용어·개념은 `wiki/concepts/`에 둔다. 같은 조건의 사람·조직·도구·제품 노트는 `wiki/entities/`에 둔다.
- 같은 대상을 여러 도메인에서 참조해도 정본을 복제하지 않는다. 대상별 적용 맥락은 각 도메인 노트에 남기고 공유 정본에 위키링크로 연결한다. 예를 들어 캐시 무효화의 일반 원리는 공유 개념에, 도니돼지 서비스의 캐시 결정은 `wiki/donidoeji/cache/` 아래에 둔다.
- 새 도메인을 만들 때는 `wiki/<domain>/index.md`를 함께 만들고 루트 `index.md`에서 연결한다.
- 도메인 허브는 해당 관심 영역의 중요한 노트와 조회 경로를 큐레이션하는 MOC(Map of Content)다. 전체 파일 목록이나 본문 복사본이 아니다.
- 루트 `index.md`는 전체 허브로서 각 도메인 허브와 도메인을 가로지르는 공유 진입점을 연결한다. 탐색 흐름은 전체 허브 → 도메인 허브 → 주제별 노트이며, 공유 정본은 여러 도메인에서 직접 참조할 수 있다.

내용을 지식 단위로 나누고 저장 가치를 판단하는 절차는 [작성 규칙](writing-rules.md#저장-판단과-기존-노트-활용)을 따른다.

### 도메인 schema

루트 `AGENTS.md`에는 문체·사실성과 [노트 메타데이터](note-metadata.md)처럼 모든 도메인에 적용하는 공통 규칙만 둔다. 논문의 외부 식별자처럼 특정 관심 영역에만 필요한 규칙은 선택적인 `wiki/<domain>/AGENTS.md`에 둔다.

도니는 `wiki/<domain>/` 안에 쓰거나 편집하기 전에 해당 도메인의 `AGENTS.md`가 있으면 읽는다. 우선순위는 엔진의 실행·보안 지시, 해당 도메인의 schema, 루트 schema 순이다. 도메인 schema는 해당 관심 영역의 작성 관례를 확장하거나 재정의하며, 다른 도메인이나 `wiki/concepts/`, `wiki/entities/`에는 적용하지 않는다. 재정의로 ACL·불변 원문·민감 정보·사실성·정본 한 곳·공통 배치와 허브 규칙, 필수 메타데이터와 엔진 자동 속성의 소유 경계를 완화하지 않는다.

도메인 schema는 루트 schema와 같은 보호 대상이다. 서브에이전트의 소유 범위 경계는 [도니의 쓰기 서브에이전트](agent.md#쓰기-서브에이전트)에, 꿈꾸기의 허용 연산과 보호 경계는 [꿈꾸기](dreaming.md#코드로-강제하는-정리-경계)에 설명한다.

#### 연구 도메인 schema 예시

기존 공통 규칙의 논문 속성 절은 `wiki/research/AGENTS.md`로 옮기되, [노트 메타데이터](note-metadata.md)의 필수 속성과 공통 출처 형식을 유지한다. 아래는 그 파일의 내용 예시이며, 빈 저장소에 자동으로 생성하지 않는다.

```markdown
# 연구 도메인 작성 규칙

이 규칙은 wiki/research/ 안의 연구 노트에만 적용하며 루트 AGENTS.md의 공통 작성 규칙을 확장한다.

## 논문 노트의 속성

- 논문 읽기 상태를 frontmatter의 `status`나 `Read Status` 섹션으로 기록하지 않는다. 유지·관리 날짜는 엔진이 채우는 `date modified`를 따른다.
- 논문 원문과 정식 외부 식별자 URL은 공통 `source` 목록에 담는다. 도메인 전용 `pdf`, `arxiv` 속성은 별도의 외부 식별이 필요할 때만 추가하며, 공통 출처 속성을 대체하지 않는다.
- 프로젝트 방향을 나타내기 위한 버전이나 실험 단계 속성을 추가하지 않는다. 버전과 주장 범위는 제목이나 본문에 적는다.
- 도메인 전용 속성은 검색·필터링·출처 조회에 유용할 때만 추가한다. 공통 필수 메타데이터를 생략하거나 엔진 자동 속성을 직접 정하지 않는다.
```

### 권한과 검색

도메인은 별도 권한 모델이 아니다. 기존 [ACL 경로 접두사](access-control.md#규칙과-우선순위)로 `wiki/research/` 같은 범위를 지정하면 도메인별 읽기·쓰기 권한을 적용할 수 있다. 공유 개념·엔티티의 접근 범위는 그 공유 경로에 적용되는 ACL을 따른다. 루트 허브 링크가 대상 노트의 권한을 부여하지는 않는다.

검색의 기존 `folder` 필터에 `wiki/research/`를 지정하면 그 도메인으로 검색 범위를 좁힐 수 있다. 필터는 ACL을 대체하거나 우회하지 않는다. 도메인을 위해 RAG·API·MCP schema나 별도 색인을 추가하지 않으며, 검색과 인덱싱의 계약은 [RAG](rag.md)를 따른다.

### 설계 선택과 참고 구조

| 선택 | 이유 |
| --- | --- |
| 도메인은 폴더로 표현한다. | ACL·검색·인덱싱이 이미 경로 기반이다. [노트 메타데이터](note-metadata.md)와 도메인 경계를 구분하며, CMDS의 `CMDS:` 메타데이터처럼 폴더와 같은 분류를 속성에 다시 기록하지 않는다. |
| 직무·학문 우선이 아니라 관심 대상 우선으로 배치한다. | discipline-first 구조는 한 제품의 개발·마케팅·디자인 지식을 서로 다른 최상위 폴더에 흩뜨린다. subject-first 구조는 제품·프로젝트의 맥락을 한곳에 유지한다. 작은 대상은 직무 아래에 두다가 커지면 독립 도메인으로 승격하는 혼합 방식도 채택하지 않는다. 배치 규칙이 두 개가 되고 규모에 따라 정본 위치가 불안정해져 반복 이동과 링크 수정이 생기기 때문이다. |
| 지식 저장소는 하나를 유지한다. | 공통 개념과 관심 영역 사이의 링크를 한 이력 안에서 유지한다. 워크스페이스는 독립적인 Git remote·LLM 설정·구성원 집합이 필요할 때의 경계지만, 현재는 그런 요구가 없어 채택하지 않는다. |
| 숫자 분류와 별도의 검토 워크플로 속성은 도입하지 않는다. | 100–900 같은 숫자 분류는 관심 대상의 이름보다 읽기와 경로 선택을 복잡하게 만든다. 노트의 공통 속성은 [노트 메타데이터](note-metadata.md)를 따르며, 별도의 승인 상태·검토 이력 체계는 요구하지 않는다. |

[LLM Wiki의 아키텍처](https://llm-wiki.cmdspace.work/#architecture)에서는 개념·엔티티를 공유 정본 영역으로, MOC를 도메인 허브로, lint를 읽기 전용 구조 점검으로 채택했다. 노트 유형과 메타데이터의 채택 범위·적용 결정은 [노트 메타데이터](note-metadata.md)에 설명한다. lint의 실행과 결과 계약은 [개발 환경의 지식 구조 점검 CLI](development.md#지식-구조-점검-cli)에 설명한다.

[CMDS](https://system.cmdspace.work)에서는 Head Quarter(HQ) → 분야 진입점 → 노트의 계층적 탐색을 채택했다. 이 저장소에서는 HQ를 루트 `index.md`, 분야 진입점을 최상위 관심 영역의 도메인 허브로 대응시킨다.

### 기존 저장소의 수동 전환

엔진의 업데이트나 초기화는 기존 지식 저장소의 노트를 일괄 이동하거나 자동 마이그레이션하지 않는다. seed를 다시 적용하거나 루트 schema를 자동으로 덮어쓰지 않는 [초기화 정책](knowledge-repository.md#엔진의-로컬-저장소-초기화)을 유지한다. 새 쓰기에는 현재 배치 규칙을 적용하고, 기존 노트는 [꿈꾸기](dreaming.md#코드로-강제하는-정리-경계)에서 실행당 이동·삭제 합계 최대 20개 범위로 점진적으로 정리할 수 있다. 꿈꾸기의 ACL·보호 경로 경계를 넘는 일괄 전환은 수행하지 않는다. 담당자가 직접 전환할 때는 다음 순서로 일반 쓰기 요청을 사용한다. 메타데이터 적용과 기존 속성의 전환은 [노트 메타데이터](note-metadata.md)를 따른다.

1. 현재 노트와 위키링크를 확인하고, 각 노트가 설명하는 관심 대상과 주제를 정한다. 직무·학문 아래에 섞인 제품 지식과 배치·날짜 폴더를 대상 중심으로 재분류하고, 재사용할 공유 정본을 구분한다. 기존 정본을 옮기며 같은 내용의 새 복사본을 만들지 않는다.
2. 필요한 도메인·주제 폴더와 도메인 허브를 만든다. 폴더 이름과 깊이는 [단계별 분류 기준](#단계별-분류-기준)에 맞추며, 하위 주제는 직속 노트 15개 초과와 같은 세부 주제 3개 이상 조건을 모두 만족할 때만 만든다. 공유 개념·엔티티의 목적지도 옮길 노트가 있을 때 만든다.
3. 일반 쓰기 요청으로 노트를 목적지로 이동하고, 해당 노트를 참조하는 링크를 새 경로로 갱신한다. 기존 평평한 경로나 금지된 분류를 계속 사용하는 호환 노트·재지정용 복사본을 남기지 않는다.
4. 루트 `AGENTS.md`의 도메인 전용 규칙을 해당 `wiki/<domain>/AGENTS.md`로 옮긴 뒤 루트에는 공통 규칙만 남긴다. 예를 들어 논문 속성 절은 위의 연구 도메인 schema로 옮긴다. 기존 도메인 허브와 schema 자체는 주제 폴더로 내리지 않는다.
5. 각 도메인 허브를 큐레이션하고 루트 `index.md`에 연결한다. 기존 개별 노트 진입점 중 도메인 허브가 대신할 것은 정리하고, 도메인을 가로지르는 공유 진입점은 유지한다.
6. 쓰기 작업이 `main`에 반영된 뒤 [읽기 전용 lint 보고서](development.md#지식-구조-점검-cli)로 미분류·얕은 배치·깊이 초과·잘못된 폴더 이름·과밀·허브 누락·링크 문제를 확인한다. 남은 문제는 별도의 정상 쓰기 요청으로 수정한다. lint 자체가 이동이나 수정을 수행하지 않는다.
