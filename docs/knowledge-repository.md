# 지식 저장소
지식 저장소는 엔진과 분리된 git 저장소이며, main을 진실 원천으로 삼아 LLM Wiki 형식의 지식과 날짜별 일기를 관리한다.

## 배경
엔진 저장소의 `CONTEXT.md`와 `docs/`는 개발 문서이고, 지식 저장소는 엔진이 관리하는 위키 본문을 담는다. 두 저장소는 별개다. 지식 저장소의 기본 구조는 Karpathy의 LLM Wiki 패턴을 따르되, Obsidian에서 읽을 수 있는 노트 형식과 날짜별 일기를 반영한다.

## 내용
### 저장소 수와 원문 수집 범위
엔진이 관리하는 지식 저장소는 하나로 고정한다. 텍스트·파일·URL·PDF와 Obsidian·Notion 내보내기를 [수집](ingestion.md)할 수 있다. 원본은 내용 해시별 `raw/<sha256>/original/<filename>`에 불변으로 저장한다. ZIP에서 추출한 노트와 첨부는 `raw/<sha256>/extracted/<kind>/files/<vault-path>`에, 추출 본문이나 볼트 노트 목록과 출처는 `raw/<sha256>/imports/<importId>.md`에 저장한다. 같은 원본 경로는 덮어쓰지 않으며, 반복 수집은 git blob ID로 바이트가 같은 원본을 재사용한다. 일반 웹·채팅의 바이너리 첨부는 `assets/`에 저장하고, 원본 수집의 바이너리만 import 작업이 `raw/`에 기록한다.

### main과 GitHub 백업
지식 저장소의 기본 브랜치는 `main`이며, main이 진실 원천이다. GitHub는 사실상 백업으로 사용하고, push는 꿈꾸기 후 하루 한 번 수행한다. 서버 디스크를 잃으면 최대 하루치 변경이 사라질 수 있으며, 사용자는 이 손실 범위를 수용했다.

예를 들어 당일의 변경이 main에 들어갔더라도 다음 백업 push 전에는 GitHub에 없을 수 있다. GitHub의 상태가 곧 최신 지식이라고 가정하지 않는다. 변경이 main에 반영되는 절차는 [쓰기 흐름](write-flow.md)에, 백업 실행 절차는 [꿈꾸기](dreaming.md)에 기록한다.

### 엔진의 로컬 저장소 초기화
`KnowledgeModule`은 설정과 로그를 주입받는 비동기 제공자로 `KnowledgeRepo.open`을 한 번 호출하고 저장소 객체를 다른 Nest 모듈에 내보낸다. git 데이터 접근은 `src/knowledge/repo.ts`의 `KnowledgeRepo`가 담당하며, 격리 편집을 위한 `Worktree`는 Nest 제공자가 아닌 일반 객체로 유지한다.

주 클론은 `DATA_DIR/knowledge`에 두고, 작업 워크트리는 `DATA_DIR/worktrees/<작업 이름>`에 둔다. 작업 이름은 영문자·숫자로 시작하고 영문자·숫자·밑줄·하이픈만 포함하며, 브랜치는 `work/<작업 이름>`으로 만든다.

`KNOWLEDGE_REPO_URL`이 있으면 처음 실행할 때 해당 저장소를 클론하고, 없으면 `git init -b main`으로 로컬 전용 저장소를 만든다. 기존 저장소에 main이 있으면 그 브랜치를 사용하고, origin/main만 있으면 로컬 main을 만들며, 다른 브랜치에만 커밋이 있으면 그 HEAD에서 main을 만든다. 빈 저장소는 초기 커밋을 만들어 main이 항상 실제 커밋을 가리키게 한다.

빈 저장소의 초기 파일은 모듈 옆의 `knowledge/seed`에서 복사한다. 개발 실행에서는 `src/knowledge/seed`, 빌드 실행에서는 `dist/knowledge/seed`에 대응하며, 빌드 자산이 없고 소스가 함께 있으면 소스 경로도 확인한다. seed가 없거나 비어 있으면 지식 내용을 임의로 만들지 않고 `raw/`, `wiki/`, `journal/` 디렉터리만 만든 뒤 필요하면 빈 초기 커밋을 남긴다. git은 빈 디렉터리를 추적하지 않으므로 이 경우 새 워크트리에서는 파일을 쓸 때 부모 디렉터리를 만든다. 초기 커밋의 author와 committer는 모두 `GIT_BOT_NAME`과 `GIT_BOT_EMAIL`이고, 작업 식별자는 `initialize`, source는 `dreaming`, requester는 봇 이메일로 기록한다.

초기 seed는 도메인 중립 공통 `AGENTS.md`, [메모리 형식](#메모리-파일의-문맥-제공-규칙)을 갖춘 빈 `MEMORY.md`와 실제 노트가 없는 `index.md` 골격을 제공하며, `raw/`, `wiki/`, `wiki/concepts/`, `wiki/entities/`, `journal/`은 `.gitkeep`로 보존한다. 예시 도메인이나 존재하지 않는 노트의 링크는 만들지 않는다. 에이전트 이름은 도니로 기록한다. seed는 빈 저장소에만 복사하며 기존 루트 `AGENTS.md`를 자동으로 덮어쓰지 않는다. 기존 저장소에도 [엔진 구조 규칙의 우선순위](knowledge-domains.md#도메인-schema)는 즉시 적용하며, 기존 노트의 배치 전환은 [지식 도메인 구조의 수동 전환](knowledge-domains.md#기존-저장소의-수동-전환)을 따른다.

`GIT_SSH_KEY_PATH`가 있으면 clone과 push를 포함한 git 명령에 `GIT_SSH_COMMAND`를 적용한다. 지정 키만 쓰도록 `IdentitiesOnly=yes`를 설정하고, `StrictHostKeyChecking=accept-new`로 처음 보는 호스트 키는 등록하되 이미 등록된 키의 변경은 거부한다. git 자체는 셸 문자열이 아니라 `execFile` 인자로 실행한다. 원격 저장소가 없으면 push는 오류가 아니라 `{ pushed: false, reason }` 결과를 반환한다. 성공한 `pushMain()`은 실제 사용한 `remote`와 원격 main으로 보낸 `sha`를 함께 반환한다.

### 격리 편집과 복구
일반 워크트리는 생성 시점의 main 커밋에서 파생하고, 수정·삭제·이동은 해당 워크트리 안에서만 수행한다. 실패 작업을 재시도할 때는 보존한 작업 HEAD와 미커밋 편집에서 이어간다. 일반 커밋의 author는 요청자이고 committer의 기본값은 `도니 <dony@llmwiki.local>`다. 변경이 없는 `commit` 호출도 요청자를 기억하므로, main을 작업 브랜치로 병합하면서 자동으로 생기는 머지 커밋에도 요청자를 기록한다. 충돌 해결을 마친 `finishMerge`는 전달받은 요청자를 author로 기록한다.

`setCommitMetadata({ jobId, source, requester, client? })`는 일반 커밋뿐 아니라 자동 머지와 `finishMerge`에도 같은 작업 출처를 적용한다. main에 반영하는 모든 엔진 커밋은 `Wiki-Job`, `Wiki-Source`, `Wiki-Requester` trailer를 남기며 클라이언트가 있으면 `Wiki-Client`도 남긴다. 공용 `commitTrailers` 함수는 본문과 빈 줄로 구분하여 붙이는 trailer 블록을 만든다. 메타데이터를 지정하지 않은 저수준 워크트리 호출은 작업 브랜치 이름과 요청자 이메일을 사용하고 source를 `web`으로 기록한다.

머지는 먼저 작업 브랜치 안에서 `main`을 병합한다. 충돌이 나면 main은 그대로 두고 충돌 파일 목록을 반환한다. 작업 워크트리에서 충돌을 해결하고 머지 커밋을 만든 뒤, 주 클론의 main을 작업 브랜치로 `--ff-only` 전진시킨다. main이 이미 갈라졌다면 fast-forward는 실패한다. 저장소 객체 사이에서도 공유하는 프로세스 단위 Promise 큐가 머지 락을 직렬화하며, 락 안의 작업이 실패해도 다음 작업에 락을 넘긴다. 호출자는 최신 main 병합부터 fast-forward와 인덱스 동기화까지 이 락 안에서 수행한다.

부팅 시 `open`은 전용 워크트리 디렉터리의 남은 작업 워크트리와 `work/` 브랜치를 정리하고 git 워크트리 메타데이터를 prune한다. 정리 전에 각 작업 브랜치 HEAD와 남은 워크트리의 미커밋 편집을 보존하며 main은 바꾸지 않는다. 정상 실패 처리의 `preserveFailed(jobId)`도 같은 보존 경로를 사용한다. 실패 HEAD·WIP 참조와 재시도 복원 규칙은 [쓰기 흐름의 실패 복구](write-flow.md#요청자-추적과-실패-복구)에 설명한다. `open`은 실행 중인 작업을 다시 여는 함수가 아니라 부팅 초기화 함수다.

### 파일 경계와 이력 조회
모든 파일 경로는 저장소 상대 경로다. 절대 경로, Windows 절대 경로, 역슬래시, NUL, `..` 세그먼트와 `.git` 세그먼트를 거부한다. 워크트리 파일 연산은 기존 경로 구성 요소의 실제 경로를 확인하여 외부로 향하는 심볼릭 링크와 git 메타데이터로 향하는 링크를 거부하며, 끊어진 심볼릭 링크도 거부한다. 내부의 일반 파일로 향하는 링크는 워크트리에서 읽을 수 있다.

main과 과거 커밋의 읽기는 작업 디스크 파일을 직접 읽지 않고 ref를 커밋 SHA로 확정한 뒤 `git ls-tree`와 `git show`로 수행한다. 따라서 아직 머지하지 않은 편집은 읽기에 나타나지 않는다. 저장소의 파일 목록은 해당 ref에서 추적하는 `.md` 일반 파일만 반환하며, 심볼릭 링크는 목록에서 제외하고 파일 읽기도 거부한다. 워크트리의 목록은 충돌 검증과 편집을 위해 아직 추적하지 않는 파일과 마크다운 이외의 일반 파일도 포함한다.

`fileObjectId(path, ref='main')`는 ref를 확정한 뒤 트리 메타데이터만 조회하여 일반 파일의 Git blob OID를 반환한다. 바이너리를 UTF-8로 디코딩하거나 내용을 git 출력으로 읽지 않으므로 대용량 불변 원본의 중복 수집 및 바이트 동일성 검사에 사용한다. 디렉터리·없는 경로·서브모듈은 null이고 심볼릭 링크는 거부한다. 호출자는 원본 바이트의 Git blob 해시와 OID를 비교하여 불변 원본의 일치를 확인한다. 워크트리의 `hasFile(path)`도 파일 메타데이터만 확인하며 기존 경로와 같은 저장소·심볼릭 링크 경계 규칙을 적용한다.

`resolveRef`는 ref를 실제 커밋 SHA로 확정한다. 이력의 `sinceSha`는 그 커밋을 제외한 이후 변경을 반환하고, `before`(기존 `beforeSha`도 지원)는 페이지 커서 커밋을 제외한 조상 커밋을 반환한다. 두 조건은 함께 사용할 수 있다. `log(path?, { ref, follow, limit, before })`의 `ref`는 조회 시작 커밋을 고정하며 생략하면 main을 사용한다. 인덱서가 이미 읽은 HEAD를 지정하면 이후 main 변경이 해당 스냅샷의 이력에 섞이지 않는다. `follow: true`이면 이동 전 이력까지 추적하며 각 커밋에 당시 `path`와 이동 시 `oldPath`를 반환한다. 페이지 경계가 이동 커밋을 지나도 이전 경로를 유지한다. 기본 limit는 50이고 `null`은 제한 없는 이력 조회다.

`compare(base, head, path?)`는 확정된 두 SHA와 변경 파일, 바이너리도 포함하는 patch를 반환한다. 커밋 상세 `show(sha, parent=1)`는 선택한 부모와 비교하며, 초기 커밋은 빈 트리와 비교한다. 존재하지 않는 부모 번호는 400 오류다. 변경 파일은 추가·수정·삭제·이동을 구분하고 이동은 이전 경로와 새 경로를 함께 반환한다. 커밋에는 author 외에도 `committerName`, `committerEmail`, `committedAt`, `trailers`를 제공한다. `blame(path, ref)`는 확정된 ref와 연속 줄별 범위를 반환하며 같은 커밋의 인접 줄을 묶고 author·날짜·요약 및 `Wiki-Job`/`Wiki-Source`의 출처를 제공한다. git 출력은 NUL 구분자로 해석하여 경로에 탭·개행·한글이 있어도 이동과 커밋 메시지를 섞지 않는다.

워크트리의 `write`는 문자열과 `Buffer`를 받아 바이너리를 변형하지 않는다. `revert(sha, paths?)`는 현재 편집을 index에 올린 뒤 대상 커밋의 첫 부모 기준 바이너리 patch를 역방향으로 index와 파일에 적용하므로 이후 독립 편집을 유지하면서 전체 또는 선택 경로만 되돌릴 수 있다. 머지 커밋도 첫 부모 기준이며 초기 커밋은 빈 트리 기준이다. 자동 적용이 충돌하면 설명을 포함한 `status: 409`, `code: revert_conflict` 오류를 내고 main을 바꾸지 않는다. `diff()`는 현재 파일 변경을 index에 올려 변경 파일과 바이너리 patch를 반환한다. 되돌리기 미리보기는 격리 워크트리에서 이 두 메서드를 호출한 뒤 워크트리를 폐기한다.

모든 git 실행에는 `-c core.quotePath=false`를 붙인다. git은 기본값에서 한글 같은 비ASCII 경로를 `"a/wiki/\355\225\234..."`처럼 8진수로 이스케이프하므로, 이 설정이 없으면 웹 커밋 상세의 diff 머리글이 읽을 수 없는 경로로 보인다. 저장소나 사용자 git 설정에 `core.quotePath=true`가 있어도 엔진 출력은 항상 UTF-8 경로를 그대로 쓴다.


### 디렉터리 레이아웃
다음은 지식 저장소 루트의 구조다.

```text
.
├── raw/
│   └── <sha256>/
│       ├── original/<filename>
│       ├── extracted/<kind>/files/<vault-path>
│       └── imports/<importId>.md
├── assets/          # 일반 첨부 바이너리
├── wiki/
│   ├── concepts/
│   ├── entities/
│   └── <domain>/
│       ├── index.md
│       ├── AGENTS.md # 선택적인 도메인 schema
│       └── <topic>/  # 주제별 노트, 깊이 규칙은 지식 도메인 구조 참조
├── index.md
├── journal/
│   └── YYYY-MM-DD.md
├── MEMORY.md
└── AGENTS.md
```

- `raw/<sha256>/`는 불변 원문 파일과 추출 마크다운을 담는다. 원문 수집 경로와 해시 규칙은 [수집](ingestion.md)을 따른다.
- `wiki/`는 도니가 유지하는 노트를 담으며, [노트 메타데이터](note-metadata.md)의 frontmatter와 태그, 위키링크를 사용해 Obsidian 볼트로 열 수 있다. 도메인과 공유 영역의 배치, 전체·도메인 허브의 역할은 [지식 도메인 구조](knowledge-domains.md#노트-배치와-탐색)를 따른다.
- `journal/YYYY-MM-DD.md`는 꿈꾸기가 날짜별로 쓰는 일기다. LLM Wiki 표준의 `log.md`를 대신하며, 세부 변경 이력은 git 커밋 이력이 담는다.
- `MEMORY.md`는 [메모리 파일의 문맥 제공 규칙](#메모리-파일의-문맥-제공-규칙)을 따르는 파일이다.
- 지식 저장소 안의 schema는 도니의 [작성 규칙](writing-rules.md)을 담으며, 루트와 도메인 schema의 적용 범위는 [지식 도메인 구조](knowledge-domains.md#도메인-schema)를 따른다. 엔진 저장소의 작업 규칙 파일과 구분한다.

Obsidian 규칙의 LiveSync는 사용하지 않으며, git 동기화로 대체한다. 날짜별 정리 내용은 `journal/YYYY-MM-DD.md`에서 읽고, 개별 변경은 git 커밋 이력으로 확인한다.

### 메모리 파일의 문맥 제공 규칙
`MEMORY.md`는 다음 작업에도 필요한 도니 전용 운영 문맥이며, 전체 공용 파일 하나를 유지한다. 쓰기·꿈꾸기·웹 질의응답과 초안 제안에서 사용하는 도니의 기본 문맥에 항상 넣으며, 요청자의 읽기 권한을 우회하지 않는다. 항상 전달하는 문맥이므로 장기 지식 본문이 아니라 짧은 작업 관례·진행 상태·참조 포인터만 담는다.

`src/knowledge/memory.ts`가 `MEMORY_PATH = 'MEMORY.md'`, `MEMORY_BUDGET_CHARS = 4000`, `MEMORY_SECTIONS = ['작업 관례', '진행 중', '참조']`를 정의한다. `memoryIssues(content): string[]`는 메모리 내용의 형식과 예산 위반을 반환한다. 파일 전체를 유니코드 코드 포인트로 세어 4,000자 이내로 유지한다. 제목·줄바꿈·공백·링크도 예산에 포함하며, 바이트 수나 UTF-16 코드 단위 수로 세지 않는다.

메모리의 2단계 제목은 아래 세 개만 정확히 한 번씩 이 순서로 둔다. 항목이 없으면 해당 절을 비워 두며, 다른 `##` 절을 추가하지 않는다.

| 절 | 기록 내용 |
| --- | --- |
| `## 작업 관례` | 사용자의 정정·선호와 반복되는 정리 결정을 다음 작업에서 적용할 짧은 규칙으로 기록한다. |
| `## 진행 중` | 현재 상태와 다음 행동을 짧게 적고, 각 항목에 `YYYY-MM-DD` 날짜와 관련 노트나 작업을 찾을 포인터를 함께 둔다. |
| `## 참조` | `[[path]] — 이유` 형식으로 다음 작업에서 다시 읽을 노트와 그 이유를 적는다. |

쓰기 작업은 사용자가 기존 이해를 정정하거나 선호를 밝히거나 반복해서 적용할 정리 결정을 내리면 이 파일을 갱신한다. 일회성 대화 진행 설명은 남기지 않으며, 오래 유지할 사실은 정본 노트에 쓰고 메모리에는 필요한 포인터만 둔다. 비밀값과 자격 증명은 저장하지 않고 개인정보는 [민감 정보 규칙](writing-rules.md#민감-정보)을 따르며, 대화·원문·노트 본문을 덤프하지 않는다.

꿈꾸기는 도니를 호출하는 매 실행마다 메모리를 검토해 중복을 합치고 오래되거나 완료된 상태를 제거하며, 세 절의 형식과 전체 예산을 유지하도록 통합한다. 계속 보존할 상세 지식은 정본 노트로 옮기고 필요한 참조만 남긴다. 변경이 필요하지 않으면 메모리를 불필요하게 다시 쓰지 않는다. 메모리의 형식·예산 위반은 도니 실행을 고르는 구조 신호에 포함하며, 새 입력·구조 신호·순환 점검 대상이 모두 없는 유휴 실행은 [꿈꾸기의 실행 선택](dreaming.md#실행-시각과-입력)에 따라 도니를 호출하지 않는다.

### LLM Wiki 표준과의 대응
다음 표는 표준의 각 구성 요소를 이 레이아웃에서 어디에 두는지 설명한다.

| LLM Wiki 표준 구성 요소 | 지식 저장소 위치 | 대응 방식 |
| --- | --- | --- |
| raw sources | `raw/` | 불변 원문 소스를 보관한다. |
| wiki | `wiki/` | 도니가 유지하는 노트를 보관한다. |
| index | 루트·도메인의 `index.md` | 전체·최상위 관심 영역별 탐색 진입점을 제공한다. |
| log | `journal/YYYY-MM-DD.md` | `log.md` 대신 날짜별 일기를 쓰고, 세부 변경 이력은 git 커밋 이력으로 남긴다. |
| schema | 루트·도메인의 `AGENTS.md` | 공통·도메인별 작성 규칙을 담는다. |
