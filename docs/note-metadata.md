# 노트 메타데이터 표준

위키 노트의 의미·별칭·출처를 풍부한 frontmatter로 기록하고, 작성자와 날짜는 엔진이 결정한다.

## 배경

기존의 최소 frontmatter 정책은 `updated`와 선택적인 `importance`만 강조하고 `related`를 금지했다. 도메인이 늘어나면서 제목과 본문만으로 노트의 역할을 분류하거나 다른 언어·약어로 찾기 어려워졌다. 같은 폴더 안에서도 개념 설명, 결정, 절차와 참고 자료를 구분하고 전체 본문을 읽기 전에 관련성을 판단할 수 있어야 한다.

[LLM Wiki](https://llm-wiki.cmdspace.work)와 [CMDS](https://system.cmdspace.work)는 `type`, `aliases`, `description`, `author`, `date created`, `date modified`, `tags`의 일곱 필수 속성을 표준화한다. 필드 정의는 [LLM Wiki의 frontmatter](https://llm-wiki.cmdspace.work/docs/#frontmatter)와 [CMDS의 공식 Frontmatter Standard](https://github.com/johnfkoo951/cmds-system-files/blob/main/rules/frontmatter-standard.md#L7-L20)에 공개되어 있다. 이 공통 기반을 채택하되, 도메인 분류는 기존 폴더 구조로 유지하고 지식의 의미와 출처를 표현하는 속성을 보완한다.

## 내용

### 적용 범위와 필드

`wiki/` 아래의 모든 Markdown 노트에 적용하며 `.MD` 확장자도 포함한다. `AGENTS.md` 작성 규칙 파일은 제외한다. 도메인 허브도 노트이므로 같은 표준을 따른다. `raw/`, `journal/`, 루트 `index.md`·`MEMORY.md`·`AGENTS.md`에는 이 표준을 강제하지 않는다. 도메인과 공유 정본의 경로는 [지식 도메인 구조](knowledge-domains.md)에 설명한다.

| 필드 | 필수 여부·형식 | 의미와 작성 기준 |
| --- | --- | --- |
| `type` | 필수 문자열, 아래 유형 어휘 중 하나다. | 노트가 수행하는 역할이다. 도메인 이름이 아니다. |
| `aliases` | 필수 문자열 배열, `[]`도 허용한다. | 다른 이름, 약어, 한국어·영어 번역을 기록한다. 제목을 기계적으로 복제하지 않는다. |
| `description` | 필수, 비어 있지 않은 문자열, 300자 이하다. | LLM과 검색을 위한 한국어 1~2문장 요약이다. 노트가 설명하는 대상과 핵심 내용을 구체적으로 적는다. |
| `author` | 필수, 비어 있지 않은 문자열 배열, 엔진 자동 속성이다. | 요청자의 표시 이름을 기록한다. 이름이 없으면 이메일을 사용하며, 사람 요청자가 없으면 봇 이름을 사용한다. |
| `date created` | 필수 `YYYY-MM-DD`, 엔진 자동 속성이다. | 노트 생성 날짜다. |
| `date modified` | 필수 `YYYY-MM-DD`, 엔진 자동 속성이다. | 노트 내용을 바꾼 날짜다. 생성 날짜보다 이를 수 없다. |
| `tags` | 필수 문자열 배열, 한 개 이상이다. | 영어 소문자 kebab-case의 넓고 재사용 가능한 주제다. 태그 선택 기준은 [작성 규칙](writing-rules.md#태그-정책)에 둔다. |
| `related` | 선택 문자열 배열, 각 값은 `"[[노트]]"`다. | 밀접한 관련 노트의 명시적 연결이다. 본문 링크를 없애거나 모든 이웃을 자동 나열하는 속성이 아니다. |
| `source` | 선택 문자열 배열, 각 값은 위키링크 또는 `http(s)` URL이다. | 원문·논문·자료의 출처다. 가져온 원문에서 만든 지식에는 raw 출처 링크를 적극적으로 남긴다. |
| `confidence` | 선택, `high`, `medium`, `low` 중 하나다. | 지식의 근거 강도다. 운영 중요도와 구분한다. |
| `importance` | 선택, `high`, `medium`, `low` 중 하나다. | 운영 규칙이나 검토 기준의 중요도다. 기존 속성을 유지한다. |
| 도메인 전용 추가 속성 | 선택, 도메인 schema가 정의한다. | `arxiv`, `pdf`처럼 실제 조회와 출처 확인에 유용한 속성을 허용한다. 공통 필수 속성을 생략하거나 금지 속성을 되살리는 용도가 아니다. |

`domain`, `category`, `status`, `updated`는 사용하지 않는다. 도메인은 폴더로 표현하며 `updated`의 역할은 `date modified`로 대체한다. 알 수 없는 추가 속성은 삭제하거나 일괄 거절하지 않는다.

### 유형 어휘와 배치

| `type` | 용도 |
| --- | --- |
| `hub` | 주요 노트와 조회 경로를 큐레이션하는 허브·MOC다. |
| `concept` | 재사용 가능한 개념·용어의 정본 설명이다. |
| `entity` | 사람·조직·도구·제품처럼 식별 가능한 대상의 정본이다. |
| `guide` | 절차·운영 방법·체크리스트를 설명한다. |
| `decision` | 결정과 채택 이유, 대안 및 적용 범위를 기록한다. |
| `reference` | 논문·문서·자료를 이해하고 다시 참조하기 위한 노트다. |
| `project` | 특정 프로젝트의 지속적인 맥락·목표·설계를 기록한다. 임시 진행 상태를 저장하는 유형은 아니다. |
| `note` | 다른 유형보다 일반 노트가 적합한 지식이다. 분류를 생략하기 위한 기본값이 아니다. |

`wiki/concepts/` 아래는 `concept`, `wiki/entities/` 아래는 `entity`, `wiki/<domain>/index.md`는 `hub`여야 한다. 그 밖의 도메인 노트는 목적에 맞는 유형을 선택한다. `type`이 `reference`인 연구 노트와 `guide`인 개발 노트도 각각 관심 대상의 도메인·주제 폴더에 두므로 `domain` 속성이 필요하지 않다. 배치와 깊이는 [지식 도메인 구조](knowledge-domains.md#레이아웃)를 따른다.

### 엔진 자동 속성

`author`, `date created`, `date modified`는 LLM이 계산하는 정보가 아니다. 모델이 요청자 이름을 추측하거나 날짜를 오래된 문맥에서 가져오면 메타데이터가 본문과 무관하게 틀릴 수 있으므로 쓰기 파이프라인에서 결정적으로 채운다. 도니는 의미를 판단해야 하는 유형·별칭·설명·태그·출처에 집중한다. 날짜는 일기와 같은 한국 표준시 기준의 `YYYY-MM-DD`를 사용하며, 사람 요청자가 없는 작업은 `GIT_BOT_NAME`을 사용한다. 기본 봇 이름은 `도니`다.

엔진은 커밋 직전 실제 내용이 추가·변경된 메타데이터 대상만 처리한다. 삭제된 노트와 내용 변화 없는 이름 변경은 속성을 다시 쓰지 않으며, 아무 변경도 없는 작업은 날짜 갱신만을 위한 커밋을 만들지 않는다. 정상적인 본문과 엔진 소유가 아닌 YAML 속성·주석은 그대로 보존하고 엔진 자동 속성만 갱신한다. 해석할 수 없는 YAML을 추측해서 재작성하지 않는다.

사람 요청자가 있으면 기존 작성자 목록을 보존하면서 요청자의 `users.name` 또는 이메일을 없을 때만 추가한다. 꿈꾸기처럼 사람 요청자가 없으면 기존 작성자를 유지하며 목록이 비었거나 없을 때만 봇 이름을 채운다. `date created`는 없을 때 오늘 날짜로 채우고 기존 값은 보존한다. `date modified`는 내용 변경마다 오늘 날짜로 갱신한다. 기존 날짜가 없는 노트의 첫 보완에서 과거 생성일을 임의 추정하지 않는다. 이 날짜 기준은 `TZ_DREAM`의 스케줄러 시간대와 독립적이다.

옛 `author`가 문자열이면 그 이름을 보존한 배열로 정규화한다. 작성자 값이 유효한 문자열이나 문자열 배열이 아니면 요청자 또는 봇 이름의 배열로 대체한다. 충돌 해결 커밋은 최신 main과 비교해 실제로 달라진 노트만 처리하므로 동시에 들어온 다른 작업의 노트에 이번 요청자의 이름·날짜를 덧씌우지 않는다.

### 검증과 복구

공통 검증기는 필수 속성의 존재·형식, 유형 어휘와 배치, 설명 길이, 태그 형식, 날짜 순서, 선택 속성의 형식과 금지 속성을 검사한다. 한국어 설명의 정확성, 태그의 재사용 가치와 근거의 충분함은 작성 판단에 해당하며 형식 검증만으로 보장하지 않는다. `source`는 선택 속성이므로 가져온 지식에 누락되었다는 이유만으로 형식 오류가 되지는 않지만, 도니는 원문 출처를 기록해야 한다.

일반 에이전트 쓰기는 첫 커밋 뒤 변경 노트를 검증한다. 엔진 자동 속성을 제외한 문제가 있으면 경로와 `{ field, message }` 목록을 도니에게 전달하고 한 번의 제한된 보완 실행을 수행한다. 최대 8턴이며 해당 오류 노트의 `read_file`·`write_file`만 허용하고 커밋·이동·삭제·서브에이전트 도구는 주지 않는다. 보완 결과를 엔진 자동 속성과 함께 다시 커밋하고 재검증한다. 머지 충돌 해결 뒤에는 최종 내용을 재검증하지만 두 번째 보완 실행을 만들지는 않는다.

메타데이터 품질 오류만으로 사용자가 제출한 지식을 버리지 않는다. 보완 실행 실패나 남은 형식 문제는 지식 반영을 막지 않고, 성공 작업의 `done` 단계 이벤트와 완료 로그에 `metadataIssues: [{ path, issues: [{ field, message }] }]`로 남긴다. 보완 시작·종료·오류는 `editing` 단계의 `metadataRepair`로 기록한다. YAML 자체가 잘못된 경우도 `frontmatter` 문제로 보고한다. 직접 편집은 LLM 보완 실행 없이 엔진 자동 속성만 채우며, 꿈꾸기는 기존 저장소의 정리 후보를 통해 의미 속성을 보완한다. ACL·불변 원문·충돌·링크 안전 경계 같은 다른 실패 조건을 완화하는 규칙은 아니다.

### 기존 저장소의 메타데이터 정리

기존 저장소 전체를 즉시 다시 쓰거나 schema를 자동 덮어쓰지 않는다. 일반 쓰기로 건드리는 노트는 새 표준을 따르고, 손대지 않은 노트의 누락과 옛 속성은 읽기 전용 lint와 꿈꾸기의 정리 후보로 다룬다. 제목·본문·실제 연결에서 근거를 얻어 메타데이터를 채우며 알 수 없는 별칭이나 출처를 만들어내지 않는다. 도메인 배치와 허브, 깨지거나 모호한 링크를 먼저 정리한 뒤 이미 편집한 노트와 남은 메타데이터 후보를 보완한다. 상한 때문에 남긴 메타데이터 작업은 일기에 기록하지 않으며 다음 실행의 구조 신호로 다시 계산한다. lint의 실행 계약은 [개발 환경](development.md#지식-구조-점검-cli), 후보 선택과 실행은 [꿈꾸기](dreaming.md#모드와-구조-신호)에 둔다.

### 검색과 연결에서의 역할

`description`은 본문을 열기 전에 노트의 범위와 관련성을 판단하는 요약이고, `aliases`는 약어와 번역 표현으로 같은 지식을 찾는 통로다. `type`은 저장 위치를 바꾸지 않고 노트의 역할로 검색을 좁힌다. `related`와 `source`의 위키링크는 본문 링크와 함께 명시적 연결에 참여하며, 외부 URL 출처는 위키 그래프 간선이 아니다. 검색 채널·결과 필드·필터·링크 해석·권한 적용의 자세한 계약은 [RAG](rag.md)에 둔다. 메타데이터가 접근 권한을 부여하거나 숨겨진 노트를 공개하지는 않는다.

### 참고 체계에서 채택한 것과 제외한 것

일곱 공통 필수 속성, 노트의 역할을 나타내는 유형, 별칭·설명으로 탐색을 돕는 방식과 명시적인 관련 노트·출처를 채택한다. 필드 이름을 채택한다는 것이 각 참고 체계의 모든 값과 운용 규칙을 복제한다는 뜻은 아니다. 이 엔진은 한국어 설명, 요청자 표시 이름의 작성자 배열, 날짜 단위의 엔진 자동 속성과 위의 여덟 유형을 사용한다. 모든 속성을 많이 채우는 것이 목적은 아니며 본문에서 확인할 수 있는 내용을 정확히 기록한다.

CMDS의 [숫자 분류 체계](https://github.com/johnfkoo951/cmds-system-files/blob/main/rules/directory-structure.md#L145-L164)와 이를 참조하는 선택 속성 `CMDS:`는 채택하지 않는다. 원래 체계가 일반 `category` 필드를 필수로 요구한다는 뜻은 아니다. 이 엔진에서도 별도 category 필드를 도입하지 않는다. 이미 읽을 수 있는 도메인 폴더가 있고 경로 기반 ACL과 검색 범위가 있으므로 별도 숫자 체계를 중복 관리하지 않는다. 관심 대상 중심의 배치 기준은 [지식 도메인 구조](knowledge-domains.md#레이아웃)를 따른다. LLM Wiki의 [검증 상태](https://llm-wiki.cmdspace.work/docs/#v5-verification) 속성인 `verificationStatus`, `claimType`과 [탐색 상태](https://llm-wiki.cmdspace.work/docs/#ingest)인 `explored`도 의무화하지 않는다. 현재 엔진에는 해당 상태를 일관되게 판정·갱신하는 절차가 없으며, 검증되었다는 인상을 주는 속성을 형식만 채우지 않는다. `status`도 공통 노트 메타데이터로 도입하지 않는다. 쟁점과 적용 범위는 본문에 설명하고 근거 강도는 선택 속성 `confidence`로 표현한다.

### 예시

다음은 `wiki/concepts/kv-cache.md`의 저장된 frontmatter 예시다. 작성자와 날짜는 요청자 홍길동의 쓰기에 엔진이 채운 결과다.

```yaml
---
type: concept
aliases: [KV cache, 키값 캐시]
description: "KV 캐시는 자기회귀 추론에서 이전 토큰의 키와 값을 재사용해 반복 계산을 줄이는 기법이다. 메모리 비용과 추론 속도의 관계를 설명한다."
author: [홍길동]
date created: 2026-10-10
date modified: 2026-10-10
tags: [kv-cache, inference]
related: ["[[wiki/concepts/attention]]"]
source: ["https://arxiv.org/abs/1706.03762"]
confidence: high
---
```

다음은 `wiki/llmwiki-engine/backup/백업 절차.md`에 가져온 자료를 반영한 예시다. `raw/<sha>/imports/<id>` 형태의 링크에는 실제 수집 SHA와 import ID를 사용한다.

```yaml
---
type: guide
aliases: [백업 절차, Backup procedure]
description: "지식 저장소와 SQLite를 함께 백업하고 복원 전 무결성을 확인하는 절차다. 운영자가 점검해야 할 백업 범위와 복구 순서를 설명한다."
author: [홍길동]
date created: 2026-10-09
date modified: 2026-10-10
tags: [backup, maintenance]
related: ["[[wiki/llmwiki-engine/backup/복구 결정]]"]
source: ["[[raw/4f9a217ca54826e1b33fb28b0f6ae933469daf1cf86441cda5871f410720e153/imports/7Qx]]", "https://www.sqlite.org/backup.html"]
importance: high
---
```

허브는 `type: hub`로 해당 관심 영역의 조회 경로를 설명하며, 쓸 별칭이 없는 노트도 `aliases: []`를 명시한다. 예시의 경로를 실재 노트나 원문이 없는 상태에서 그대로 복사하지 않는다.
