# 운영 상태와 관측
엔진은 생존·준비 상태와 보호된 관측 정보를 제공하며, 관리자는 운영 사이드바·설정·명령 팔레트에서 같은 실행 계약으로 수동 작업을 수행한다.

## 배경
프로세스가 HTTP에 응답하는 것과 지식 저장소·검색 인덱스를 사용할 준비가 된 것은 다르다. 생존 확인을 외부 API나 인덱싱 실패에 묶으면 불필요한 재시작이 발생하므로 `/healthz`와 `/readyz`를 구분한다. 운영 지표는 사용자 작업 내용을 담지 않으며 공개 접근을 허용하지 않는다.

## 내용
### 생존과 준비 상태
- `GET /healthz`는 기존과 같이 `200 {"ok":true}`를 반환한다. 로그인 없이 호출할 수 있다.
- `GET /readyz`는 SQLite의 `SELECT 1`, 지식 저장소 `main` HEAD 조회, 최초 인덱싱 완료 상태, 비동기 인덱서 상태의 `lastError`를 확인한다.
- 최초 인덱싱이 `pending` 또는 `error`이거나 DB·git·인덱서 확인이 실패하면 `503`을 반환한다. 모두 통과해야 `200`이다.
- 성공 응답은 `{ ok: true, initialIndex: "ready", checks: { database, repository, index } }`다. 자동 실행을 끈 서버는 초기 색인을 생략하고 `initialIndex: "skipped"`로 응답하며 나머지 준비 확인은 그대로 수행한다. 실패 응답은 공통 오류 형식인 `{ error: { code: "service_unavailable", message: "Internal server error" } }`이며 내부 확인 결과·오류 문자열·파일 경로를 포함하지 않는다.
- 최초 인덱싱 성공은 `initialIndex: "ready"`, 실패는 `"error"`로 기록하고 실패 로그를 남긴다. 최초 실패 후에는 원인을 해결하고 엔진을 재시작한다. 최초 준비 이후 발생한 인덱서 오류는 정상 동기화로 해소되면 준비 상태도 회복된다.
- 임베딩 API 키가 없는 키워드 검색 모드는 그 자체로 준비 실패가 아니다. 최초 동기화 중에는 준비되지 않았지만 이후 증분 동기화가 진행 중이라는 이유만으로 준비 상태를 내리지 않는다.

컨테이너 생존 확인에는 `/healthz`를 쓰고 트래픽 수신 전 확인에는 `/readyz`를 쓴다. 두 경로와 `/metrics`는 Next 화면이 아니라 Nest 컨트롤러가 처리한다.

### 자동 실행 중지
`JOBS_AUTOSTART=false`는 서버가 사용자 요청 없이 OpenAI 비용을 쓰지 않도록 자동 실행을 중지한다. 기본값은 `true`이며 환경 변수의 검증과 복사 DB의 격리 절차는 [개발 환경](development.md#환경-변수)에 기록한다.

- 시작 시 대기 에이전트 작업의 복구·큐 처리와 대기 중인 직접 저장·되돌리기의 자동 재개를 시작하지 않는다. 새 에이전트 쓰기·가져오기·에이전트 재시도 요청은 작업을 접수해 `queued`로 유지하며, 이 요청의 성공은 실제 지식 저장 완료를 뜻하지 않는다. 큐 처리는 `JOBS_AUTOSTART=true`로 다시 시작할 때 재개한다.
- 꿈꾸기 cron과 초기·주기 인덱스 동기화를 시작하지 않는다. 가져오기 상태·재시도 연결을 복구하는 비용 없는 재조정은 유지하며, 가져오기 통합 작업이 접수되어도 큐가 자동 실행하지 않는다. 저장된 색인은 그대로 사용하므로 최신 지식과 다를 수 있다.
- 채팅·검색·노트 제안, 직접 노트 저장·되돌리기와 관리자 꿈꾸기·재색인 수동 실행은 그대로 동작한다. 이 스위치는 모든 OpenAI 호출을 차단하는 방화벽이 아니며 직접 실행한 요청에는 비용이 발생할 수 있다.
- 관리자 `GET /api/admin/ops`는 `jobsAutostart`를 반환한다. 운영 설정의 개요는 값이 `false`이면 자동 실행이 꺼져 있고 대기 작업·예약 실행이 중지되어 있다는 안내를 표시한다.

### Prometheus 접근과 지표
`GET /metrics`는 관리자 웹 세션 또는 `Authorization: Bearer <METRICS_TOKEN>`만 허용한다. 일반 사용자 세션은 `403`, 미인증·잘못된 bearer는 `401`이다. REST API 토큰이나 MCP OAuth 토큰은 지표 인증 수단이 아니다. `METRICS_TOKEN`을 설정하지 않으면 bearer 인증은 비활성화되며 관리자 세션은 계속 사용할 수 있다. bearer가 있는 요청은 관리자 쿠키가 함께 있어도 해당 bearer가 유효해야 한다. 토큰은 SHA-256의 고정 길이 digest를 constant-time 비교한다.

수집기는 비밀 저장소에서 전달한 별도 토큰을 쓰며 TLS 주소를 수집 대상으로 지정한다. `/metrics` 응답은 Prometheus text 형식이고 `Cache-Control: no-store`를 사용한다.

| 지표 | 의미 |
|---|---|
| `llmwiki_http_requests_total{method,route,status}` | 응답 종료까지 완료된 HTTP 요청 수다. |
| `llmwiki_http_request_duration_seconds{method,route,status}` | 응답 종료까지 걸린 초 단위 히스토그램이다. SSE는 연결 전체 수명이므로 일반 API 지연과 구분해서 해석한다. |
| `llmwiki_write_queue_depth{status}` | DB에 기록된 `queued`, `running`, `merging` 작업 수다. |
| `llmwiki_write_jobs_total{result}` | DB에 보존된 `succeeded`, `failed` 작업 수다. |
| `llmwiki_dream_runs_total{result}` | DB에 보존된 `succeeded`, `failed` 꿈꾸기 실행 수다. |
| `llmwiki_dream_duration_seconds{result}` | 완료된 꿈꾸기의 시작부터 종료까지 걸린 초 단위 히스토그램이다. |
| `llmwiki_index_stale` | 인덱싱된 SHA가 없거나 현재 HEAD와 다르면 1, 같으면 0이다. |
| `llmwiki_index_lag_seconds` | SHA가 다를 때 마지막 동기화 완료 후 경과한 초다. 동기화 완료 이력이 없으면 -1이고 HEAD와 같으면 0이다. 커밋 개수나 정확한 변경 대기 시간은 아니다. |
| `llmwiki_index_pending_vectors` | 임베딩을 기다리는 청크 수다. |

작업·꿈꾸기 지표는 수집 시 DB에서 읽으므로 재시작 후에도 보존된 실행을 포함하고 반복 수집으로 중복 증가하지 않는다. 기록 삭제·DB 복원으로 값이 줄 수 있다. HTTP 지표는 프로세스 재시작 시 초기화된다. 인덱스 지표는 수집 시 비동기 `IndexerService.status()`를 기다린다.

레이블에는 HTTP 메서드, 등록된 라우트 템플릿, 상태 코드와 고정된 결과만 쓴다. 요청 ID, 사용자 ID, SHA, 노트 경로, 작업 ID, 원문 입력은 지표 레이블로 쓰지 않는다. 등록되지 않은 서버 경로는 `unmatched_backend`, Next 자산은 `next_asset`, Next 화면은 `next_page`로 묶는다.

### LLM 사용량 원장
관리자 운영 설정은 최근 7·30·90일의 입력·캐시 입력·출력·추론 토큰 합계와 UTC 날짜·용도·모델별 사용량 표를 제공한다. `GET /api/admin/usage?days=N`은 인증된 관리자만 허용하며 `{ days, rows }`를 반환한다. 다른 운영 읽기 API처럼 관리자 세션 또는 관리자의 read scope REST 토큰을 사용한다. `days`는 기본 30이며 1~90의 정수다. 오늘 UTC 날짜를 포함한 N일을 조회하고, 각 행은 `day`, `lane`, `model`, `calls`, `inputTokens`, `cachedInputTokens`, `outputTokens`, `reasoningTokens`를 담는다. 응답은 `Cache-Control: no-store`로 공유 캐시를 금지한다.

`024_llm_usage.sql`의 `llm_usage`는 공급자가 사용량을 반환한 응답 한 건마다 한 행을 저장한다. 도니의 모든 실행 용도, 검색 확장·재정렬의 `search`, 질의·문서 임베딩의 `embedding`을 같은 원장에 기록한다. 실패·미완료 응답도 공급자가 사용량을 보냈다면 포함하지만, 사용량을 받지 못한 실패와 캐시 적중에는 추정 행을 만들지 않는다. 임베딩의 `usage.total_tokens`는 입력 토큰으로 기록한다. 재개 체크포인트의 이전 누적치를 다시 저장하지 않는다.

캐시 입력은 입력의 부분집합이고 추론은 출력의 부분집합이므로 네 열을 더해 총 사용량으로 해석하지 않는다. 모델별 가격·할인·외부 호출을 반영하지 않는 토큰 원장이며 청구 금액이 아니다. 원문 입력·응답·노트 내용은 저장하지 않는다. 선택적인 `owner`와 `ref`는 UUID 열이 아니라 호출자 문맥을 담는 불투명 문자열이며 API 표현을 유지한다. 기록은 90일 보존하고 새 행을 저장할 때 오래된 행을 정리한다.

### 요청 로그와 SSE
Next로 전달되기 전에 요청 로깅 미들웨어를 실행한다. `x-request-id`가 `[A-Za-z0-9._:-]{1,128}` 형식이면 그대로 쓰고 아니면 [식별자 규칙](identifiers.md)에 따라 새 요청 식별자를 발급한다. 응답의 `X-Request-ID`에도 같은 값을 넣는다.

응답이 끝나면 Pino 구조화 로그에 `{ method, route, status, ms, requestId, userId }`를 남긴다. 인증된 사용자 ID가 없으면 `userId`는 `null`이다. 원문 URL의 쿼리, 요청·응답 본문, Authorization 헤더와 쿠키를 기록하지 않는다. 요청 ID는 로그에서 문제를 연관 짓는 용도이며 지표의 레이블은 아니다.

도니 대화의 답변 실패는 `Chat answer failed` 로그에 전체 `err`, 안전한 `errorCode`, 대화 식별자와 SDK 오류의 `openaiRequestId`를 함께 기록한다. 취소는 실패 오류 로그를 남기지 않는다. 공급자 오류 원문과 공급자 요청 식별자는 서버 진단에만 사용하며 클라이언트에는 [대화 실패 코드와 안내](web.md#도니-대화-작업-공간)만 전달한다.

역방향 프록시에서는 `text/event-stream` 압축·버퍼링을 끄고 이벤트와 heartbeat가 즉시 전달되게 설정한다. 서버의 압축 제외 정책은 [웹 성능](performance.md), 이벤트 계약과 재연결은 [실시간 이벤트](events.md)에 기록한다.

### PID와 중지 후 복원
시작 시 `DATA_DIR/server.pid`에 현재 Node 프로세스의 PID를 기록한다. 정상 종료에서는 Next 종료와 함께 PID 파일을 읽고 아직 자신의 PID가 기록되어 있을 때만 삭제한다. 다른 프로세스가 덮어쓴 PID 파일은 지우지 않는다. 강제 종료처럼 종료 훅을 실행하지 못한 경우 파일이 남을 수 있으므로 파일 존재만으로 프로세스 생존을 단정하지 않는다. 백업 복원과 중지 절차는 [백업](backup.md)에 기록한다.

### 운영 이력과 관리자 조작
로그인한 viewer 이상은 다음 읽기 API를 사용할 수 있다.

| API | 응답과 페이지 구분 |
|---|---|
| `GET /api/dreams?before=<runId>&limit=` | `{ runs, nextCursor }`다. 다음 요청의 `before`에는 반환된 실행 ID 커서를 그대로 넣는다. |
| `GET /api/dreams/:id` | 꿈꾸기 실행의 상세다. 요약, 변경 경로, 일기 경로와 push 상태를 포함한다. |
| `GET /api/backup/status` | `{ lastAttempt, lastSuccess }`다. 해당 기록이 없으면 각 값은 `null`이다. |
| `GET /api/journal` | `{ date, path, dreamRunId }` 배열이다. |
| `GET /api/activity?before=&limit=&path=&source=&type=` | `{ items, nextCursor }`다. `type`은 `commit`, `job`, `dream`, `backup`이다. |

활동은 시간, 종류, ID의 내림차순으로 정렬하고 복합 커서로 동시간 항목도 빠뜨리지 않는다. 커서는 정렬 키 등을 담은 JSON 배열의 base64url 문자열이지만 클라이언트는 직접 조립하지 않고 `nextCursor`를 그대로 사용한다. 권한과 커서의 관계는 [폴더별 접근 제어](access-control.md#읽기와-쓰기-범위)를 따른다. 다른 사용자의 작업은 공개 요약·상태만 노출하고 원문 `input`과 `error`는 소유자 또는 관리자에게만 제공한다.

목록의 `limit` 기본값은 50이며 1~100을 허용한다. 활동의 `source` 필터는 `git`, `mcp`, `web`, `chat`, `dreaming`, `import`, `revert` 중 하나다. `path`는 저장소 상대 파일 경로이며 마크다운뿐 아니라 `assets/` 파일도 허용한다. 절대 경로, 상위 디렉터리 이동, `.git` 내부 경로는 허용하지 않는다.

관리자는 `GET /api/admin/ops`에서 큐·실패 작업·인덱스·꿈꾸기·원격 git push 상태를 함께 조회한다. `POST /api/admin/dreams/run`, `POST /api/admin/jobs/:id/retry`, `POST /api/admin/jobs/:id/cancel`, `POST /api/admin/index/reindex`는 수동 실행, 재시도, 대기 작업 취소와 인덱싱을 수행하며 성공·실패 결과를 감사 기록으로 남긴다. 인덱싱 본문의 `{ "full": true }`는 전체 재구축을 요청하고, `false` 또는 생략은 증분 재색인을 요청한다.

꿈꾸기 수동 실행의 HTTP `201`은 요청이 정상 처리되었다는 뜻이지 실행 성공을 보장하지 않는다. 서버는 실행 완료를 기다린 뒤 실행 객체를 반환하며, 실행 중 발생한 오류가 기록되면 HTTP `201`이어도 본문의 `status`는 `failed`다. 응답의 `status`·`error`와 실행 상세를 확인해야 한다. 이미 꿈꾸기가 실행 중이면 서버는 `409`로 거부한다.

### 웹 운영 화면과 지금 실행
운영 API는 [운영 이력과 관리자 조작](#운영-이력과-관리자-조작)에 정의하며, 웹은 다음 접점에서 같은 조작을 제공한다. 운영 사이드바와 설정 운영 탭은 관리자 전용이다.

- **운영 사이드바**는 36px 높이 헤더와 독립적으로 스크롤하는 본문을 사용한다. 대기·실행 및 병합 작업 수, 색인 동기화·오류·main 반영 대기 상태, 임베딩 대기 청크 수, 현재·최근 꿈꾸기와 최근 원격 push 시도·성공을 보여 준다. `꿈꾸기 지금 실행`, `색인 갱신`, `전체 색인 재구축`, `원문 가져오기`를 바로 실행하며 `전체 운영 설정`은 `/settings?tab=ops`로 이동한다.
- **설정 운영 탭** `/settings?tab=ops`는 준비 상태, 큐와 가장 오래된 대기 시간, 실행·대기 작업, 최근 실패 작업 최대 20개, 색인 SHA·임베딩 준비 상태·최근 오류, 꿈꾸기와 push 상세를 보여 준다. 대기 시간은 마지막 조회 시점을 기준으로 표시한다. 실패 작업의 재시도와 대기 작업의 취소를 제공하며, 실행·병합 중인 작업에는 취소 버튼을 제공하지 않는다. 설정 탭의 권한·URL·이동 규칙은 [웹의 설정 화면](web.md#로그인과-관리-화면)을 따른다.
- **명령 팔레트**의 운영 명령은 관리자에게만 노출한다. 한국어 표시명과 별도로 다음 영어 검색어를 제공한다. 일반 `가져오기 열기` 탐색 명령과 아래 관리자 빠른 실행 명령은 구분한다.

| 운영 명령 | 영어 검색어 |
|---|---|
| 운영 설정 열기 | `Operations Queue Index Dream Settings` |
| 지금 꿈꾸기 실행 | `Dream Now Dony Journal` |
| 증분 재색인 | `Incremental Reindex Search` |
| 전체 재색인 | `Full Rebuild Reindex Search` |
| 원문 가져오기 시작 | `Import URL Text File Obsidian Notion` |

운영 상태를 아직 받지 못했거나 공통 실행이 진행 중이면 꿈꾸기·재색인을 비활성화한다. 서버가 꿈꾸기 실행 중 또는 색인 동기화 중이라고 보고한 경우에도 해당 실행을 비활성화한다. 가져오기는 공통 실행 중에 비활성화한다.

사이드바의 가져오기는 현재 화면에 `ImportDialog`를 직접 연다. 팔레트의 `원문 가져오기 시작`은 편집 중인 변경의 이탈 확인을 거쳐 `/imports?new=1`로 이동한다. 이 쿼리의 자동 열기·소비·닫기 규칙과 수집 UI는 [웹의 원문 가져오기](web.md#원문-가져오기와-내보내기)에 기록한다.

### 공통 실행·확인·결과 계약
`OpsPanel`, `OpsOverview`, `useOpsCommands`는 `useOpsActions`를 사용한다. 서버 조작은 TanStack Query의 mutation key `['ops', 'command']`를 공유하고 `useIsMutating`으로 실행 중 상태를 함께 표시한다. 제출 시에도 mutation 캐시를 동기적으로 확인하고 확인 창 뒤에 다시 검사하므로, 서로 다른 접점이 React 재렌더링 전에 제출해도 중복 실행을 막는다. 이 가드는 같은 QueryClient 안의 제출을 직렬화하며, 다른 브라우저의 실행까지 막는 전역 잠금은 아니다.

| 조작 | 실행 전 확인과 의미 |
|---|---|
| 색인 갱신·증분 재색인 | 별도 확인 창 없이 즉시 `full: false`로 요청한다. |
| 전체 색인 재구축·전체 재색인 | 모든 노트의 검색 색인과 임베딩 재생성에 시간·모델 비용이 들 수 있고 저장된 노트는 변경하지 않는다는 설명을 확인한다. |
| 꿈꾸기 수동 실행 | 변경과 미학습 대화 정리, 일기 작성, 설정된 원격으로 git push하며 지식 저장소에 실제 변경이 생길 수 있다는 설명을 확인한다. |
| 실패 작업 재시도 | `resumable: true`인 작업은 `이어서 재시도`로 표시하며 저장된 진행 상황과 변경을 이어 처리하는 새 작업을 큐에 넣고 원래 실패 이력을 보존한다는 설명을 확인한다. 나머지는 `새 작업으로 재시도`로 표시하며 원래 입력을 다시 큐에 넣는다는 설명을 확인한다. |
| 대기 작업 취소 | 대기 중인 작업만 취소할 수 있다는 설명을 확인한다. |

실행 결과와 요청 오류는 전역 `notify` 알림으로 제공한다. 재시도 알림도 작업의 재개 가능 여부에 따라 `이어서 재시도`와 `새 작업으로 재시도`를 구분한다. 반환된 꿈꾸기의 `status: failed`는 HTTP 요청이 성공했더라도 오류 알림과 실행 오류를 표시한다. 꿈꾸기 결과는 `/dreams/<id>`, 재시도·취소 결과는 반환된 작업의 `/jobs/<id>`로 연결한다. 결과 객체가 없는 재색인은 `/settings?tab=ops`로 연결하고, 요청 자체가 실패하면 꿈꾸기 기록·원래 작업·운영 상태 중 해당 조작의 확인 화면으로 연결한다. 사이드바에서 가져오기를 등록하면 통합 작업 링크를 알리고, 실패하면 가져오기 창에서 오류를 확인하도록 안내한다.

mutation이 성공하거나 실패해 종료되면 운영 상태·준비 상태·작업·감사·꿈꾸기·push·활동·검색 조회를 즉시 무효화한다. 화면별 SSE 무효화 구독을 따로 두지 않으며, 이벤트에 의한 중앙 배치 갱신과 재연결 계약은 [실시간 이벤트](events.md)에 기록한다.

운영 화면의 원격 push는 꿈꾸기가 수행한 지식 저장소 git push의 결과다. SQLite·업로드·로컬 git bundle을 함께 보존하는 전체 백업의 성공 여부를 뜻하지 않는다. push 결과의 계약은 [꿈꾸기](dreaming.md), 전체 백업 생성·검증·복원은 [백업](backup.md)을 따른다.

### Slack 완료 알림
`SLACK_WEBHOOK_URL`을 설정하면 꿈꾸기의 최종 결과를 DB에 저장한 뒤 성공·실패 알림을 보낸다. 알림은 실행 상태, 실행 시간, 머지 SHA와 push 결과만 담으며 노트·일기 본문이나 사용자 입력을 보내지 않는다. 전송 실패는 경고 로그를 남길 뿐 저장된 실행 결과를 바꾸지 않는다. 전송 시간 제한과 민감한 필드 제외 정책은 [꿈꾸기의 Slack 완료 알림](dreaming.md#slack-완료-알림)에 기록한다.
