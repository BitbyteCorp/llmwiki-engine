# RAG 설계
엔진은 지식 저장소의 main에서 검색 인덱스를 파생하고, 키워드·벡터·위키링크를 함께 사용해 관련 지식을 찾는다.

## 배경

관련 지식을 찾는 일은 질문에 답할 때뿐 아니라 새 지식을 기존 노트에 반영하고 충돌·중복을 정리할 때도 필요하다.
검색 인덱스는 main의 마크다운을 진실 원천으로 삼는 파생물이며, 언제든 다시 만들 수 있다.
따라서 작업 워크트리의 미머지 변경은 인덱싱하지 않고, 모든 검색은 main 기준으로 수행한다.
지식 저장소 자체의 구성과 보존 정책은 [지식 저장소](knowledge-repository.md)에서 다룬다.

## 내용

### Nest 모듈과 의존성

`RagModule`은 `KnowledgeModule`을 가져오고 `IndexerService`와 `SearchService`를 제공하며 두 서비스를 다른 모듈에 내보낸다. 두 서비스는 설정·SQLite 연결·로그를 공용 `CONFIG`, `DB`, `LOGGER` 토큰으로 주입받으며, 인덱서는 `KnowledgeRepo`를 클래스 타입으로 주입받는다.

`IndexerService.onModuleInit()`은 벡터 테이블과 임베딩 설정을 확인하는 `init()`을 호출한다. main의 변경 반영은 별도의 `syncToHead()`로 수행하므로 서버 진입점은 초기 동기화를 시작하고, CLI는 워커나 스케줄러를 시작하지 않은 Nest 애플리케이션 컨텍스트에서 필요한 서비스를 조회한다. `rag.commands.ts`의 `registerRagCommands()`가 `reindex` 명령을 등록한다.

### 저장 구조와 한국어 검색

검색 데이터는 SQLite 하나에 저장하며, FTS5는 키워드 검색을, sqlite-vec은 벡터 검색을, 링크 테이블은 노트 사이의 위키링크 관계를 담당한다.
DB 선택 이유, sqlite-vec의 위험과 검색 모듈 경계, PostgreSQL로 전환할 조건은 [DB 선택](architecture.md#db-선택)에 기록한다.

FTS5 기본 토크나이저인 unicode61은 공백으로 구분된 한국어 단어에서 조사를 떼어내지 않는다.
예를 들어 본문의 `저장소는`은 `저장소`와 다른 토큰이므로, `저장소`라는 질의로 해당 표현을 찾지 못한다.
이를 피하기 위해 부분 문자열을 매칭하는 trigram 토크나이저를 사용한다.
다만 3글자 미만 질의는 FTS를 건너뛰고 벡터 검색에 의존한다. 글자 수는 유니코드 코드 포인트 기준이며, 앞뒤 공백을 제거한 빈 질의는 빈 결과를 반환한다. FTS 질의는 입력 전체를 리터럴 구문으로 검색하므로 FTS 연산자를 입력해도 검색 문법으로 실행하지 않는다.

### 인덱싱 범위와 청크 문맥

main에 추적된 마크다운을 인덱싱한다. `wiki/`, `journal/`, `raw/`의 종류(`kind`)는 각각 `wiki`, `journal`, `raw`이며, 루트의 `index.md` 등 나머지 경로는 `other`다.
메모리 파일인 `MEMORY.md`는 검색 대상에서 제외하며, 문맥 제공 규칙은 [지식 저장소](knowledge-repository.md)에 기록한다.

청킹은 frontmatter를 분리한 뒤 H2/H3 섹션 단위로 수행하며, 긴 섹션은 약 800토큰 단위로 나눈다.
임베딩 입력 앞에는 `노트 제목 > 섹션 경로`와 태그를 맥락 헤더로 붙인다.
제목은 frontmatter의 `title`, 본문의 첫 H1, 확장자를 뺀 파일명 순서로 정한다. 코드 펜스 안의 H2/H3는 섹션 경계로 취급하지 않는다. 청크 본문은 원문의 줄과 문자를 보존하며, 토큰 수는 ASCII 네 글자 또는 비ASCII 코드 포인트 한 글자를 한 토큰으로 근사한다. 섹션이 길면 최대 약 800토큰을 넘지 않도록 줄바꿈이나 공백 경계를 우선하여 나눈다.
이는 청크가 노트의 일부만 담더라도 어느 주제와 섹션에 속하는지 함께 전달하기 위한 장치다.
예를 들어 노트 제목이 `지식 저장소`, H2가 `검색`, H3가 `한국어`, 태그가 `search`라면 헤더는 다음처럼 표현한다.

```text
지식 저장소 > 검색 > 한국어
태그: search
```

임베딩 모델은 OpenAI `text-embedding-3-small`을 사용하고 설정으로 변경할 수 있다.
인덱스 메타데이터에 모델명과 차원을 함께 저장한다. `EMBEDDING_MODEL`이나 `EMBEDDING_DIMENSIONS`가 바뀌면 전체 재인덱싱하며, sqlite-vec의 `vec0` 테이블도 새 차원으로 다시 만든다. 기본 차원은 1536이며 테이블은 SQL 마이그레이션이 아니라 런타임에 생성한다. OpenAI SDK는 `OPENAI_BASE_URL`을 반영하고 임베딩을 최대 128개씩 묶어 요청한다.
Luna와 별도 임베딩 모델을 사용하는 이유는 [Luna](luna.md)에서 다룬다.

### 증분 인덱싱과 복구

마지막으로 인덱싱한 커밋 SHA를 저장하고, main에 머지될 때마다 `git diff --name-status 이전SHA..HEAD`로 변경 파일을 찾는다.
변경된 파일만 다시 청킹하고, 맥락 헤더와 본문을 포함한 임베딩 입력의 SHA-256 해시가 같으면 기존 임베딩을 재사용한다. 캐시는 해시·모델·차원의 조합으로 구분하므로 제목·태그·섹션 경로가 바뀌면 임베딩을 새로 생성하지만, 제목과 본문이 같은 파일 이름 변경이나 같은 설정의 전체 재인덱싱은 캐시를 재사용한다.
파일 삭제와 이름 변경도 인덱스에 반영한다.

서버 시작 시에는 저장된 SHA와 main의 HEAD를 맞춰 누락된 변경을 반영한다.
전체 인덱스를 다시 생성하는 명령도 제공하므로 파생 인덱스를 원문에서 재구축할 수 있다.

`llmwiki reindex`는 누락된 변경을 증분 반영하며, `llmwiki reindex --full`은 main 전체에서 인덱스를 재구축한다. 인덱서 내부에서 증분 동기화와 전체 재구축을 직렬화하여 동시 요청이 같은 이전 SHA를 중복 처리하지 않게 한다. 청킹과 임베딩 요청이 완료된 뒤 청크·벡터·링크·SHA를 한 트랜잭션으로 갱신하므로 요청 실패를 성공한 동기화로 기록하지 않는다.

`OPENAI_API_KEY`가 없어도 FTS와 링크를 갱신하고 새 청크의 벡터를 대기 상태로 기록한다. 나중에 키를 설정하면 다음 동기화에서 대기 벡터를 채우며, 이때 main에 새 커밋이 없어도 처리한다. 검색은 키가 없는 동안 FTS만 사용하며 서비스 인스턴스마다 경고를 한 번 기록한다. 따라서 키가 없고 질의가 3글자 미만이면 결과가 없다. 실제 임베딩 API 오류는 누락된 키로 간주하지 않고 호출자에게 전달한다.

```mermaid
flowchart TD
    A[main에 머지] --> C[저장된 SHA와 main HEAD 비교]
    B[서버 시작] --> C
    C --> D[git diff --name-status 이전SHA..HEAD]
    D --> E[변경 파일의 frontmatter 분리와 H2/H3 청킹]
    E --> F[긴 섹션을 약 800토큰으로 분할]
    F --> G{청크 내용 해시가 같은가}
    G -->|예| H[기존 임베딩 재사용]
    G -->|아니오| I[맥락 헤더를 붙여 임베딩 생성]
    H --> J[FTS5 · sqlite-vec · 링크 테이블 갱신]
    I --> J
    D --> K[삭제 · 이름 변경 반영]
    K --> J
    J --> L[마지막 인덱싱 SHA 저장]
    M[전체 재생성 명령 · 임베딩 모델 변경] --> N[main의 인덱싱 대상 전체 청킹]
    N --> O[맥락 헤더를 붙여 임베딩 생성]
    O --> P[전체 인덱스 재구축]
    P --> L
```

작업 워크트리에서 쓰는 동안에는 이 경로를 실행하지 않으며, main에 머지된 뒤에만 검색 결과에 반영한다.
머지까지의 작업 절차는 [쓰기 흐름](write-flow.md)에서 다룬다.

### 하이브리드 검색

키워드 검색의 BM25 상위 50개와 벡터 검색 상위 50개를 가져와 RRF로 합치며, RRF의 상수는 `k=60`으로 둔다.
합친 청크 결과를 노트 단위로 묶고 청크별 RRF 점수를 합산한 뒤 상위 N개 노트를 선택한다. 기본 N은 10이며, 명시한 `limit`은 1~100의 정수여야 한다. 종류 필터는 키워드와 벡터의 상위 50개를 고르기 전에 적용한다. 각 노트는 가장 높은 청크 점수의 본문 전체를 `snippet`으로, 그 청크의 섹션 경로를 `heading`으로 반환한다.
선택된 노트의 위키링크 1-hop 이웃은 `related` 경로 목록으로 함께 반환하며, 들어오는 링크와 나가는 링크를 모두 포함하고 자기 자신과 중복을 제거한다. `[[이름]]`, `[[이름#섹션]]`, `[[이름|표시명]]`은 `.md`를 뺀 basename을 대소문자 구분 없이 찾아 연결한다. 같은 basename이 여러 경로에 있으면 정렬상 첫 경로를 선택한다. 미해결 링크도 저장하여 대상 노트가 나중에 추가되거나 이름이 바뀌면 다시 해석한다.
키워드와 의미 유사도로 직접 찾은 노트에 링크로 이어지는 맥락을 보태는 구조다.

```mermaid
flowchart TD
    A[검색 질의] --> B[FTS5 trigram · BM25 상위 50]
    A --> C[질의 임베딩 · 벡터 상위 50]
    B --> D[RRF k=60으로 통합]
    C --> D
    D --> E[노트 단위로 묶음]
    E --> F[상위 N개 노트 선택]
    F --> G[링크 테이블에서 위키링크 1-hop 이웃 조회]
    F --> H[검색 노트와 관련 노트 반환]
    G --> H
```

### 사용처

- [MCP](mcp.md)의 `search`는 하이브리드 검색을 제공한다.
- [웹 버전](web.md)의 질의응답은 Luna가 `search`와 `read_note`를 반복 호출하는 에이전트형 RAG이며, 답변에 근거 노트를 인용한다.
- [쓰기 흐름](write-flow.md)은 새 노트를 만들기 전에 기존 노트를 검색해 기존 지식에 반영할 수 있는지 판단한다.
- [dreaming](dreaming.md)은 변경 노트와 가까운 노트를 찾아 충돌·중복 후보로 사용한다.

## 검토한 대안

- OpenAI 호스티드 `file_search` 벡터 스토어는 지식을 외부 벡터 스토어에 복제하고 git과 동기화해야 하며, MCP 검색까지 그 스토어에 의존하게 되므로 채택하지 않았다.
- PostgreSQL 대안 검토는 [DB 선택](architecture.md#db-선택)에 기록한다. Qdrant는 컨테이너 하나 요구사항과 맞지 않으므로 채택하지 않았다.
