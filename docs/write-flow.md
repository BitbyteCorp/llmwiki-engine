# 지식 쓰기 흐름

엔진의 모든 쓰기는 요청자별 작업 워크트리에서 수행하고, 같은 프로세스 전역 머지 락으로 main 반영과 색인 갱신을 직렬화한다. 자연어를 정리하는 도니 작업과 사용자가 직접 편집한 노트를 반영하는 작업, Git 변경을 되돌리는 작업은 같은 이력과 이벤트 형식을 사용한다.

## 작업 종류와 출처

`WriteJob.kind`는 `agent`, `direct`, `revert`다. `source`는 `mcp`, `web`, `chat`, `dreaming`, `import`, `revert` 중 하나이며, `client`에는 호출 클라이언트 이름을 선택적으로 기록한다. `WriteJobsService.submit({ userId, input, source, client?, sourcePaths?, requiredReads?, dedupeKey? })`는 출처를 명시해야 하며 작업 정보와 `reused` 플래그를 반환한다. 선택적인 `requiredReads`는 완료 전에 끝까지 읽어야 하는 경로 목록이며 [원문 수집의 완독 검증](ingestion.md#통합-작업과-복구)에 사용한다. `dedupeKey`를 지정하면 같은 키의 실패하지 않은 작업을 재사용하고 새 작업이나 이벤트를 만들지 않는다. 키는 `017_write_job_dedupe.sql`의 영속 열과 부분 고유 인덱스로 보존하므로 재시작 뒤에도 중복 제출을 막으며, 실패한 작업은 키를 해제한다. 키를 생략한 제출은 각각 독립적인 작업이다. direct 작업의 입력에는 재실행에 필요한 `baseSha`, 연산, 메시지와 호출자 정보가 JSON으로 보존되고, revert 작업에는 대상 SHA와 선택 경로가 보존된다.

`src/db/migrations/016_agent_job_kind.sql`은 [에이전트 이름과 식별자의 분리](agent.md#배경)에 맞춰 기존 에이전트 작업 종류를 `agent`로 바꾼다. 작업 행과 관련 이력을 보존하며 `write_jobs.kind`의 기본값은 `agent`, 허용 값은 `agent`, `direct`, `revert`로 변경한다. 테이블 재구축 중 인덱스·트리거 보존과 외래 키 검증은 [SQL 마이그레이션 러너의 재구축 규칙](development.md#sql-마이그레이션과-테이블-재구축)을 따른다.

작업 상태는 `queued → running → merging → succeeded`이며 실행 오류나 취소는 `failed`로 끝난다. 상태 외에 `queued`, `preparing`, `editing`, `committing`, `merging`, `resolving_conflict`, `indexing`, `cleanup`, `done`, `failed` 단계 이벤트를 순서대로 저장한다. 각 이벤트는 `{ phase, at, detail }`이며 UTC ISO-8601 시각과 선택적 세부 정보를 포함한다. `WriteJobsRepository.events(id)`와 `WriteJobsService.events(id)`로 동일한 이력을 조회한다.

작업과 서브에이전트의 ID는 API·이벤트에서 고정 22자리 base62로 노출하며 SQLite의 ID 열은 같은 바이트의 base64url 형식으로 저장한다. 작업 이벤트의 JSON 세부 정보는 발행한 API 형식을 그대로 보존한다. 레거시 UUID 입력과 기존 실패 Git ref의 호환 규칙은 [식별자](identifiers.md)를 따른다.

`EventsService`는 각 단계에서 `job.updated`를 작업 소유자와 관리자에게 발행하고, main 반영 후 `main.updated`를 모든 로그인 사용자에게 발행한다. 색인 서비스는 별도로 `index.updated`를 발행한다. SSE 이벤트는 갱신 알림이고, 영속적인 작업 이력의 원천은 SQLite다.

## 도니 비동기 쓰기

1. MCP나 채팅 등의 요청을 받으면 즉시 queued 작업 ID를 반환한다.
2. 단일 에이전트 워커가 아래 대기열 선택 규칙으로 다음 작업을 골라 한 번에 하나씩 실행한다. 실행 중인 작업은 뒤에 들어온 작업이 선점하지 않는다.
3. main에서 작업 워크트리를 만들고 요청자 이름·이메일과 커밋 메타데이터를 설정한다.
4. 도니는 main 검색 결과와 작업 워크트리의 실제 파일을 읽고, [작성 규칙](writing-rules.md)에 따라 편집한다. 독립적인 다중 파일 작업은 같은 워크트리의 [쓰기 서브에이전트](agent.md#쓰기-서브에이전트)에 나누고, 부모가 실제 결과 파일을 검증한 뒤 의미 단위로 커밋한다.
5. 남은 수정은 엔진이 요약 첫 줄을 최대 200자로 잘라 커밋한다. 빈 요약은 `Update knowledge`를 사용한다. 변경이 없는 작업은 빈 커밋 없이 성공한다.
6. 전역 머지 락 안에서 최신 main을 작업 브랜치에 병합한다. 충돌 경로를 작업 행에 저장하고 도니가 해결한다. 각 해결 시도의 시작과 `resolved`, `unresolved`, `error` 결과를 `resolving_conflict` 단계 세부 정보로 기록한다. 파일 부재와 충돌 마커를 검증한 뒤 머지를 완료한다.
7. main을 fast-forward하고 머지 SHA와 작업 커밋을 기록한 후 이벤트를 발행하고 색인을 갱신한다. 워크트리를 정리하고 done 이벤트를 남긴다.

Notion 가져오기 25개 배치 중 첫 배치(`1/25`)에서는 자식 네 개 중 세 개가 노트 작성을 마쳤지만, 부모가 약 39분 뒤 96턴 한도 초과로 실패하여 작성된 지식이 main에 반영되지 않았다. 문맥 압축 뒤 같은 원문을 다시 읽는 흐름을 줄이기 위해 도니는 main을 먼저 검색하고, 편집할 노트와 관련 루트 색인·도메인 허브·schema만 한 번 확인하며 무관한 파일은 훑지 않는다. 파일이 바뀌지 않았으면 이미 읽은 페이지를 다시 읽지 않고, 각 노트에 필요한 원문을 읽는 대로 작성·확장한다. 최종 편집 뒤에는 변경 파일을 한 번만 재확인하며, 자식 종료를 기다린 부모도 실제 결과를 한 번 검토하고 신속히 커밋한다. 부모가 한도 전에 탐색에서 마무리로 전환하게 하는 경고의 임계값·주입 횟수·재개 시 계산은 [도니의 실행 체크포인트](agent.md#실행-체크포인트)에 기록한다.

도니의 편집은 머지 락 밖에서 진행하므로 direct 작업이 느린 모델 응답을 기다릴 필요가 없다. 꿈꾸기 등 다른 쓰기 경로도 저장소의 같은 머지 락을 사용한다. 한 데이터 디렉터리에는 엔진 프로세스 하나만 실행한다.

한 큐 작업 안의 파일 편집은 동시에 진행할 수 있지만 작업 큐와 main 머지는 여전히 직렬이다. `runWrite`는 부모 실행의 성공·실패와 관계없이 종료 구간에서 모든 실행 중인 자식의 취소와 종료를 기다린다. 따라서 워커의 잔여 변경 커밋, 충돌 해결, 머지, 워크트리 정리는 자식이 더 이상 파일을 바꾸지 않는 상태에서 시작한다.

부모 실행은 도구 호출 없는 최종 응답을 받으면 `RunAgentOptions.beforeFinish`를 호출한다. 훅이 후속 사용자 메시지를 반환하면 그 응답을 완료로 수락하지 않고 응답·후속 메시지를 모델 입력에 추가한 뒤 체크포인트를 저장하고 같은 턴 한도 안에서 계속 실행한다. 거절된 완료 문구는 최종 작업 요약에 합치지 않는다. 훅이 오류를 던지면 잔여 변경 자동 커밋·머지에 들어가지 않고 기존 실패 보존 절차를 수행한다. `onTurnLimit` 훅은 일반적인 턴 초과 오류보다 앞서 작업별 실패 사유를 낼 수 있다. 필수 읽기가 없는 작업은 기존 완료 흐름을 유지하며 필수 읽기의 구체적인 실패 조건은 [원문 수집](ingestion.md#통합-작업과-복구)에 기록한다.

부모의 기본 한도는 `WRITE_MAX_TURNS = 96`이다. `onTurnLimit`에서 필수 원문 완독 검증을 통과하고 실제 `Dony exceeded maxTurns (96)` 오류로 종료된 경우에만 별도의 턴 한도 후 마무리를 검토한다. 미완독 원문이 있으면 기존 `unread assigned sources` 오류로 실패하고 마무리를 실행하지 않는다. 위 자식 종료 절차를 마친 뒤 `Worktree.changedSinceBase()`로 작업 기준 커밋 대비 바뀐 경로를 커밋 여부와 관계없이 모은다. 이 메서드는 `diff()`처럼 모든 변경을 스테이징한 뒤 기준 커밋과 인덱스를 비교한다. 바뀐 경로가 없으면 원래 턴 한도 오류로 실패하고, 하나라도 있으면 마무리 대상이다.

마무리는 부모 대화를 재개하지 않는 독립적인 `agent.runAgent()` 호출로 한 번만 실행한다. `lane: 'write'`, `WRITE_TURN_LIMIT_WRAP_UP_MAX_TURNS = 8`을 사용하며 새 JSON 입력은 `jobId`, 원래 `request`, 변경 경로 목록 `changedPaths`를 담는다. 요청자의 권한과 author를 적용하는 일반 `agent.worktreeTools(wt, author, user)`만 제공하고, 서브에이전트 풀의 도구나 새 자식 실행은 제공하지 않는다. 기존 기본 문맥·쓰기 지침에 부모가 96턴을 소진했다는 최종 마무리 지침을 덧붙인다. 새 탐색과 새 원문 읽기를 금지하고 변경 파일만 한 번 검토하여 frontmatter, 존재하지 않는 대상의 링크, 잘린 섹션을 고친 뒤 커밋하도록 한다. 마지막 한국어 요약에는 턴 한도 후 마무리임을 명시하고 실제 통합한 지식과 통합하지 못한 지식을 구분하며, 아직 main에 머지되었다고 주장하지 않는다.

마무리 시작과 정상 종료는 `editing` 이벤트의 `detail`을 각각 정확히 `{ wrapUp: 'started' }`, `{ wrapUp: 'finished' }`로 기록한다. 이 세부 정보에는 경로나 본문을 넣지 않는다. 서브에이전트가 아닌 이벤트의 세부 정보는 작업 전체가 제한되지 않으면 이력 조회에서 그대로 전달될 수 있으므로, 마무리 이벤트 자체가 제한된 경로·내용을 노출하지 않게 한다. 마무리에도 같은 `onUsage`를 전달하지만 `resume`과 `onCheckpoint`는 전달하지 않으며 부모 체크포인트를 새로 쓰거나 덮어쓰지 않는다.

마무리가 실패하거나 8턴을 소진하면 부모 96턴 한도, 마무리 8턴 한도, 원래 부모 실패 사유와 마무리 실패 사유를 함께 담은 오류로 작업을 실패시키며 `finished` 이벤트를 남기지 않는다. 이때도 [요청자 추적과 실패 복구](#요청자-추적과-실패-복구)의 실패 ref·미커밋 변경 보존과 원래 부모 체크포인트 유지 절차를 그대로 따른다. 마무리가 성공하면 그 요약을 반환하고 기존 워커의 잔여 변경 자동 커밋, 권한 검사, 메타데이터 보완, 직렬 머지·색인·정리 절차로 돌아간다. 마무리 성공 이벤트 자체는 main 반영 완료를 뜻하지 않는다.

커밋 경로는 변경된 위키 노트에 [엔진 자동 속성](note-metadata.md#엔진-자동-속성)을 채운다. 일반 에이전트 작업은 첫 커밋 뒤 메타데이터 문제를 한 번의 제한된 보완 실행으로 고치고, 보완 커밋과 충돌 해결 뒤 최종 검증에서 남은 문제를 작업 결과에 기록한다. 메타데이터 오류만으로 지식 반영을 거절하지 않으며 자세한 제한과 결과 필드는 [노트 메타데이터 표준의 검증과 복구](note-metadata.md#검증과-복구)에 둔다.

사용자 쓰기는 [폴더별 접근 제어](access-control.md)를 따른다. 도니의 검색·워크트리 읽기는 요청자의 읽기 범위 안에서 실행하며 편집 뒤 머지 전에 변경 경로의 쓰기 권한을 검사한다. 충돌 해결 뒤 main에 반영하기 직전에도 현재 사용자 역할과 규칙으로 재검사하며 거절된 작업은 main을 바꾸지 않고 실패한다. 꿈꾸기는 시스템 권한을 사용하되 규칙이 있으면 ACL 경계 간 정보 이동을 자동 보장할 수 없다는 경고를 감사·실행 기록에 남긴다.

### 대기열 선택 순서

에이전트 큐는 `source=import`인 가져오기 작업과 그 외 출처의 대화형 작업으로 나눈다. 기본적으로 대화형 작업을 먼저 선택하며 각 부류 안에서는 생성 시각, 같은 시각이면 삽입 순서를 따른다. 따라서 가져오기끼리의 FIFO와 같은 가져오기의 배치 순서를 유지하고, 뒤 배치는 앞 배치의 실행·머지·정리가 끝난 뒤 시작한다. 재시도는 원래 `source`를 유지한 새 작업이므로 원래 부류의 끝에 들어간다.

가져오기가 무한히 밀리지 않도록 `MAX_CONSECUTIVE_INTERACTIVE_JOBS = 3`으로 연속 대화형 선택을 제한한다. 세 번 연속 대화형 작업을 선택한 뒤에는 대기 중인 가장 오래된 가져오기를 우선 선택한다. 가져오기가 없으면 대화형 작업을 계속 실행하되 횟수는 3으로 유지하므로, 그 사이 가져오기가 들어오면 다음 선택에서 실행한다. 가져오기를 선택하거나 큐가 비면 횟수를 0으로 되돌린다. 이 횟수는 워커 프로세스 메모리에 두므로 프로세스 재시작 시 0부터 시작한다. 이 제한은 작업 선택 횟수 기준이며 이미 실행 중인 작업의 소요 시간을 제한하지 않는다.

이 정책은 `kind=agent` 대기 작업에만 적용한다. `source=dreaming`으로 이 큐에 제출한 작업도 가져오기가 아닌 부류로 처리하지만, 정기 꿈꾸기는 별도 `DreamingService` 실행 경로를 사용하므로 이 큐의 우선순위를 적용하지 않는다. 직접 편집·되돌리기와 그 재시도도 기존처럼 에이전트 큐 밖에서 실행하며 같은 전역 머지 락만 공유한다.

### 충돌 해결

충돌 해결 시작 시 각 허용 경로의 base, 작업 브랜치, main 버전을 한 번씩 읽어 불변 스냅샷으로 보관한다. 모델 입력에는 각 버전과 충돌 표시가 있는 실제 워크트리의 첫 페이지 JSON만 넣으며 파일이 없으면 `null`을 넣는다. 빈 파일은 `content: ""`인 유효한 페이지다. 페이지는 기본·최대 300줄이며 본문과 직렬화한 본문 각각 최대 12,000자로 제한한다. 긴 줄도 `nextOffset`과 `nextCharOffset`으로 이어 읽어 줄바꿈과 유니코드 문자 경계를 보존한다.

읽기 전용 `read_conflict_version({ path, version, offset?, limit?, charOffset? })`의 `version`은 `base`, `workBranch`, `main` 중 하나다. 도구는 해결 시작 시 보관한 스냅샷의 페이지를 반환하므로 워크트리를 수정하거나 두 번째 해결 시도로 넘어가도 원래 양쪽 변경을 계속 읽을 수 있다. 충돌 표시가 있는 실제 파일과 편집 후 결과의 나머지 페이지는 기존 `read_file`로 읽는다. 두 읽기 도구와 `write_file`은 현재 시도의 충돌 경로로만 제한하며 각 스냅샷 페이지 읽기에도 요청자의 현재 읽기 권한을 검사한다.

도니는 파일을 교체하기 전에 양쪽 의도와 유지할 지식을 판단하는 데 관련된 버전과 실제 파일의 모든 페이지를 끝까지 읽어야 한다. 첫 페이지 밖의 꼬리 지식을 삭제하지 않고 전체 해결 결과를 `write_file`로 저장한 뒤 `read_file`의 모든 페이지로 검토한다. 엔진은 요청한 모든 파일의 부재와 충돌 마커를 검사하며 미해결 경로만 한 번 더 요청한다. 두 시도 뒤에도 부재나 마커가 남으면 실패한다. 해결 도구에는 삭제·이동·커밋 도구를 제공하지 않으며 머지 완료는 엔진이 수행한다.

### 쓰기 사용량

에이전트 작업은 부모 쓰기, 턴 한도 후 마무리, 같은 풀의 서브에이전트, 머지 충돌 해결 응답의 사용량 델타를 합산한다. 성공·실패한 실행의 마지막 `done` 또는 `failed` 단계 이벤트는 `detail.usage`를 담으며 Pino의 `Write job completed` 또는 `Write job failed` 로그에도 같은 `usage`를 남긴다. 필드와 부분집합 관계는 [도니의 비용과 사용량](agent.md#비용과-사용량)을 따른다. 응답 사용량을 받기 전에 실패했으면 합계는 0이며, 실패 응답에 제공된 사용량은 포함한다.

이 합계는 해당 작업 실행에서 새로 받은 응답만 대상으로 한다. 이어서 재시도한 새 작업도 0부터 집계하므로 보존된 부모 체크포인트의 이전 누적 사용량을 다시 청구된 사용량처럼 더하지 않는다. 이전 비용은 원래 작업의 종료 이벤트에 남는다. 직접 편집·되돌리기처럼 모델을 실행하지 않는 작업이나 queued 상태 취소에는 에이전트 실행 합계를 새로 만들지 않는다.


### 대화에서 제출하는 쓰기

웹 대화의 `write_knowledge`는 [도니의 기록 요청 규칙](agent.md#대화-중-지식-기록-도구)을 따라 `WriteJobsService.submit()`에 요청자의 `userId`, 기록할 `input`, `source: 'chat'`, 대화 ID인 `client`를 전달한다. `dedupeKey`는 `chat:<conversationId>:<userMessageId>:<호출 순번>:<내용 SHA-256>:<현재 요청자 ID>`이며 호출 순번은 새 답변마다 1부터 시작한다. [체크포인트가 있는 실패 답변의 이어가기](web.md#도니-대화-작업-공간)는 이전 도구 호출과 결과를 그대로 사용하므로 이미 접수한 기록 요청을 다시 제출하지 않으며 이후 호출 순번도 이어간다. 체크포인트가 없는 재시도와 재생성은 새로 실행하되 같은 내용의 턴과 같은 순번의 비실패 작업을 재사용한다. 편집한 내용과 다른 요청자는 새 작업으로 구분한다. 해당 답변에서 추적한 근거 노트 경로도 `sourcePaths`로 보존하여 작업 실행과 이력 조회의 읽기 권한 검사에 사용한다. 대화 구성원 역할과 별개인 전역 쓰기 권한은 [접근 제어](access-control.md#읽기와-쓰기-범위)를 따른다.

새 작업의 도구 결과 `{ jobId, status: 'queued' }`는 큐에 접수했다는 뜻이며 파일 저장·커밋·main 반영의 완료가 아니다. 재사용 결과 `{ jobId, status, reused: true }`는 기존 작업의 현재 상태를 반환한다. 도니의 접수·재사용·완료 안내는 [기록 상태 안내 규칙](agent.md#대화-중-지식-기록-도구)을 따른다. 실제 완료와 실패는 위의 비동기 작업 상태와 [웹 작업 상세](web.md#쓰기-작업과-꿈꾸기일기)에서 확인한다. 답변 생성의 종료와 쓰기 작업의 완료는 별개다.

이 경로는 `proposal()`의 초안 미리보기와 다르다. 초안은 사용자가 diff를 확인한 뒤 직접 쓰기 API로 적용하지만, 도니의 선제적 기록과 사용자의 명시적인 대화 기록 요청은 모두 기존 에이전트 큐에 바로 제출한다. 기록 기준과 야간 꿈꾸기의 관계는 [도니의 기록 정책](agent.md#대화-중-지식-기록-도구)을 따른다.

## 직접 편집과 낙관적 동시성 제어

`NoteWriterService.apply({ userId, source, ops, baseSha, message?, client? })`는 에이전트 큐에 들어가지 않고 즉시 실행한다. 성공 결과는 `{ jobId, mergeSha, changed }`다. 락을 얻은 뒤 현재 main과 `baseSha`를 비교하고, **그 최신 main에서** 작업 워크트리를 만든다. 신선도 확인부터 편집·커밋·main 반영·색인까지 같은 락을 유지한다.

`baseSha`는 클라이언트가 노트를 읽었을 때 받은 main HEAD인 `updatedSha`다. 다른 파일만 바뀌었다면 오래된 baseSha로도 편집할 수 있으며 다른 변경을 보존한다. 연산이 건드리는 경로가 바뀌었다면 `409 stale_note`를 반환하고 메시지에 현재 main SHA를 포함한다. 이동은 원본과 대상 경로를 모두 검사한다.

낙관적 동시성 검사와 별개로 저장·삭제 대상의 쓰기 권한을 요구한다. 이동은 원본과 대상 모두 쓸 수 있어야 하며 읽기조차 불가능한 경로는 존재를 숨기는 404를 반환한다.

연산은 다음과 같다.

- `put`: `{ op: 'put', path, content?, contentBase64?, create? }`. `create: true`는 독점 생성이며 이미 존재하면 `409 note_exists`다. 생략하거나 false이면 생성 또는 교체한다. 문자열 내용과 base64 내용 중 정확히 하나를 제공한다.
- `delete`: `{ op: 'delete', path }`. 없으면 `404 note_missing`다.
- `move`: `{ op: 'move', from, to }`. 원본이 없으면 `404 note_missing`, 대상이 있으면 `409 note_exists`다.

잘못된 경로, 허용되지 않은 파일 형식, 내용 인코딩이나 요청은 `400 invalid_note`다. 절대 경로, 상위 디렉터리 접근과 Git 내부 경로는 허용하지 않으며 워크트리의 경로 격리를 유지한다. 여러 연산 중 하나라도 실패하면 main에는 어떤 연산도 반영하지 않는다.

일반 직접 쓰기는 `.md` 노트와 `assets/**` 파일만 허용한다. 바이너리는 `contentBase64`로 전달하고 실제 바이트로 저장한다. 큰 원본도 그룹 반복 정규식 없이 길이·문자·패딩을 선형 검사하며, 존재 여부와 신선도에는 파일 내용이나 바이너리 patch를 읽지 않는다. **가져오기 예외**로 `source: 'import'`인 요청은 `raw/**`에도 바이너리 원본을 새로 생성할 수 있다. 기존 raw 경로는 출처와 관계없이 불변이며 교체·삭제·이동 시 `409 note_exists`다. raw로의 이동도 금지한다. 가져오기는 원본 생성에 `create: true`를 사용한다.

직접 편집·되돌리기도 같은 커밋 경로에서 변경 노트의 엔진 자동 속성을 채운다. 직접 쓰기는 메타데이터를 위한 LLM 보완 실행을 만들지 않으므로, 의미 속성은 클라이언트가 [노트 메타데이터 표준](note-metadata.md)에 맞춰 제출한다. 내용 변화 없는 이동은 기존 메타데이터를 유지한다.

수집의 새 raw 원문 생성은 시스템 보존 단계이므로 경로 ACL을 적용하지 않는다. 수집 요청자에게 전역 편집 권한은 여전히 필요하며 이어지는 도니 통합 작업은 요청자의 읽기·쓰기 규칙을 적용한다. 요청자가 보존된 raw 경로를 읽을 수 없으면 도니도 해당 원문을 읽지 못한다.

## 이력 조회와 되돌리기

`NoteWriterService.applyRevert({ userId, sha, paths?, preview?, client? })`는 main의 최신 워크트리에서 대상 커밋의 역변경을 적용한다. merge 커밋은 첫 부모를 기준으로 되돌린다. `paths`를 지정하면 격리된 저장소 상대 경로만 되돌리며 assets도 선택할 수 있다. 충돌을 자동으로 임의 해결하지 않고 오류로 반환한다. raw 불변성은 일반 direct/import 연산의 경계이며, 명시적으로 요청하고 감사 이력을 남기는 history revert는 보상 변경으로 raw 추가·변경도 되돌릴 수 있다.

`preview: true`는 `{ files, patch }`를 반환하며 main, 커밋, 작업 행을 만들지 않는다. 실제 적용은 `kind: 'revert'`, `source: 'revert'` 작업을 생성하고 direct와 같은 머지 락·커밋·색인·이벤트 흐름을 따른다. 성공 결과는 `{ jobId, mergeSha, changed }`다. 삭제와 실제 revert의 성공·실패는 요청자를 포함해 감사 로그에 기록한다.

되돌리기 미리보기도 실제로 되돌릴 모든 경로의 쓰기 권한을 요구한다. Git 목록·커밋 상세·비교·작업 상세는 읽을 수 있는 변경만 반환하고 제한된 파일의 패치와 요약을 노출하지 않는다.

REST 계약은 다음과 같다.

| 요청 | 결과 |
|---|---|
| `GET /api/notes/content?path=&ref=` | 내용, frontmatter, body, `updatedSha`, 해석된 커밋 SHA인 `ref` |
| `PUT /api/notes` | 200 `{ jobId, mergeSha }` |
| `POST /api/notes/move` | 201 `{ jobId, mergeSha }` |
| `DELETE /api/notes?path=&baseSha=` | 200 `{ jobId, mergeSha }` |
| `GET /api/notes/resolve?name=` | 유일하면 path와 단일 후보, 모호하면 null path와 후보 목록 |
| `GET /api/notes/blame?path=&ref=` | 해석된 ref와 줄별 커밋·요청자·작업 출처 범위 |
| `GET /api/history?path=&follow=1&before=&limit=` | 경로별 커밋 이력과 이동 추적 |
| `GET /api/history/compare?base=&head=&path=` | 두 커밋의 파일 변경과 patch |
| `GET /api/history/commits/:sha?parent=N` | 지정 부모 기준 커밋 상세; 이전 `/api/commits/:sha` 경로를 대체 |
| `POST /api/history/revert` | 미리보기 `{ files, patch }` 또는 201 `{ jobId, mergeSha }` |

## 요청자 추적과 실패 복구

일반 커밋과 자동 병합·충돌 해결 커밋의 author는 요청한 사용자이며 committer는 `GIT_BOT_NAME`·`GIT_BOT_EMAIL`의 봇으로 기본값은 `도니 <dony@llmwiki.local>`다. 모든 작업 커밋에 `Wiki-Job`, `Wiki-Source`, `Wiki-Requester`와 선택적 `Wiki-Client` trailer를 기록한다. 사용자의 이름이 없으면 이메일을 사용하고, 실행 전에 사용자가 삭제되면 실패한다. 작업 이력은 사용자 삭제 후에도 보존된다.

실패하면 main을 바꾸지 않고 오류와 만든 커밋을 기록한다. 워크트리 정리 전에 HEAD를 `refs/wiki/failed/<jobId>`에 보존하므로 작업 브랜치를 제거한 뒤에도 실패 커밋을 조회할 수 있다. 추적 파일의 수정·삭제와 추적하지 않은 새 파일도 HEAD를 부모로 하는 별도 스냅샷 커밋으로 `refs/wiki/failed-wip/<jobId>`에 보존한다. 스냅샷은 어떤 브랜치에도 추가하지 않으며 실제 HEAD와 인덱스를 바꾸지 않는다. 워크트리가 깨끗하면 WIP ref를 만들지 않는다. 새 ref 이름은 API base62 ID를 사용하며 이전 UUID ref도 읽는 규칙은 [식별자](identifiers.md)를 따른다. 색인 실패는 이미 main에 반영된 쓰기를 실패로 되돌리지 않으며 단계 세부 정보와 로그에 남긴다. 정리 실패 역시 성공한 쓰기를 무효화하지 않는다.

시작할 때 이전 실행의 running·merging 작업은 중단 사유와 failed 이벤트를 남긴다. 해당 작업의 자식별 최신 스냅샷이 running이면 같은 ID·이름·소유 경로·도구 호출 수를 보존한 cancelled 스냅샷과 `error: 'interrupted'`, 종료 시각을 추가한다. 부모 실패 처리와 자식 종료 이벤트는 같은 DB 트랜잭션으로 기록하며 재시작을 반복해도 종료 이벤트를 중복 추가하지 않는다. 저장소 복구는 버려진 작업 브랜치의 HEAD와 접근 가능한 워크트리의 미커밋 파일을 위 두 ref에 보존한 뒤 워크트리와 브랜치를 제거한다. 디스크에서 이미 사라진 워크트리의 미커밋 파일은 복구할 수 없지만 남은 브랜치의 커밋은 보존한다. 중단된 작업도 실패 작업과 같은 방식으로 이어서 재시도한다. queued 에이전트 작업은 워커에서 다시 처리하고, queued direct/revert 재시도는 에이전트 큐 밖에서 재개한다. `main.ts`가 명시적으로 `WriteJobsService.start()`를 호출하므로 CLI 컨텍스트 생성만으로 에이전트 큐를 소비하지 않는다. 종료는 현재 에이전트 실행과 direct/revert 재시도를 기다린다.

`retry(id)`는 failed 작업의 원래 출처·클라이언트·입력을 유지한 **새 작업**을 만들고 queued 이벤트의 `detail.retryOf`에 원래 ID를 남긴다. 에이전트 작업은 일반 큐로, direct/revert는 바로 머지 락으로 실행한다. direct/revert는 원래 입력을 결정적으로 다시 실행하며 에이전트의 이어서 실행 규칙을 적용하지 않는다. direct 재시도도 원래 baseSha를 사용하므로 충돌한 입력은 다시 stale_note로 실패할 수 있다. 원래 실패 이력은 변경하지 않는다. `cancel(id)`는 queued 상태에서만 원자적으로 상태를 failed, 오류를 `canceled`로 바꾸며 이미 실행 중인 작업은 취소하지 않는다.

에이전트 부모 쓰기 실행은 도구 턴을 마칠 때마다 `agent_checkpoints`의 `job:<jobId>` 소유자에 모델 입력 항목, 누적 텍스트·도구 호출 수·토큰 사용량을 저장한다. 최종 응답을 수락한 턴은 별도 체크포인트를 만들지 않지만 완료 훅이 응답을 거절하면 후속 메시지까지 저장한다. 작업이 성공하면 체크포인트를 삭제한다. 실패 작업에 체크포인트가 있으면 새 작업 생성과 같은 트랜잭션에서 새 소유자로 복사한 뒤 이전 소유자의 것을 삭제하고 queued 이벤트에 `detail.resumedFrom`도 남긴다. 재시도는 이전 모델 대화를 이어가며 턴 한도는 새 실행 기준으로 적용한다. 실패 ref의 커밋에서 새 브랜치를 만들고 WIP 스냅샷은 HEAD에 커밋하지 않은 파일 상태로 복원한다. 체크포인트가 없어도 실패 커밋이나 WIP가 있으면 파일 상태는 유지하고 원래 요청으로 모델 실행만 새로 시작한다. 보존된 상태가 전혀 없을 때만 최신 main에서 기존 방식으로 새로 시작한다. 새 커밋은 새 작업 ID의 메타데이터를 사용하고 기존 커밋은 원래 작업의 출처를 유지한다.

새 작업 행, 체크포인트 이동, 출처와 `retryOf`·`resumedFrom`을 담은 queued 이벤트는 한 DB 트랜잭션으로 저장한다. 따라서 재시도 접수가 중간에 실패해도 원래 체크포인트가 사라지거나 실패 ref를 찾을 연결만 빠진 작업이 남지 않는다.

재시도 시점에 main이 바뀌었어도 보존한 작업 변경을 버리지 않는다. 작업 브랜치와 현재 main의 공통 조상을 기준으로 변경·권한을 검사하며 편집이 끝나면 기존 전역 머지 락 안에서 최신 main을 병합하고 충돌을 해결한다. 이전 서브에이전트의 파일 변경도 WIP에 포함되지만 자식 실행·풀은 재개하지 않는다. 부모의 보존된 대화에 있는 이전 자식 ID는 새 풀에서 `unknown`이며 부모는 실제 파일을 검증하고 필요한 남은 작업을 새 자식에 맡긴다. 이 체크포인트는 부모 쓰기 실행만 대상으로 하며 꿈꾸기와 자식별 실행은 대상이 아니다.

작업 API의 `resumable`은 체크포인트나 보존된 실패 커밋·WIP가 있는 failed 에이전트 작업에만 true다. 작업 상세와 관리자 재시도는 이 경우 `이어서 재시도`, 그 외에는 `새 작업으로 재시도`로 표시한다. 수집 통합 작업의 재시도는 [원문 수집](ingestion.md#통합-작업과-복구)의 import 연결도 새 작업으로 갱신한다.

`GET /api/jobs`와 상세 조회는 소유자 또는 관리자만 허용한다. 상세 결과는 `{ job, user, commits, events }`이며 kind, source, client, conflicts는 job 안에 있다. 서브에이전트 이벤트의 소유 경로와 읽기 배정 경로, 결과·오류는 [쓰기 서브에이전트의 ACL 투영](agent.md#쓰기-서브에이전트)을 따른다. 소유 선언이나 거절된 시도만으로는 원문 접근으로 간주하지 않으므로 공개 작업의 입력·요약 전체를 제한하지 않는다. 목록 커서는 작업 ID를 받으며 생성 시각과 ID를 함께 비교해 같은 시각의 행을 빠뜨리지 않는다. 기존 ISO 시각 커서도 허용한다. 다른 사용자의 커밋을 조회해도 해당 작업에 대한 권한이 없으면 연결된 job은 null이다. `POST /api/jobs/:id/retry`와 `/cancel`은 editor 이상인 소유자 또는 관리자에게 허용하며 `{ job }`을 반환한다.
