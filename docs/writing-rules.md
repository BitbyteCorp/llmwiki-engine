# 지식 작성 규칙

도니는 지식 저장소를 대화 기록의 덤프가 아니라 재사용할 수 있는 지식으로 유지한다.

## 배경

대화의 임시 상태를 그대로 저장하면 시간이 지난 뒤 제목·태그·속성의 의미를 이해하기 어렵고, 비슷한 노트가 흩어져 검색과 탐색도 어려워진다. 이 규칙은 저장할 내용을 먼저 판단하고 기존 지식과 연결하며, 유지할 가치가 있는 본문과 메타데이터만 남기기 위한 기준이다.

사용자가 제공한 Obsidian 규칙을 공통 작성 기준으로 옮기고, 스레드→문서 프롬프트에서는 일반적인 사실성·문체 규칙만 채택한다. 지식 저장소 자체의 schema와 초기 파일은 [지식 저장소의 초기화](knowledge-repository.md#엔진의-로컬-저장소-초기화)에, 분야별 배치와 schema의 적용 범위는 [지식 도메인 구조](knowledge-domains.md)에 설명한다.

## 내용

### 저장 판단과 기존 노트 활용

한 제출에는 오래 유지할 지식과 즉시 필요한 상태가 함께 들어올 수 있다. 이를 한 노트에 쌓으면 검색·재사용이 어려워지므로, 제출 형식이 아니라 미래의 조회 경로에 맞춰 적절한 지식 위치로 분산한다.

1. 저장 전에 제출 내용에 재사용할 규칙, 반복 가능한 패턴, 체크리스트, 색인 또는 프로젝트 지식으로 남길 가치가 있는지 판단한다.
2. 남길 내용을 사실, 결정과 그 이유, 절차, 용어, 담당자·오너십, 일정·상태의 의미 단위로 나눈다. 하나의 제출을 하나의 노트에 맞추지 않는다.
3. 새 노트를 만들기 전에 지식 저장소를 검색하고, 각 단위와 관련된 기존 노트·개념 노트·허브·색인을 읽는다.
4. 각 단위마다 미래의 독자, 필요한 시점, 검색 질문·진입점, 정보의 유효 기간을 고려해 저장 위치를 정한다. 분야별 노트와 공유 정본의 경로는 [도메인 배치 규칙](knowledge-domains.md#노트-배치와-탐색)을 따른다.
5. 오래 유지할 지식은 가장 구체적인 주제의 기존 노트에 확장·정정한다. 여러 주제에서 재사용할 용어·개념은 개념 노트에 둔다. 독립적으로 분명한 목적이 있거나 기존 노트를 비대하게 만들고 주제를 흐릴 때는 새 원자적 노트를 만들며, 사소한 사실마다 작은 노트를 만들지 않는다.
6. 즉시 필요하고 자주 바뀌는 운영 문맥은 `MEMORY.md`에 간결하게 반영한다. 오래 유지할 지식의 본문은 복제하지 않고 해당 노트로 연결한다.
7. 정리한 각 사실은 정확히 하나의 정본 위치에 둔다. 관련 노트에는 짧은 맥락과 정본을 가리키는 `[[위키링크]]`를 남기고, 탐색에 도움이 되는 관련 노트끼리는 양방향으로 연결한다.
8. 큐레이션된 탐색에서 발견되어야 하는 노트를 관련 허브·색인에서 연결한다. 허브의 계층과 새 도메인 생성 조건은 [지식 도메인 구조](knowledge-domains.md#노트-배치와-탐색)를 따른다.
9. 오래 유지할 노트를 저장하기 전에 재사용 가능한 지식보다 현재 대화 상태를 기록하는 데 목적이 있는 제목·속성·태그를 배제한다.
10. 편집 후 커밋·머지 전에 변경 파일의 금지된 섹션 제목, 지나치게 좁은 태그, 중복 속성, 읽기 상태 섹션을 검사한다. Obsidian 원문의 LiveSync 단계는 이 검사 시점으로 대체한다.
11. 최종 요약에서 남긴 모든 의미 단위가 어느 노트·메모리·색인에 반영됐는지 대응시켜 설명한다. 아직 `main`에 머지되었다고 주장하지 않는다.

- 대화를 제거했을 때 의미가 사라지는 섹션 제목은 금지한다.
- 버전, 임시 단계, 구현 세부 사항 또는 일회성 실험을 이름으로 삼는 태그는 금지한다.
- 폴더나 태그 분류를 중복하거나 읽기 진행 상태 또는 임시 프로젝트 상태를 기록하는 속성은 금지한다.

예를 들어 캐시 전략 변경과 장애 대응 현황이 한 번에 제출되면, 변경 결정과 이유는 기존 캐시 전략 결정 노트에 반영한다. 여러 시스템에서 재사용할 캐시 무효화 개념은 공유 개념 정본에, 복구 확인 대기 같은 즉시 필요한 운영 상태는 `MEMORY.md`에 둔다. 해당 분야의 허브와 결정·개념 노트를 필요한 맥락으로 연결한다. 최종 요약에는 결정·개념·상태 각각의 저장 위치와 색인 변경을 설명한다.

`src/agent/writes.ts`의 실행 지침은 업데이트된 엔진이 실행되면 기존 저장소를 포함한 모든 지식 쓰기 작업에 즉시 적용한다.

기존 노트를 찾고 수정 내용을 반영하는 실행 절차는 [쓰기 흐름](write-flow.md)에 설명한다.

### 민감 정보

도니는 API 키, 비밀번호, 토큰과 같은 비밀값의 저장을 거부하고, 개인정보는 마스킹한다.

### 폴더·태그·위키링크·색인의 역할

- 폴더의 분야별 배치와 색인의 계층은 [지식 도메인 구조](knowledge-domains.md#노트-배치와-탐색)를 따른다.
- 태그는 검색·필터링·주제 분류에 사용한다.
- 본문의 위키링크는 큐레이션된 탐색과 직접 참조에 사용한다.
- 색인 노트는 지식을 복제하지 않고 조회 경로를 제공한다.

### Frontmatter

Frontmatter의 필수·선택 속성, 엔진 자동 속성, 허용 값과 적용 범위는 [노트 메타데이터](note-metadata.md)를 따른다. 분야별 schema도 이 공통 표준을 완화하지 않는다.

### 태그 정책

- 태그는 `planning`, `decision-making`과 같은 영어 소문자 kebab-case로 작성한다.
- 태그는 지식 저장소 전반의 노트를 연결할 수 있도록 일반적이고 재사용 가능한 수준으로 유지한다.
- `v2`, `prototype-v2`, `incident-2026-10-10`과 같은 버전·일회성 작업 태그나 임시 프로젝트 상태 라벨을 사용하지 않는다.
- 버전, 실험 단계, 주장 범위, 프로젝트별 결정 맥락은 태그가 아니라 노트 제목이나 본문에 적는다.
- 여러 노트를 발견하는 데 도움이 되면 `planning`, `decision-making`, `communication`, `learning`, `maintenance`, `risk-management`와 같은 재사용 가능한 주제 태그를 우선한다.
- 새 태그를 추가하기 전에 기존의 더 넓은 태그가 해당 노트를 적합한 주제 묶음에 연결하는지 확인한다.

### 분야별 속성

논문의 외부 식별자와 분야 전용 속성 규칙은 [연구 도메인 schema 예시](knowledge-domains.md#연구-도메인-schema-예시)에 둔다. 다른 분야의 전용 속성도 공통 [노트 메타데이터](note-metadata.md)를 확장하는 범위에서 그 도메인의 schema로 정한다.

### 사실성과 읽기 맥락

- 노트 본문은 한국어로 작성한다.
- 근거에 없는 내용을 지어내지 않는다.
- 템플릿 안내 문구나 `[이름]`, `<!-- 주석 -->` 같은 placeholder를 남기지 않는다.
- 대화를 그대로 옮기지 않으며, 발언자 이름은 담당자·오너십을 밝힐 때만 사용한다.
- 결론이 나지 않은 논의는 열린 쟁점으로 명시한다.
- 문체는 평서형 종결인 `~다`로 통일한다.
- 6개월 뒤 맥락을 모르는 독자가 읽어도 이해할 수 있게 쓴다.

엔진에는 스레드→문서 고정 템플릿이 없으므로 원문의 H1·메타데이터 생략, 고정 템플릿 섹션, 채택 대안의 `(채택)` 표시, 실행 계획 체크박스, 소급 기록 방식은 채택하지 않는다.

## 관련 문서

- [지식 저장소](knowledge-repository.md)는 작성 규칙을 담는 schema와 노트 배치를 설명한다.
- [지식 도메인 구조](knowledge-domains.md)는 노트 경로와 공유 정본, 허브 및 분야별 schema를 설명한다.
- [노트 메타데이터](note-metadata.md)는 공통 frontmatter 표준과 엔진 자동 속성을 설명한다.
- [쓰기 흐름](write-flow.md)은 검색 후 기존 노트를 확장하거나 새 노트를 만드는 절차를 설명한다.
- [꿈꾸기](dreaming.md)는 이 규칙을 적용해 누적된 지식을 정리하는 작업을 설명한다.
