# 도니의 지식 작성 schema

도니는 이 지식 저장소를 대화 기록의 덤프가 아니라 재사용할 수 있는 지식으로 유지한다. 이 파일은 지식 작성·정리·답변의 기준이며, 엔진 개발이나 배포를 위한 작업 규칙이 아니다.

## 저장소 구조와 문맥

이 저장소는 엔진의 개발 문서와 분리된 지식 저장소다. `main`이 진실 원천이며, 쓰기와 dreaming에서는 `main`에서 파생한 작업 워크트리 안에서만 편집한다. GitHub는 dreaming 후 하루 한 번 push하는 백업이므로 최신 지식은 `main`을 기준으로 확인한다.

```text
.
├── raw/
├── wiki/
├── index.md
├── journal/
│   └── YYYY-MM-DD.md
├── MEMORY.md
└── AGENTS.md
```

- `raw/`는 불변 원문 소스를 담는다. 원문을 보관할 때는 실제로 제공된 텍스트만 추가하며, 이미 보관한 원문을 수정·삭제·이동하거나 정리된 내용으로 덮어쓰지 않는다. 원문의 오류나 바뀐 사실은 원문을 보존한 채 `wiki/` 노트에서 설명한다. 현재 원문 수집 대상은 텍스트이며 파일·URL·PDF 업로드는 대상이 아니다.
- `wiki/`는 도니가 유지하는 노트를 담는다. Frontmatter, 태그, 위키링크를 사용하며 Obsidian 볼트로 읽을 수 있다.
- `index.md`는 중요한 진입점을 선별한 큐레이션 색인이다. 파일 전체 목록이나 대화 기록이 아니라 실제로 존재하는 노트로 안내한다.
- `journal/YYYY-MM-DD.md`는 dreaming이 날짜별로 쓰는 일기다. LLM Wiki 표준의 `log.md`를 대신하며, 개별 변경의 세부 이력은 git 커밋 이력에 남긴다.
- `MEMORY.md`는 즉시 필요한 자주 바뀌는 정보를 담는 도니 전용 문맥이다. 사용자별 파일이 아니라 전체 공용 파일 하나를 유지하며, 쓰기·dreaming·웹 질의응답으로 도니를 실행할 때마다 항상 문맥에 포함된다. 필요한 실제 정보가 있을 때 갱신하며, 오래 유지할 지식은 적합한 `wiki/` 노트에 정리한다.
- `AGENTS.md`는 이 저장소의 지식 schema이며 도니의 작성 규칙을 담는다.
- 각 `raw/`, `wiki/`, `journal/`의 `.gitkeep`는 빈 디렉터리를 git에 보존하기 위한 파일이며 지식 노트가 아니다.

Obsidian 규칙의 LiveSync는 사용하지 않으며 git 동기화로 대체한다. 위키의 진입점은 `index.md`, 날짜별 정리 내용은 `journal/YYYY-MM-DD.md`, 개별 변경은 git 커밋 이력에서 확인한다.

## 저장 판단과 기존 노트 활용

1. 저장 전에 내용이 재사용할 규칙, 반복 가능한 패턴, 체크리스트, 색인 또는 프로젝트별 노트 중 무엇인지 판단한다.
2. 새 노트를 만들기 전에 지식 저장소를 검색한다. 새 내용이 적합한 기존 노트에 속하면 그 노트를 확장하며, 독립적으로 분명한 목적이 있을 때만 새 노트를 만든다.
3. 큐레이션된 탐색에서 발견되어야 하는 새 노트는 관련 색인 노트에서 연결한다. 필요하면 `index.md`와 메모리 파일도 갱신한다.
4. 오래 유지할 노트를 저장하기 전에 재사용 가능한 지식보다 현재 대화 상태를 기록하는 데 목적이 있는 제목·속성·태그를 배제한다.
5. 편집 후 커밋·머지 전에 변경 파일의 금지된 섹션 제목, 지나치게 좁은 태그, 중복 속성, 읽기 상태 섹션을 검사한다. Obsidian 원문의 LiveSync 단계는 이 검사 시점으로 대체한다.

대화를 제거했을 때 의미가 사라지는 섹션 제목은 금지한다. 버전, 임시 단계, 구현 세부 사항 또는 일회성 실험을 이름으로 삼는 태그는 금지한다. 폴더나 태그 분류를 중복하거나 읽기 진행 상태 또는 임시 프로젝트 상태를 기록하는 속성은 금지한다.

편집은 의미 단위마다 커밋하며, 한 작업에서도 여러 번 커밋할 수 있다. main 머지는 엔진이 직렬 처리하며, 충돌은 작업 워크트리에서 해결한다. 커밋의 author는 요청한 사용자, committer는 도니 봇 계정으로 구분한다. 잘못된 지식은 별도의 되돌리기나 승인 절차가 아니라 정정 쓰기 요청으로 기존 노트에 반영한다.

## 민감 정보

도니는 API 키, 비밀번호, 토큰과 같은 비밀값의 저장을 거부하고, 개인정보는 마스킹한다. 이 기준은 노트뿐 아니라 원문, 메모리, 일기에도 적용한다.

## 폴더·태그·위키링크·색인의 역할

- 폴더는 지식 저장소의 큰 구조를 나누는 데 사용한다.
- 태그는 검색·필터링·주제 분류에 사용한다.
- 본문의 위키링크는 큐레이션된 탐색과 직접 참조에 사용한다.
- 색인 노트는 한 영역의 중요한 진입점을 모으는 데 사용한다.

## Frontmatter

- Frontmatter는 최소한으로 유지하며 Obsidian에서 유용한 속성만 둔다.
- 노트의 유지·관리 맥락을 눈에 보이게 남길 필요가 있으면 `updated`를 둔다.
- 운영 규칙이나 검토 기준을 나타내는 노트에는 `importance`를 둔다.
- `importance`의 값은 `high`, `medium`, `low`만 사용한다.
- 폴더와 태그가 이미 같은 정보를 표현하면 `category`, `domain`, `status`와 같은 중복 분류 속성을 추가하지 않는다.
- `belongs_to`, `has`, `related`, `related_to`와 같은 사용자 정의 관계 속성을 추가하지 않는다. 직접 참조는 본문의 위키링크로 표현한다.

## 태그 정책

- 태그는 `kv-cache`와 같은 영어 소문자로 작성한다.
- 태그는 지식 저장소 전반의 노트를 연결할 수 있도록 일반적이고 재사용 가능한 수준으로 유지한다.
- `v2`, `arxiv-v2`, `guardrail`과 같은 버전·구현 세부 사항·일회성 작업 태그나 임시 프로젝트 상태 라벨을 사용하지 않는다.
- 버전, 실험 단계, 주장 범위, 프로젝트별 결정 맥락은 태그가 아니라 노트 제목이나 본문에 적는다.
- 여러 노트를 발견하는 데 도움이 되면 `papers`, `research-ideas`, `cask`, `kv-cache`, `reasoning`, `inference`, `evaluation`, `llm-agents`와 같은 넓은 주제 태그를 우선한다.
- 새 태그를 추가하기 전에 기존의 더 넓은 태그가 해당 노트를 적합한 주제 묶음에 연결하는지 확인한다.

## 논문 노트의 속성

- 논문 읽기 상태를 frontmatter의 `status`나 `Read Status` 섹션으로 기록하지 않는다. 눈에 보이는 유지·관리 신호로는 `updated`를 사용한다.
- `source`, `pdf`, `arxiv` 속성은 논문 노트에서 정식 외부 식별자를 가리킬 때만 둔다. 이 속성은 분류가 아니라 출처 메타데이터다.
- 프로젝트 방향을 나타내기 위한 버전이나 실험 단계 속성을 추가하지 않는다. 버전과 주장 범위는 제목이나 본문에 적는다.
- 검색·필터링·출처 조회에 유용하지 않은 속성은 추가하지 않는다.

## 사실성과 읽기 맥락

- 노트 본문은 한국어로 작성한다.
- 근거에 없는 내용을 지어내지 않는다. 빈 저장소에는 예시 지식이나 존재하지 않는 노트의 링크를 채워 넣지 않는다.
- 템플릿 안내 문구나 `[이름]`, `<!-- 주석 -->` 같은 placeholder를 남기지 않는다.
- 대화를 그대로 옮기지 않으며, 발언자 이름은 담당자·오너십을 밝힐 때만 사용한다.
- 결론이 나지 않은 논의는 열린 쟁점으로 명시한다.
- 문체는 평서형 종결인 `~다`로 통일한다.
- 6개월 뒤 맥락을 모르는 독자가 읽어도 이해할 수 있게 쓴다.

## 채택한 규칙과 채택하지 않은 형식

Obsidian 규칙에서는 저장 판단, 기존 노트 활용, 폴더·태그·위키링크·색인의 역할, 최소 Frontmatter, 태그 정책, 논문 속성 규칙을 채택한다. LiveSync 자체는 채택하지 않으며 git 동기화와 커밋·머지 전 검사로 대체한다.

스레드→문서 프롬프트에서는 일반적인 사실성·문체 규칙만 채택한다. 이 저장소에는 스레드→문서 고정 템플릿이 없으므로 원문의 H1·메타데이터 생략, 고정 템플릿 섹션, 채택 대안의 `(채택)` 표시, 실행 계획 체크박스, 소급 기록 방식은 채택하지 않는다. 제목·본문·최소 메타데이터는 노트의 목적과 위 규칙에 맞게 구성한다.
