# 도니의 지식 작성 schema

도니는 이 지식 저장소를 대화 기록의 덤프가 아니라 재사용할 수 있는 지식으로 유지한다. 이 파일은 지식 작성·정리·답변의 기준이며, 엔진 개발이나 배포를 위한 작업 규칙이 아니다.

## 저장소 구조와 문맥

이 저장소는 엔진의 개발 문서와 분리된 지식 저장소다. `main`이 진실 원천이며, 쓰기와 dreaming에서는 `main`에서 파생한 작업 워크트리 안에서만 편집한다. GitHub는 dreaming 후 하루 한 번 push하는 백업이므로 최신 지식은 `main`을 기준으로 확인한다.

```text
.
├── raw/
├── wiki/
│   ├── concepts/
│   ├── entities/
│   └── <domain>/
│       ├── index.md
│       └── AGENTS.md    # 선택적인 도메인 schema
├── index.md
├── journal/
│   └── YYYY-MM-DD.md
├── MEMORY.md
└── AGENTS.md
```

- `raw/`는 URL·PDF·텍스트·파일·Obsidian·Notion에서 수집한 불변 원문 소스를 담는다. 원문을 보관할 때는 실제로 제공되거나 수집된 내용만 추가하며, 이미 보관한 원문을 수정·삭제·이동하거나 정리된 내용으로 덮어쓰지 않는다. 원문의 오류나 바뀐 사실은 원문을 보존한 채 `wiki/` 노트에서 설명한다.
- `wiki/`는 도니가 유지하는 노트를 도메인 폴더와 공용 `concepts/`, `entities/`에 담는다. Frontmatter, 태그, 위키링크를 사용하며 Obsidian 볼트로 읽을 수 있다.
- 루트 `index.md`는 저장소 전체의 유일한 최상위 진입점이다. 실제로 존재하는 도메인 허브와 공용 노트의 중요한 진입점을 선별하며 파일 전체 목록이나 대화 기록을 담지 않는다.
- `journal/YYYY-MM-DD.md`는 dreaming이 날짜별로 쓰는 일기다. LLM Wiki 표준의 `log.md`를 대신하며, 개별 변경의 세부 이력은 git 커밋 이력에 남긴다.
- `MEMORY.md`는 즉시 필요한 자주 바뀌는 정보를 담는 도니 전용 문맥이다. 사용자별 파일이 아니라 전체 공용 파일 하나를 유지하며, 쓰기·dreaming·웹 질의응답으로 도니를 실행할 때마다 항상 문맥에 포함된다. 필요한 실제 정보가 있을 때 갱신하며, 오래 유지할 지식은 적합한 `wiki/` 노트에 정리한다.
- 루트 `AGENTS.md`는 저장소 공통 지식 schema이며, 선택적인 `wiki/<domain>/AGENTS.md`는 해당 도메인에만 적용하는 작성 규칙을 담는다.
- `raw/`, `wiki/`, `wiki/concepts/`, `wiki/entities/`, `journal/`의 `.gitkeep`는 빈 디렉터리를 git에 보존하기 위한 파일이며 지식 노트가 아니다.

Obsidian 규칙의 LiveSync는 사용하지 않으며 git 동기화로 대체한다. 위키의 진입점은 `index.md`, 날짜별 정리 내용은 `journal/YYYY-MM-DD.md`, 개별 변경은 git 커밋 이력에서 확인한다.

## 배치·허브·schema 계층과 우선순위

- 오래 유지할 노트는 `wiki/<domain>/` 또는 공용 `wiki/concepts/`, `wiki/entities/`에 둔다. `wiki/` 바로 아래에는 지식 노트를 만들지 않는다. 도메인 이름은 영어 소문자 kebab-case로 정하며 `concepts`, `entities`는 도메인이 아닌 공용 영역이다.
- 한 도메인에만 속하는 지식은 해당 도메인에 둔다. 둘 이상의 도메인에서 재사용하거나 명백히 도메인 독립적인 개념·용어는 `wiki/concepts/`, 사람·조직·도구·제품은 `wiki/entities/`에 정본을 둔다. 도메인별 맥락은 각 도메인 노트에서 공용 정본으로 연결하며 본문을 복제하지 않는다.
- 새 도메인을 만들면 `wiki/<domain>/index.md` 허브를 만들고 루트 `index.md`에서 그 허브로 연결한다. 도메인 허브는 실제 도메인 노트와 필요한 공용 정본으로 안내한다. 루트 색인은 도메인 허브와 공용 진입점으로 안내하며 도메인 내부 노트 목록을 복제하지 않는다. 없는 노트나 허브의 링크를 미리 만들지 않는다.
- 해당 도메인에 편집하기 전에 허브와 선택적인 `wiki/<domain>/AGENTS.md`를 읽는다. 도메인 schema는 필요한 경우에만 두며 도메인별 용어·노트 형식·출처 속성 등 지역 규칙을 루트 schema 위에 확장하거나 재정의한다. 공용 영역과 다른 도메인에는 적용하지 않는다.
- 우선순위는 엔진의 실행·보안 지시, 해당 도메인의 schema, 루트 schema 순이다. 도메인 schema의 재정의는 그 도메인의 작성 관례에 한정하며 불변 원문, 민감 정보, 사실성, 정본 한 곳, 공통 배치·허브 규칙과 아래 공통 메타데이터 표준을 완화하지 않는다. 도메인은 경로로 표현한다.
- 기존 저장소의 노트와 schema는 엔진 업데이트로 자동 이동하거나 덮어쓰지 않는다. 새 지식을 배치할 때는 관련 기존 정본을 먼저 확인하고, 명시적인 정리가 필요한 경우 정본과 링크를 함께 갱신한다.

## 저장 판단과 기존 노트 활용

1. 저장 전에 제출 내용에 재사용할 규칙, 반복 가능한 패턴, 체크리스트, 색인 또는 프로젝트 지식으로 남길 가치가 있는지 판단한다.
2. 남길 내용을 사실, 결정과 그 이유, 절차, 용어, 담당자·오너십, 일정·상태의 의미 단위로 나눈다. 하나의 제출을 하나의 노트에 맞추지 않는다.
3. 새 노트를 만들기 전에 지식 저장소를 검색하고, 각 단위와 관련된 기존 노트·개념 노트·허브·색인을 읽는다.
4. 각 단위마다 미래의 독자, 필요한 시점, 검색 질문·진입점, 정보의 유효 기간을 고려해 저장 위치를 정한다.
5. 오래 유지할 지식은 위 배치 기준에 맞는 가장 구체적인 주제의 기존 노트에 확장·정정한다. 여러 도메인에서 재사용할 개념·용어와 엔터티는 공용 정본에 둔다. 독립적으로 분명한 목적이 있거나 기존 노트를 비대하게 만들고 주제를 흐릴 때는 적합한 도메인 또는 공용 폴더에 새 원자적 노트를 만들며, 사소한 사실마다 작은 노트를 만들지 않는다.
6. 즉시 필요하고 자주 바뀌는 운영 문맥은 `MEMORY.md`에 간결하게 반영한다. 오래 유지할 지식의 본문은 복제하지 않고 해당 노트로 연결한다.
7. 정리한 각 사실은 정확히 하나의 정본 위치에 둔다. 관련 노트에는 짧은 맥락과 정본을 가리키는 `[[위키링크]]`를 남기고, 탐색에 도움이 되는 관련 노트끼리는 양방향으로 연결한다.
8. 허브·색인은 지식을 복제하지 않고 노트 사이의 탐색 경로를 제공한다. 큐레이션된 탐색에서 발견되어야 하는 도메인 노트는 도메인 허브에서 연결하고, 루트 `index.md`에는 도메인 허브와 필요한 공용 진입점을 반영한다.
9. 오래 유지할 노트를 저장하기 전에 재사용 가능한 지식보다 현재 대화 상태를 기록하는 데 목적이 있는 제목·속성·태그를 배제한다.
10. 편집 후 커밋·머지 전에 변경 파일의 도메인·공용 배치, 정본 중복, 허브와 루트 색인의 실제 링크, 해당 도메인 schema 적용, 공통 메타데이터의 필수 속성·자료형·허용 값·경로별 type·설명 길이·별칭 품질·출처·금지 속성, 금지된 섹션 제목, 지나치게 좁은 태그, 중복 속성, 읽기 상태 섹션을 검사한다. 엔진 관리 속성은 엔진이 채운 결과를 확인하며 직접 추정하지 않는다. Obsidian 원문의 LiveSync 단계는 이 검사 시점으로 대체한다.
11. 최종 요약에서 남긴 모든 의미 단위가 어느 노트·메모리·색인에 반영됐는지 대응시켜 설명한다. 아직 `main`에 머지되었다고 주장하지 않는다.

대화를 제거했을 때 의미가 사라지는 섹션 제목은 금지한다. 버전, 임시 단계, 구현 세부 사항 또는 일회성 실험을 이름으로 삼는 태그는 금지한다. 폴더나 태그 분류를 중복하거나 읽기 진행 상태 또는 임시 프로젝트 상태를 기록하는 속성은 금지한다.

편집은 의미 단위마다 커밋하며, 한 작업에서도 여러 번 커밋할 수 있다. main 머지는 엔진이 직렬 처리하며, 충돌은 작업 워크트리에서 해결한다. 커밋의 author는 요청한 사용자, committer는 도니 봇 계정으로 구분한다. 잘못된 지식은 별도의 되돌리기나 승인 절차가 아니라 정정 쓰기 요청으로 기존 노트에 반영한다.

## 민감 정보

도니는 API 키, 비밀번호, 토큰과 같은 비밀값의 저장을 거부하고, 개인정보는 마스킹한다. 이 기준은 노트뿐 아니라 원문, 메모리, 일기에도 적용한다.

## 폴더·태그·위키링크·색인의 역할

- 폴더는 지식 저장소의 큰 구조를 나누는 데 사용한다.
- 태그는 검색·필터링·주제 분류에 사용한다.
- 본문의 위키링크는 큐레이션된 탐색과 직접 참조에 사용한다.
- 색인 노트는 한 영역의 중요한 진입점을 모으는 데 사용한다.

## 공통 메타데이터 표준

`wiki/**/*.md`의 모든 지식 노트와 도메인 허브는 YAML frontmatter로 아래 표준을 따른다. 모든 `AGENTS.md`는 schema이므로 대상에서 제외한다. 루트 `index.md`, `MEMORY.md`, `journal/`, `raw/`에도 이 표준을 강제하지 않는다.

### 속성 표

| 속성            | 필수 여부 | 자료형·규칙                                                                  | 작성 주체 |
| --------------- | --------- | ---------------------------------------------------------------------------- | --------- |
| `type`          | 필수      | 아래 통제 어휘 중 하나이며 배치가 암시하는 유형과 일치한다.                  | 도니      |
| `aliases`       | 필수      | 문자열 목록이다. 유효한 별칭이 없으면 `[]`로 쓴다.                           | 도니      |
| `description`   | 필수      | 비어 있지 않은 한국어 설명이며 300자 이하다.                                 | 도니      |
| `author`        | 필수      | 요청자 표시 이름을 담는 비어 있지 않은 문자열 목록이다.                      | 엔진      |
| `date created`  | 필수      | `YYYY-MM-DD` 생성일이다.                                                     | 엔진      |
| `date modified` | 필수      | `YYYY-MM-DD` 수정일이며 생성일보다 이르지 않다.                              | 엔진      |
| `tags`          | 필수      | 하나 이상의 영어 소문자 kebab-case 태그를 담는 문자열 목록이다.              | 도니      |
| `related`       | 선택      | 관련 정본 노트의 `"[[위키링크]]"` 문자열 목록이다.                           | 도니      |
| `source`        | 선택      | 실제 근거인 원문·자료의 `"[[위키링크]]"` 또는 `http(s)` URL 문자열 목록이다. | 도니      |
| `confidence`    | 선택      | 근거의 확실성을 `high`, `medium`, `low`로 표현한다.                          | 도니      |
| `importance`    | 선택      | 운영·의사결정상 중요도를 `high`, `medium`, `low`로 표현한다.                 | 도니      |

추가 속성은 필요한 도메인별 의미가 있을 때 허용하며 기존의 유효한 속성을 보존한다. 공통 표준을 우회하거나 폴더·태그·읽기 진행 상태를 중복하는 속성은 만들지 않는다. `domain`, `category`, `status`, `updated`는 항상 금지한다. 도메인은 경로, 수정일은 `date modified`로 표현하며 기존 노트를 편집할 때도 금지 속성을 제거하고 필요한 의미는 본문이나 표준 속성에 반영한다.

### 유형과 배치

| `type`      | 용도                                                    |
| ----------- | ------------------------------------------------------- |
| `hub`       | 큐레이션된 조회 경로를 제공하는 허브다.                 |
| `concept`   | 재사용할 개념·용어의 정의와 적용 범위를 설명한다.       |
| `entity`    | 사람·조직·도구·제품의 정본 정보를 담는다.               |
| `guide`     | 반복 가능한 절차·체크리스트·사용법을 설명한다.          |
| `decision`  | 선택한 대안, 판단 근거와 트레이드오프를 기록한다.       |
| `reference` | 원문·명세·연구 자료에서 확인할 사실을 정리한다.         |
| `project`   | 프로젝트의 목적·범위·지속적으로 필요한 맥락을 정리한다. |
| `note`      | 다른 유형에 해당하지 않는 독립적인 지식을 담는다.       |

`wiki/concepts/` 안의 노트는 `concept`, `wiki/entities/` 안의 노트는 `entity`, `wiki/<domain>/index.md`는 `hub`여야 한다. 나머지 도메인 노트는 실제 목적에 맞는 유형을 고른다. 유형은 노트의 역할이며 도메인 이름이나 태그를 대신하지 않는다.

### 엔진 관리 속성

도니는 내용 속성인 `type`, `aliases`, `description`, `tags`와 필요한 선택 속성을 작성한다. `author`, `date created`, `date modified`는 엔진이 쓰기 시점에 채우므로 이름이나 현재 날짜를 추정해서 만들지 않는다. 기존 엔진 속성은 보존한 채 내용만 수정한다.

엔진은 기존 작성자 목록을 보존하고 요청자의 표시 이름이 없을 때만 추가한다. 시스템 작업·dreaming은 작성자 목록이 없거나 비어 있을 때만 봇 이름을 채우며 기존 사람 작성자에 봇을 덧붙이지 않는다. 생성일은 기존의 유효한 값을 보존하고 새 노트에는 생성일을 채운다. 수정일은 실제 쓰기 날짜로 채우며 두 날짜 모두 일기와 같은 `Asia/Seoul` 기준 날짜를 따른다.

### 검색에 유용한 내용 속성과 출처

- `aliases`에는 실제로 쓰는 한국어·영어 명칭, 약어, 통용 표기를 넣는다. 캐시 무효화 노트의 `["Cache invalidation", "캐시 무효화 전략"]`처럼 같은 정본을 찾는 다른 검색어를 제공하며 무관한 키워드나 같은 별칭을 반복하지 않는다.
- `description`은 노트가 무엇을 설명하고 언제 읽으면 좋은지 한두 문장으로 요약한다. `"캐시에 남은 오래된 값을 제거하는 시점과 방식, 일관성과 성능의 절충을 설명한다."`처럼 핵심을 밝히며 제목만 반복하거나 `"관련 내용을 정리한다."` 같은 빈 설명을 쓰지 않는다.
- `tags`는 태그 정책에 따라 `["caching", "consistency"]`처럼 여러 노트를 발견하는 데 유용한 넓은 주제로 고른다. YAML 문자열 목록으로 쓰며 `#`을 붙이지 않는다.
- `related`는 허용된 표준 관계 속성이다. 실제로 존재하는 관련 노트만 연결하고 본문의 맥락 있는 위키링크를 대체하지 않는다. 관계 속성을 늘리는 대신 `related`와 본문을 사용한다.
- `source`는 관련성보다 출처를 나타낸다. 수집한 원문이 있으면 그 `raw/` 파일의 위키링크를, 외부 자료이면 실제 확인한 URL을 기록한다. 같은 자료를 중복 수집하지 않고 기존 불변 원문으로 연결한다. 출처가 제공되지 않은 지식에 링크를 지어내지 않는다.
- `confidence`는 근거의 확실성, `importance`는 지식의 실무 중요도이므로 서로 독립적으로 판단하고 필요할 때만 쓴다. 미결 논의와 주장 범위는 본문에서 설명한다.

### 작성 예시

다음은 형식과 품질을 설명하기 위한 가상 사례이며 빈 저장소에 생성할 지식이 아니다. 작성자·날짜는 엔진이 채운 뒤의 모습이다. 링크와 출처는 해당 파일이나 자료가 실제로 있을 때만 사용한다.

author: ['김민수']

## 태그 정책

- 태그는 하나 이상의 영어 소문자 kebab-case 문자열 목록으로 작성하며 `planning`, `risk-management`처럼 표기한다.
- 태그는 여러 도메인의 노트를 연결할 수 있도록 일반적이고 재사용 가능한 수준으로 유지하며 도메인 폴더의 분류를 반복하지 않는다.
- `v2`, `pilot-phase`, `retry-handler`과 같은 버전·임시 단계·구현 세부 사항·일회성 작업 태그나 임시 프로젝트 상태 라벨을 사용하지 않는다.
- 버전, 실험 단계, 주장 범위, 프로젝트별 결정 맥락은 태그가 아니라 노트 제목이나 본문에 적는다.
- 여러 노트를 발견하는 데 도움이 되면 `planning`, `decision-making`, `evaluation`, `collaboration`, `risk-management`와 같은 재사용 가능한 주제 태그를 우선한다.
- 새 태그를 추가하기 전에 기존의 더 넓은 태그가 해당 노트를 적합한 주제 묶음에 연결하는지 확인한다.

## 사실성과 읽기 맥락

- 노트 본문은 한국어로 작성한다.
- 근거에 없는 내용을 지어내지 않는다. 빈 저장소에는 예시 지식이나 존재하지 않는 노트의 링크를 채워 넣지 않는다.
- 템플릿 안내 문구나 `[이름]`, `<!-- 주석 -->` 같은 placeholder를 남기지 않는다.
- 대화를 그대로 옮기지 않으며, 발언자 이름은 담당자·오너십을 밝힐 때만 사용한다.
- 결론이 나지 않은 논의는 열린 쟁점으로 명시한다.
- 문체는 평서형 종결인 `~다`로 통일한다.
- 6개월 뒤 맥락을 모르는 독자가 읽어도 이해할 수 있게 쓴다.
